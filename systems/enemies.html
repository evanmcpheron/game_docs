Enemy bodies, decisions and rewards

Share live-body components while keeping AI decisions and reward ownership separate.

How to use this chapter

Follow the linked phase in order, then open individual asset pages for exact parents, folders, fields, functions and tests. Narrative recipes are suggested implementation details around the preserved architectural ownership rules.

Separate the reusable body from decisions

Create BP_EnemyBase from PaperZDCharacter, add the shared Stats/Health/ActionState/Combat components and configure the inherited PaperZD Animation component with ABP_EnemyTest and implement BPI_Damageable. Configure BP_EnemyAIController as its AI Controller Class and the appropriate auto-possession policy for placed and spawned test enemies. The two child Blueprints inherit initialization, interruption and death handling; they select melee or ranged attack behavior/data.

A different health number belongs in BPDA_EnemyDefinition, not another inheritance level. A stationary NPC does not inherit this family just to display a sprite. Ordinary enemy runtime state may reset on area load; a specifically unique placement adds PersistentState and must be suppressed before AI if its world record is Completed.

ABP_EnemyTest reads movement/action/health facts for Idle, Move, Attack, Hit and Death. Its source/sequences are development fixtures. AI and Combat remain separate from the animation state machine; a missing notify cannot suppress damage, rewards or action cleanup.

Use the small committed brain

Idle → Patrol when local patrol intent is appropriate
Idle/Patrol → Approach when a valid visible target is reachable
Approach → request Combat attack when range/geometry permit
Accepted attack → WaitingForAttack until Combat ends/cancels
Any live state → Dead when Health reports legitimate death

ThinkInterval near 0.10 seconds is a starting test value. That timer chooses DesiredMoveAxis, target and attack request. The body still applies its current movement intent every simulation update. Applying movement only on the think timer causes pulsed motion and is not a reason to rewrite Character Movement.

Probe for floor support ahead and blocking walls before choosing a walk direction. Use simple range/line-of-sight tests consistent with the attack’s real geometry. This baseline does not solve arbitrary multi-platform navigation, and it must not claim a 3D NavMesh automatically supplies that behavior.

Attack timing stays in Combat

AI requests an attack; Combat accepts/rejects and owns Windup/Active/Recovery. WaitingForAttack observes completion instead of maintaining another telegraph timer. A ranged child uses the existing attack’s active-entry projectile hook, with one projectile per accepted execution, not one spawn every think or active frame.

Rewards follow legitimate death once

Health emits lethal once. EnemyBase sets its local reward guard before observable callbacks, stops brain/movement/attacks, and requests GI. Ordinary enemies use GrantReward; a unique encounter uses CommitUniqueEncounter so completion and reward agree. A loaded Completed record suppresses the encounter without invoking the legitimate-death path.

Test an ordinary and unique enemy side by side: defeat, travel away/back, then save and relaunch. The ordinary encounter may return and reward again after reset. The unique one remains completed and cannot duplicate its reward. Change enemy art or remove the HUD; neither must change that outcome.

Canonical roadmap reference · PART O — Enemy architecture

Current guidance retains gameplay policy and incorporates the PaperZD architecture decision. Historical source text remains in the unchanged original roadmap. E-number references belong to the original roadmap; see verification notes.

Use BP_EnemyBase, a Blueprint Class derived from PaperZDCharacter → PaperCharacter → Character, with Stats, Health, ActionState and Combat, plus inherited PaperZD presentation configured with ABP_EnemyTest. Create BP_Enemy_MeleeBasic and BP_Enemy_RangedBasic as child Blueprint Classes of BP_EnemyBase → PaperZDCharacter → PaperCharacter → Character. Use BP_EnemyAIController, a Blueprint Class derived from AIController, and assign it as the enemy's AI Controller Class with auto-possession appropriate for placed and spawned enemies.

The base owns component wiring, receiving damage, death handling, interruption, facing, and the reward guard. A child overrides only attack selection or movement-intent policy that actually differs. Tuning comes from BPDA_EnemyDefinition (PrimaryDataAsset) instances. A new health value or projectile speed is not a reason for another inheritance layer.

Default AI: a small Blueprint state machine

Use E_EnemyBrainState, a Blueprint Enumeration asset with no parent, for Idle, Patrol, Approach, WaitingForAttack, and Dead. The AIController owns target selection and decisions. Combat owns windup/active/recovery timing, so the AI waits for its result rather than running a second competing telegraph timer.

A think timer can update detection and decisions around every 0.1 seconds. The body must still apply its current movement intent every simulation frame; calling Add Movement Input only once every 0.1 seconds can produce pulsed movement. Check a floor probe ahead and a wall probe before walking. Use simple range/line-of-sight tests and reachable attack geometry; do not assume a 3D NavMesh will solve 2D platform traversal.

Behavior Trees or State Trees become useful when multiple enemy behaviors require richer reusable task orchestration. They are not the primary recommendation for this initial two-family slice. No custom BT Task or StateTree task assets are required now.

Ordinary enemies get fresh runtime state after an area reload. A unique enemy additionally has BPC_PersistentState (ActorComponent) with an authored stable ID. If its completion record is present, suppress the encounter before AI/reward execution starts. Completing it updates its record and reward in one GameInstance transaction, so reloading cannot grant the same unique reward again.
