System implementation guide

Paper2D + PaperZD animation

Paper2D renders; PaperZD orchestrates characters; gameplay owners decide the rules.

One animation architecture

Paper2D = 2D assets and rendering foundation. PaperZD = complex character animation orchestration. Gameplay systems = authoritative gameplay state and rules. PaperZD uses Paper2D; it does not replace it.

Sprite assets → Paper2D Flipbooks → PaperZD Animation Sequences
             → PaperZD Animation Blueprint / state machine → character

CharacterMovement / Health / ActionState / Combat / Abilities
             → read-only PaperZD AnimInstance observations → presentation

Paper2D owns sprites, sprite sheets, PaperFlipbooks, TileSets and TileMaps. Use Paper2D directly for straightforward prop/environment loops such as torches, waterfalls, pickups and background effects unless a concrete orchestration requirement justifies PaperZD. PaperZD owns Animation Sources, sequences, Animation Blueprints, transitions, state machines, notifies/notify states and character playback for the player, enemies, animated NPCs, and any later approved bosses or other complex characters. No boss assets or new gameplay mechanics are added by this decision.

Install and compose characters

Enable Paper2D, PaperZD and Enhanced Input. PaperZD is a third-party plugin; choose and record an installation compatible with the actual UE 5.8.3/toolchain and verify an Editor build and packaged slice in the game project. This repository has no plugin installation or game build to prove compatibility. Compilation or packaging failure is an installation issue to resolve, not a reason to retain a competing body animator.

BP_PlayerCharacter and BP_EnemyBase use PaperZDCharacter → PaperCharacter → Character (APaperZDCharacter). It retains native capsule/CharacterMovement and integrates the inherited Paper2D Sprite with the native PaperZD Animation component. Configure its AnimInstanceClass; do not add a second animation component. Enemy children retain BP_EnemyBase as their direct parent.

BP_NPCBase remains Actor for the stationary dialogue fixture. When a stationary NPC is animated, add one native PaperZD Animation component, link its PaperFlipbookComponent render reference and assign a source-compatible PaperZD AnimBP. Use PaperZDCharacter for an ordinary moving animated NPC when CharacterMovement is actually needed. Keep interaction and dialogue ownership unchanged; do not inherit enemy AI. World markers, projectiles, pickups and doors keep their existing bases.

C++ that derives from PaperZDCharacter or uses PaperZD classes/notifies directly requires the PaperZD module. Exported headers exposing those types use PublicDependencyModuleNames, as the plugin guide specifies. Declare Paper2D for direct Paper2D use too. Include PaperZDCharacter.h, PaperZDAnimInstance.h or the specific installed plugin header as needed; do not fabricate Epic API pages for these third-party classes. See native module guidance.

Author native animation assets

Phase 1 creates AS_Player (native Flipbook Animation Source), five locomotion ASQ_Player_*Test sequences, and ABP_Player (PaperZD Animation Blueprint; runtime UPaperZDAnimInstance). Create sequences through their source editor and assign the registered FB_Player_*Test clips. Wire the state machine to Output Animation and set the player’s AnimInstanceClass. Save all source/sequence/Blueprint packages.

Phase 2 adds Attack, Hit and Death sequences. They initially reuse FB_Player_LandTest as visibly labeled placeholder art; debug state identifies their intent. Distinct sequences support distinct notifies and clothing mapping even while art is shared. This proves wiring, not attack readability or finished art. Configure looping on the PaperZD Play Sequence nodes; do not let the body’s raw flipbook loop independently. Phase 5 adds AS_EnemyTest, its five native sequences and ABP_EnemyTest, with explicit reused development art for both enemy fixtures. Every new asset has a full contract and placement page.

Player state machine

StateObserved facts / transitionsPlayback and exit
IdleConfirmed grounded support and negligible horizontal speed; no higher-priority action.Loop; Move on speed, Rise/Fall on native airborne facts.
Move / RunGrounded horizontal movement. One Move node covers the committed run visual.Loop; no separate sprint mechanic or animation-imposed turn lock.
RiseNative airborne mode and positive Z velocity after the scheduled launch is observed.Loop until velocity changes; near-zero airborne velocity goes to Fall. No dedicated Apex state required.
FallAirborne and nonpositive Z velocity, including walk-off.Loop; confirmed landing can request Land cosmetics.
LandBody-reported landing observation; Walking confirmation is still required for jump budget rearm.Short non-looping transitional presentation. New accepted jump/attack, Hit or Death interrupts immediately; finish/time-remaining may choose Idle/Move cosmetically.
AttackCurrent accepted Combat execution, or the existing Ability presentation fallback.Non-looping; fit play rate to the owner’s duration where useful. Remain visually appropriate if the clip ends early; gameplay ends/cancels independently.
HitAccepted damage and gameplay Hitstun facts, subject to lethal priority.Non-looping; exit when the gameplay owner resolves Hitstun, never on a required animation unlock.
DeathHealth has already established death and ActionState has become Dead.Non-looping terminal pose while the body exists. Rewards/recovery/cleanup cannot require its completion.

Priority is Death → Hit → accepted Attack/Ability presentation → locomotion. A presentation cache contains read-only velocity, support, facing, action, execution identity and progress; it is not another gameplay state owner or a project animation enum. Keep animation updates safe when the owning Actor is absent in preview or components are not ready. Resolve/bind on PaperZD OnInit, pull facts on update, and unbind on body/AnimInstance replacement.

PaperZD Jump Nodes can simplify urgent Hit/Death routing without wiring every pair of states. Transitional states can simplify Land→Idle/Move flow. These are animation graph tools: a Jump Node does not execute a gameplay jump. No dash, double jump, wall/ledge traversal, slide or roll nodes are introduced. The Ability action uses the Attack presentation branch until an explicit cosmetic requirement changes it; no new gameplay ability is implied.

Gameplay timing and interruption

Combat retains its authoritative Windup/Active/Recovery elapsed clock, interval-crossing hit queries, per-target deduplication and matching execution token. Ranged active entry releases one projectile using its existing guarded route. ActionState alone governs permissions and cancellation; Health establishes lethal state once. Movement owns jump budget/buffer/coyote/cut policy; abilities own costs/recharge. Animation reads these facts, never grants success or releases their locks.

Gameplay deadlines and explicit cancel/death/travel/EndPlay cleanup must finish even if the AnimBP is missing, notifies are skipped, playback is paused or interrupted, or a late callback arrives from an old body. Validate action token plus body/session identity for requests that cross a callback boundary. Presentation can finish early or hold a pose; it cannot extend a gameplay lock. Do not duplicate Combat timers inside the graph or drive CharacterMovement from a pose.

PaperZD notifies and notify states

Prefer PaperZD sequence notifies for footsteps, sound, effects, attack presentation beats, cosmetic equipment events and presentation completion callbacks. Use notify states for bounded cosmetic trails/effect intervals; explicitly remove cosmetics on interruption/state exit and teardown too. Use built-in notifies or source-defined events first; author a custom Blueprint/C++ notify only for actual reusable behavior. An editor preview can have a null owning AnimInstance.

A projectile release notify may send a timed request when appropriate, but Combat validates the live execution, eligibility window and once-only release guard. The committed slice retains release at authoritative active entry; the notify can synchronize sound/muzzle flash. If a later timing request is authored, Combat must still process the active-entry/deadline route when the notify is absent, deduplicate both requests, and reject a canceled/stale request. Damage correctness cannot depend on the notify. A notify never becomes the sole end-of-hitstun, end-of-attack or movement-unlock path.

Equipment and layered visuals

Equipped clothing/armor must visibly change the character. Profile keeps its one owned-entry inventory and Head/Body slot map. Item Appearance references BPDA_EquipmentAppearance: a read-only map from source-owned PaperZD sequence to compatible layer flipbook plus a layout label. It stores no state transitions or clock.

Profile equipped EntryId → item.Appearance → resolved wearable mapping
Gameplay facts → PaperZD graph → body sequence + rendered time/facing
                             → BPC_EquipmentVisuals → HeadLayer / BodyLayer

BPC_EquipmentVisuals is the small remaining project adapter. The player supplies EquipmentRoot, HeadLayer and BodyLayer. The adapter stops autonomous layer playback, resolves the current sequence’s wearable clip, changes only the layer asset when needed, then copies the body’s rendered playback time with events disabled and matching facing/mirroring. It never changes or seeks the body Sprite, selects a state, or accumulates a clock.

In the referenced PaperZD source, AnimInstance OnTick runs after animation processing. ABP_Player uses that observation point to obtain GetPlayer().GetCurrentAnimSequence() and the body Sprite’s GetPlaybackPosition(), then call the adapter. An equip refresh synchronizes to the last rendered pose immediately; the next post-animation update applies the new pose in the same frame. Verify ordering in the installed version. Keep autonomous adapter Tick off; do not synchronize only on sequence-change events, which miss time changes/restarts inside one sequence.

Validate pivots, scale, individual frame durations, frame counts, mirroring and intentional Y-depth/sort order in both directions. Missing, unloaded or incompatible wearable mappings hide the layer. A matching FrameLayoutId is only a diagnostic label. DA_Equipment_TestHelmet maps Idle/Move/Rise/Fall to the static helmet fixture while those body clips are aligned static placeholders; Land/Attack/Hit/Death hide. This is not proof of a full animated wardrobe.

PaperZD’s published source also contains composite-layer/skin APIs. Their availability and equipment coverage depend on the installed release and authored data; this manual does not assume they automatically implement the Profile slot system or wardrobe rendering. If verified native layer support replaces manual copying cleanly, keep the same appearance/ownership contract, document that version and remove the replaced synchronization path. Never let both paths write a layer.

Acceptance and references

  • Compile source, sequences and AnimBP; exercise every committed state and missing-asset diagnostics.
  • Accept a new jump/attack during Land. Interrupt Attack→Hit→Death and deliver a stale callback; no lock or extra hit survives.
  • Remove notifies/disable animation and prove damage, projectile release, rewards, movement and ability recharge still work.
  • Equip/unequip during every state, pause and reverse facing at 30/60/120 FPS; no drift, one-frame lag, duplicate notify or clothing collision.
  • Travel, death recovery, disk load and repeated possession rebuild visuals from current owners without saving animation frames or retaining old bodies.
  • Run a packaged slice with the actual plugin and all referenced development fixtures included.
