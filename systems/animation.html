How to use this chapter

Follow the linked phase in order, then open individual asset pages for exact parents, folders, fields, functions and tests. Narrative recipes are suggested implementation details around the preserved architectural ownership rules.

Use Paper2D assets as presentation inputs

Import a simple image you own as T_TestPlayer. Create SPR_TestPlayer from it, then create the five named test flipbooks in Animation. One static placeholder frame can populate each initial clip while debug text shows the selected state. No artwork or compiled flipbook is supplied by this documentation package; these pages tell you how to create the registered assets in your project.

Create BPDA_AnimationSet from PrimaryDataAsset, compile it, then create DA_Anim_PlayerTest as a Data Asset instance of that schema. Map Idle/Move/Rise/Fall/Land to their exact registered flipbooks. E_AnimState also includes Apex, Attack, Hit and Death; define deliberate fallback presentation for missing test clips rather than silently adding unregistered flipbook assets or new gameplay mechanics.

Drive a visual clock, not gameplay

  1. Pass the inherited Sprite component and resolved set into BPC_FlipbookAnimator.InitializeVisuals. This is an Actor Component, not an Animation Blueprint/AnimInstance.
  2. Build S_AnimationSnapshot on the body from native velocity/support, facing and ActionState/Combat timing.
  3. Select presentation priority: Death first, then Hit, then active attack/ability presentation, then locomotion. A Land request must be interruptible immediately by accepted gameplay.
  4. Only switch a component’s assigned flipbook when its desired asset changes. Seek playback from one common clock; do not continually reset the asset and accidentally restart at frame zero.

The source E_AnimState has no separate Ability value. This guide preserves it. An explicit suggested initial fallback is to display an ability through the existing Attack action-presentation slot, driven by ability timing, until an approved dedicated cosmetic state is added. That is not permission to add a traversal ability because an animation might support one.

Clothing uses the same pose time

In Phase 7 add EquipmentRoot, HeadLayer and BodyLayer inside the existing player Blueprint. They are native component instances, not new custom class assets or folders. Keep their collision disabled. An item’s Appearance reference resolves to an animation-set instance; the animator receives the resolved set rather than checking whether ItemId equals a particular helmet.

Current gameplay facts → selected cosmetic state
Shared clock / authoritative action progress
  ├─ body Sprite: selected clip, shared time/frame
  ├─ HeadLayer: matching clip, shared time/frame
  └─ BodyLayer: matching clip, shared time/frame

Stop autonomous playback on manually driven layers. A mid-run equipment change should immediately display the same phase as the body, not start a fresh independent clip. Matching FrameLayoutId is a useful diagnostic label, but you must also check pivots, image scale, frame count, frame durations and facing convention.

Use a deliberate Y-depth or sorting policy and test it facing both directions. Missing equipment action/death clips should hide or use a compatible intentional fallback, never show a mismatched run cycle over a dead body. The single FB_Helmet_Test can prove a static aligned overlay; it is not proof that a full multi-frame wardrobe has been authored.

Test independence before polishing art

Disable the animator and confirm that damage, jump budget, cooldown and purchases still work. Then change equipment during Move, Rise, Fall, Attack, Hit and Death presentation and confirm clock alignment/collision independence. A cosmetic completion event can hide a visual, but it cannot decide whether an attack hit, an ability succeeded or a player died.

Canonical roadmap reference · PART K — Animation architecture

Preserved source text, with local cross-links added for this expanded chapter. E-number references belong to the original roadmap; see verification notes.

Use Paper2D flipbooks for the baseline. BPC_FlipbookAnimator is a Blueprint Actor Component derived from ActorComponent, not an Animation Blueprint derived from AnimInstance. BPDA_AnimationSet is a Blueprint Class derived from PrimaryDataAsset. Its content instances map E_AnimState values to Paper2D Flipbook assets (PaperFlipbook). Sprites are Paper2D Sprite assets (PaperSprite) created from imported Texture2D content; none of those content assets requires choosing a Blueprint parent.

The animator receives S_AnimationSnapshot values and action events. Presentation priority is Death, Hit, active Attack/Ability presentation, then locomotion. A normal locomotion update must not overwrite a death or hit clip. Conversely, a landing clip must be interruptible by a newly accepted jump or attack.

Keep gameplay time authoritative. Combat selects its definition, starts windup, applies hits during the active interval, and ends recovery whether or not a visual clip exists. The animator plays a compatible clip using the same action timing. A flipbook-completion event may report cosmetic completion; it must not grant damage, complete a purchase, or decide whether the character is alive. PaperFlipbookComponent exposes playback-position controls and non-looping completion events in Blueprints. [E9]

Layered visible equipment

The player already has the inherited Paper2D Sprite. Add native PaperFlipbookComponent instances named HeadLayer and BodyLayer, with a native SceneComponent named EquipmentRoot for visual placement. These are component instances inside BP_PlayerCharacter (PaperCharacter → Character), not additional custom Blueprint classes.

An equipped item's BPDA_ItemDefinition (PrimaryDataAsset) references an appearance instance of BPDA_AnimationSet (PrimaryDataAsset). The animator receives the resolved set. It never checks ItemId == SomeHelmet in a graph.

Use one animation clock and one selected state for body and clothing. The animator can stop autonomous playback on the layered components and explicitly set each layer's playback frame/position from that shared clock. Do not expect independently playing flipbooks to remain synchronized after mid-animation equipment changes. [E9]

Author compatible layers with the same pivots, scale, frame timing, facing convention, and frame count for a shared state. Use small Y-depth offsets or an intentional material/sort policy; verify the order when facing both directions. All visual layers have collision disabled. A missing equipment clip should hide/fallback deliberately, not reuse a mismatched run cycle during a death animation.

Test equipping during movement, jumping, attacking, hitstun, and death; test loading with equipment already owned; test low frame rates. Make layer-layout validation part of content checks.

PaperZD decision

PaperZD offers an animation-graph workflow for 2D animated characters. That can reduce authoring friction as an animation catalog grows. It is not necessary for this baseline: the built-in alternative is the explicit flipbook coordinator above. The plugin's own listing also calls out packaging/toolchain considerations. This guide does not assume a verified 5.8.3-compatible PaperZD installation and introduces no PaperZD-dependent class. Re-evaluate it only after the built-in animation slice reveals a concrete authoring problem. [E16]
