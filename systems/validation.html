How to use this chapter

Follow the linked phase in order, then open individual asset pages for exact parents, folders, fields, functions and tests. Narrative recipes are suggested implementation details around the preserved architectural ownership rules.

Two different kinds of validation

The audit page in this documentation checks files, coverage, links and local browser behavior. It does not prove a Blueprint compiles or a game packages. In your project, BP_ArchitectureTestHarness and L_SystemTests exercise public gameplay APIs and inspect results. Keep these proof categories separate in your own notes.

Use deterministic fixture setup

Write down initial XP, inventory, world records, checkpoint, enemy state and active ability/effect state before a scenario. Then issue the same public commands gameplay uses and compare typed results. Do not edit protected arrays halfway through a test to make an assertion pass. When asynchronous saving/travel is involved, continue from the actual completion/readiness event, not a guessed fixed Delay.

Cross-map proof is not one Get All Actors query

Load each authored map in a controlled validation session, report its PersistentIds and SpawnIds, and combine the manifests. Initially, copying the per-map diagnostic output into one reviewable report is an acceptable explicit manual step. Later, the existing GI can hold development-only manifest values between map loads if needed; do not retain harness Actor references from unloaded worlds or add a production manifest manager simply for organization.

Package the slice before growing content

Set a Game Default Map, choose a Development packaging configuration for diagnostic tests, include the actual slice maps and all referenced definitions/presentation/executor content, then package to a separate output directory. Run the executable from a clean test user-data state and repeat the full acceptance run. Check Output Log/packaging results rather than treating successful PIE as proof that soft references cooked correctly.

The current catalog and player test appearance intentionally reference Tests assets. Do not blanket-exclude the Tests folder while trying to package the development slice. Before a final production cook, author approved replacement content in its canonical folders, update references and only then remove development dependencies from the shipped cook. Do not move existing registered fixtures out of their assigned folders to hide the dependency.

Regression gates

After movement, prove single jump and frame-rate behavior. After persistence, prove reward coherence and death without rollback. After equipment/passives, prove rebuild values do not grow with repeated refresh. After abilities/effects, prove cancellation and handoff. Before scaling world content, prove IDs, save generations and fresh packaged loading with actionable failures.

Record actual expected/observed values, build identifier, schema/content version and test date. A checkbox means you ran the test, not that the documentation author compiled your game. Optimize only measured bottlenecks; validation is not a reason to start a speculative streaming/native rewrite.

Canonical roadmap reference · PART AH — Refactor checkpoints

Preserved source text, with local cross-links added for this expanded chapter. E-number references belong to the original roadmap; see verification notes.

Gate 1: after movement, before combat

Inspect BP_PlayerCharacter (PaperCharacter → Character), BPC_ActionState (ActorComponent), and BPC_FlipbookAnimator (ActorComponent). Confirm that native floor/velocity state is not duplicated by contradictory visual booleans, jump execution has one path, and landing presentation cannot block a buffered jump. Stop feature work until the same tests pass at the selected frame-rate targets.

No new Blueprint is required. Move misplaced animation selection into the existing animator and action permission rules into the existing action component. Keep the movement policy in the Character rather than extracting an unnecessary movement manager.

Gate 2: after the persistence slice, before inventory breadth

Inspect BP_GameInstance (GameInstance), BP_PlayerProfile (Object), BP_WorldState (Object), and BP_SaveGame (SaveGame). Kill the player after progress made beyond checkpoint activation; travel away and return; exit and load. Search for direct writes to SaveGame and runtime Actor references in snapshot structs.

A transaction must not publish partially updated models. A failed save must not clear dirty state. Repeated calls to a persistent pickup must grant once. Resolve these errors before authoring dozens of persistent objects.

Gate 3: after equipment and passive skills

Inspect BPC_Stats (ActorComponent), the Profile model, and BPC_FlipbookAnimator (ActorComponent). Equip/unequip and buy/load repeatedly; final values must not creep upward, old equipment visuals must not remain attached, and skill points must not be awarded again by loading.

Check that inventory is the only owner of entry instances and equipment stores references to those entries. Check that the skill widget's availability matches the Profile query without recreating the rules in widget graphs.

Gate 4: after active abilities and effects

Inspect BPC_Abilities (ActorComponent), BPC_StatusEffects (ActorComponent), BP_AbilityBase (Actor), and action-token handling. Interrupt an ability in every phase, destroy its target, die, pause, and change areas. Watch for lingering executors, duplicated timers, charges incorrectly restored, and callbacks clearing a newer action lock.

Do not add another layer of managers to cover cancellation bugs. Make Start, Cancel, Finish, and teardown idempotent and keep cooldown authority in the abilities component.

Gate 5: before scaling world content

Audit all placed persistent IDs, area/spawn targets, definition IDs, cook references, and source-control naming. Exercise missing/corrupt/older save generations with BP_ArchitectureTestHarness (Actor) in L_SystemTests, a Level asset (World) with no Blueprint parent.

Measure whether area load times or memory actually justify streaming. The default remains area-map travel. Introduce a different loading strategy only with measured need and a plan to preserve initialization, recovery, and state-application contracts. Do not begin a speculative streaming or native-code rewrite as a substitute for finishing the representative slice.
