How to use this chapter

Follow the linked phase in order, then open individual asset pages for exact parents, folders, fields, functions and tests. Narrative recipes are suggested implementation details around the preserved architectural ownership rules.

Calculate a complete build, then replace the cache

BaseStats describes the starting body. CumulativeLevelGrowth describes total growth at the current level. Equipment, passives and active effects contribute modifiers. BPC_Stats consumes all those inputs and returns one final block. None of those sources should increment an already-final value and then try to undo it later.

For each E_StatId:
  FlatValue = Base + CumulativeLevelGrowth + sum(all current flat modifiers)
  Final = ClampForStat(FlatValue * (1 + sum(all additive percentage fractions)))

The percentage 0.10 means ten percent, not ten times the stat. With Base=10, growth=2, flat additions=3 and percentage sum=0.10, the result is 16.5. Rebuilding the same inputs a hundred times must still give 16.5. The initial test stat vocabulary is MaxHealth, AttackPower and Defense; it is not a promise that the final game has only those stats.

The body assembles; Profile owns

  1. Initialize the authored character/enemy definition reference. Before progression exists, growth is a zero block.
  2. For the player, query Profile.GetBuildInputs to resolve current level, equipped entry definitions and purchased passive definitions.
  3. Ask StatusEffects for its current modifiers only once after Phase 9. Profile should not find or inspect that live component.
  4. Assign stable runtime SourceIds such as Equipment:EntryId, Skill:SkillId and Effect:Handle for diagnostics.
  5. Pass the complete arrays to Recalculate. Replace the old cache and publish one OnStatsChanged after all fields are consistent.

Source IDs help you explain a number and detect duplicate contributions. They do not imply that a general modifier-manager framework is required. The source’s RebuildStats name is treated as an alias/wrapper to Recalculate; both must not maintain competing caches.

Maximum and current health are different

Stats owns MaxHealth. Health owns CurrentHealth. After a maximum decrease, Health clamps current health downward. A maximum increase does not heal. This avoids an equip/unequip loop that generates health for free. Clean recovery explicitly fills health after the current build is rebuilt; normal travel restores the captured current amount after effects and final capacity are known.

Do not save FinalStats as permanent base values, and do not let item definitions mutate Profile simply because Stats read them. Changing a chosen skill or item affects the next rebuild through its source definition; loading reconstructs the result without adding its bonus again.

Diagnostic display and stopping point

Print the base, growth, each named source, total flat/percentage contributions and final clamp result. Test repeated equip, repeated build notifications, buff refresh/expiry and save/load. The system is ready when identical inputs always produce identical outputs and removed sources leave no residue.

Canonical roadmap reference · PART P — Stats architecture

Current guidance retains gameplay policy and incorporates the PaperZD architecture decision. Historical source text remains in the unchanged original roadmap. E-number references belong to the original roadmap; see verification notes.

BPC_Stats is a Blueprint Actor Component derived from ActorComponent. It owns the final calculated cache for the current body. Base player values come from a BPDA_CharacterDefinition (PrimaryDataAsset) instance; enemy values come from BPDA_EnemyDefinition (PrimaryDataAsset) instances. S_StatBlock and S_StatModifier are Blueprint Structures, no parent. E_StatId is a Blueprint Enumeration, no parent.

For each stat, use this deliberately simple evaluation policy:

FlatValue = Base
          + CumulativeLevelGrowth
          + sum(EquipmentFlat)
          + sum(PassiveSkillFlat)
          + sum(TemporaryEffectFlat)

FinalValue = ClampForStat(
    FlatValue * (1 + sum(AllAdditivePercentageModifiers))
)

With no percentage modifiers, this is exactly the additive model in the brief. Define percentage ordering once; do not let each item decide its own formula. Initially MaxHealth, AttackPower, and Defense are enough to prove the architecture. They are implementation examples, not a final stat catalog. Do not automatically scale platforming movement parameters with RPG level.

The player body supplies a complete build snapshot assembled from Profile + definitions and temporary effects. Recalculate on spawn, level change, equipment change, skill purchase, and effect application/expiration. Do not recalculate on every Tick. Every source has an ID such as Equipment:<EntryId> or Effect:<Handle> for debugging; replacing a source cannot add its bonuses twice.

Maximum health belongs to Stats. Current health belongs to Health. Health queries the authoritative current maximum through its initialized Stats reference. On max-health changes, use CurrentHealth = Min(CurrentHealth, NewMaxHealth) as the initial policy. Increasing max health does not silently heal the player, and equipping/unequipping cannot become a free-heal loop.

Profile never reads Stats to decide what it owns. Stats never modifies the inventory or buys skills. The composition root on the player assembles inputs, which avoids a circular dependency between equipment, skills, buffs, and stat calculation.
