Build the first working controller

The capsule is the physical player. The flipbook is its picture. The Character Movement component moves the capsule, finds floors and integrates velocity. Your Blueprint supplies horizontal intent and one deliberate jump policy. Keeping those jobs separate lets you replace placeholder art without changing the platforming.

  1. Open BP_PlayerCharacter and select inherited CharacterMovement. Enable a plane constraint with normal (0,1,0), so X is horizontal and Z is vertical. Put floor/ledge geometry on that plane with enough Y depth to overlap the capsule. Set unwanted controller/orient-to-movement rotation off.
  2. Add CameraArm and Camera, point the camera along Y, and verify moving toward +X appears toward the intended screen side. Facing flips only the supplied visual components, never the camera arm or physical capsule.
  3. Implement SetMoveIntent(Axis). Clamp/cache MoveAxis. Choose one place to apply Add Movement Input with World Direction (1,0,0) and Scale Value MoveAxis while CanMove is true. Do not apply the same input both in Triggered and again in Tick. Do not multiply this scale by Delta Seconds.
  4. Clear the axis on Completed and Canceled. Test only starting, stopping and reversing direction. Tune native acceleration and braking separately before adding custom turn code.
  5. Add the jump variables from the asset page. Implement RequestJump, ReleaseJump and TryConsumeJumpRequest as small functions. Route IA_Jump Started to a new request; Completed/Canceled to release.

One jump budget, one initial impulse

A buffered press is stored intent. Ground support or coyote permission makes it eligible. The jump budget makes it a single jump rather than an accidental double jump. ActionState adds permission but does not replace either test. “The button was pressed” and “the jump happened” are distinct events.

TryConsumeJumpRequest (custom function)
  if no pending request: return false
  if Now - LastJumpPressedTime > JumpBufferWindow:
      clear request; return false
  if body/action is blocked: return false or clear under interruption policy
  if bLaunchPending OR bJumpConsumedUntilLanding: return false
  GroundAllowed = genuine native walking support AND not launch pending
  CoyoteAllowed = bCoyoteEligible AND within CoyoteWindow
  if neither support permission exists: return false
  clear pending request BEFORE any callbacks
  set bJumpConsumedUntilLanding = true; bCoyoteEligible = false
  set bLaunchPending = true; bJumpCutConsumed = false
  remember whether a released press needs a pending cut
  ExecuteJump → Launch Character((0,0,JumpSpeed), XY=false, Z=true)
  OnJumpCommitted (custom dispatcher, reports acceptance)
  return true

The exact execution graph remains a suggested implementation, not a compiled Blueprint. The engine launch is pending until movement processes it; do not assume the immediately following node will see positive vertical velocity. That is why bLaunchPending exists. The detailed source names MoveAxis and LastJumpPressedTime are used here; the source’s MoveIntent/JumpPressedTime spellings are recorded as aliases in Architecture Notes.

Observe movement; do not invent another physics simulation

Use the native movement-mode change event to distinguish leaving Walking and actually returning to Walking. Maintain LastGroundedTime only while there is genuine support and no pending jump launch. A walk-off may open bCoyoteEligible. A committed jump, knockback, death, teleport or transition closes it. Expiration closes it as well. A Character spawned in the air starts without a made-up recent ground timestamp.

OnLanded is useful for impact information and requesting a cosmetic Land state, but the source’s cited engine behavior is that the movement mode is still Falling during that event. Wait for Walking confirmation before re-arming the jump budget and trying the buffered request. Do not make the Land flipbook finish first. A new valid jump may replace landing presentation immediately.

Suggested implementation detail: centralize support/launch observation in one body update function and use a known post-movement observation point in your installed Editor, rather than letting several Tick/event paths reset the same flags. Check actual native velocity and mode before clearing bLaunchPending. Log a launch generation and its observation if ordering is unclear. Do not “fix” a same-frame problem with Delay(0.1), which changes responsiveness instead of explaining it.

Variable height, including a release before velocity appears

ReleaseJump always sets bJumpHeld=false. For a committed jump that is still rising, one cut retains a fraction of positive Velocity.Z. A Launch Character call with XY Override false and Z Override true applies that reduced Z. It is not another new jump: it does not reset the budget, open coyote permission or emit a second OnJumpCommitted.

ReleaseJump
  bJumpHeld = false
  if a jump request is still buffered: preserve released intent for consumption
  if initial launch has not been observed: bPendingJumpCut = true
  else if Velocity.Z > 0 AND not bJumpCutConsumed:
      request a one-time cut

ApplyPendingJumpCut
  if not pending OR already consumed: return
  if launch is still pending: return, keep the cut request
  if Velocity.Z > 0:
      Launch Character((0,0,Velocity.Z * JumpCutMultiplier), XY=false, Z=true)
      bJumpCutConsumed = true
  clear pending cut when applied or when rise is definitively over

A buffered request pressed and released just before landing must become a short jump. Derive its pending cut from bJumpHeld at consumption; do not discard the release merely because the player was still falling when it happened. Conversely, an early ceiling impact must not cause the pending-cut path to create a fresh upward impulse. Never cut negative falling velocity or repeatedly multiply upward velocity every frame.

A movement debugging session

In L_MovementLab, display MoveAxis, native Velocity, movement mode, LastGroundedTime age, pending request age, bCoyoteEligible, bJumpConsumedUntilLanding, bLaunchPending and bJumpCutConsumed. Record why TryConsumeJumpRequest rejected a press. “False” is less useful than “buffer expired at age 0.18; window 0.10.”

Run taps, holds, ledge walk-offs, knockback departures, short falls, ceiling hits, buffered landings and modal interruption at approximately 30, 60 and 120 FPS. For each failure, first determine whether the request was absent, permission was wrong, the budget was wrong, the impulse was doubled, or presentation was misleading. Do not add a second native Jump path as a fallback. Stop this phase only when the empty course feels good without rewards or combat effects.

Canonical roadmap reference · PART J — Player movement architecture

Current guidance retains gameplay policy and incorporates the PaperZD architecture decision. Historical source text remains in the unchanged original roadmap. E-number references belong to the original roadmap; see verification notes.

J1. Owner and coordinate convention

BP_PlayerCharacter is a Blueprint Class derived from PaperZDCharacter → PaperCharacter → Character. It owns the movement requests, jump buffer, coyote eligibility, facing sign, and movement interruption hooks. Its inherited CharacterMovementComponent remains responsible for movement integration, floor handling, gravity, and collision.

Use world X for horizontal, Z for vertical, and Y for depth. Constrain movement to an XZ plane using normal (0, 1, 0). Use ordinary 3D collision with sensible depth thickness. Keep gameplay collision independent of sprite silhouettes. Position the camera side-on along Y and test its horizontal orientation before authoring rooms.

Do not move the Character each frame with Set Actor Location. Do not let PaperFlipbook frame changes resize the gameplay capsule.

J2. Implement horizontal movement first

Begin with Add Movement Input along world X. Tune MaxWalkSpeed, MaxAcceleration, BrakingDecelerationWalking, friction, and airborne control on the inherited movement component. Disable unwanted orient-to-movement/controller rotation. The player should have an explicit FacingSign of -1 or +1; flip the visual layers, not the camera.

Test starting, stopping, and turning separately. Acceleration and deceleration are not one interchangeable setting. If a turn feels sluggish, adjust the turn/braking policy rather than adding animation delays. Only add a custom braking rule after native settings have been tested.

J3. Use one jump execution path

For this Blueprint-only implementation, use a project function ExecuteJump that calls Unreal's Launch Character node with (0, 0, JumpSpeed), XY Override false, Z Override true. Use that same path for a grounded jump and a legal coyote jump. The node schedules a launch through Character Movement and puts movement into falling. [E7]

This is a deliberate choice: it gives grounded and coyote jumps the same eligibility and variable-height rules without changing native jump-count logic or replacing Character Movement. Do not also bind input to the native Jump function. This implementation owns its one-jump budget explicitly. Native Jump with JumpMaxHoldTime and StopJumping is a valid different approach, but it is not the parallel implementation used here. [E17]

J4. Press, buffer, validate, consume

OnJumpPressed:
    bJumpHeld = true
    LastJumpPressedTime = CurrentGameTime
    bJumpRequestPending = true
    TryConsumeBufferedJump()

TryConsumeBufferedJump:
    require pending request and age <= JumpBufferWindow
    require action state allows jumping
    require not dead / transitioning / in dialogue
    require genuine ground support OR currently valid coyote permission
    require !bJumpConsumedUntilLanding and !bLaunchPending
    consume request BEFORE scheduling the launch
    consume the jump budget; close coyote permission
    set bLaunchPending
    ExecuteJump()
    broadcast your own OnJumpCommitted presentation event

Expiry removes the request. Holding the button does not continuously create requests. A press just before landing can remain buffered; an old press must not cause a jump seconds later.

J5. Coyote time is permission after a walk-off, not an extra jump

While genuinely grounded, maintain LastGroundedTime. When movement changes from Walking to Falling because the player walked off a ledge, open coyote permission only if no jump was committed and no forced launch/interruption caused that departure.

A legal coyote request requires Now - LastGroundedTime <= CoyoteWindow. Consume it when jumping. Close it when it expires, when hit/knockback starts, on death, on teleport/transition, and on any other forced departure.

Do not keep updating grounded time during the frame after a launch was requested while the native movement update still reports the old floor state. The bLaunchPending guard prevents that edge case.

Reset the jump budget only on a genuine landing transition. Do not reset it every frame that a stale Is Moving on Ground query happens to return true. A character spawned in the air must start with no invented recent-ground timestamp.

J6. Variable jump height and the same-frame release edge case

On release, set bJumpHeld = false. If the committed jump is still rising, request a one-time cut to its positive vertical velocity, for example Velocity.Z * JumpCutMultiplier. Apply that with Launch Character, preserving XY and overriding Z. Never apply the cut to negative falling velocity.

Because a launch is applied on a later movement update, a press and release can happen before positive vertical velocity is visible. In that case, retain bPendingJumpCut and apply it after the launch is observed. The same rule handles a buffered press released before landing: the buffered jump should be a short jump, not a maximum-height jump.

Mark the cut consumed so it does not repeat every frame. Do not call both jump-hold force and jump-cut logic.

J7. Rising, apex, falling, and landing

Use native movement/floor state and vertical velocity as the source of truth. Rising and falling can have different configured gravity scales. Treat the apex as a small presentation band around zero vertical velocity, not a third physics mode or a mandatory movement lock.

Use OnLanded for impact information and a landing presentation request. Unreal still reports Falling during OnLanded. Re-arm and consume buffered jumps when the movement-mode change confirms Walking, or at the next controlled movement update after that confirmation. Do not reject a valid buffered jump simply because Is Falling was checked too early inside OnLanded. [E8]

A landing animation must not delay newly valid movement or jumping. A buffered jump can interrupt the landing presentation immediately.

J8. Interruption and animation output

BPC_ActionState (ActorComponent) controls whether jumping/movement/attacking is currently allowed. The Character responds to its changes by clearing buffers or applying movement restrictions. Prefer an explicit capability query such as CanMove, CanJump, CanAttack rather than a collection of unrelated booleans set by several systems.

PaperZD AnimInstance queries native movement, facing and current gameplay action facts. A read-only observation cache is transient; no pushed snapshot or custom body clock is required. Animation cannot decide jump eligibility.

J9. Movement completion tests

Run the same obstacle course at approximately 30, 60, and 120 frames per second, with both short taps and long holds. Include starting/stopping, reversal, small ledges, ceiling hits, ground-to-air transitions, short falls, and room-boundary camera movement.

Specifically verify: a coyote jump once within the window; rejection outside it; no second airborne jump; no coyote jump after knockback; buffering just before landing; buffer expiry; a press-and-release in one frame; release before a buffered landing; no jump from an old request after dialogue; and immediate control after landing.

Completion criterion: the controller is enjoyable with temporary art and no rewards. Do not use leveling, combat spectacle, or camera shake to conceal poor movement.
