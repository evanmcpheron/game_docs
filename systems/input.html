Install mappings on the local player, route through Controller

Create IA_Move as Axis1D and the other planned actions as Boolean. IMC_Player contains gameplay mappings; IMC_UI arrives with the full menus in Phase 10. Use the existing Enhanced Input Local Player Subsystem to add/remove mapping contexts. This project does not create a custom subsystem class.

Suggested initial keyboard bindings are A/D for movement, Space for jump, J for attack, E for interaction, I for inventory, K for skills, Q for the test ability and Escape for pause/cancel. These are development controls, not a final input design. Add the corresponding mappings only when their action asset’s phase arrives. Map left to -1 using a Negate modifier; right is +1.

Intent does not bypass permission

Started on Attack means one request was made. Combat checks definition validity, body health, grounded/airborne eligibility and ActionState permission. A disabled button or hidden widget is not authoritative validation. The same command must still reject an invalid request sent from the development harness.

For jump, do not add a Hold trigger that delays the initial press. Variable height comes from release/cut behavior in the Character, not from postponing the launch until a trigger threshold. Holding a Boolean action with per-frame Triggered must not repeatedly create new jump requests or swings.

Clear stale intent at every blocking boundary

Modal opening, dialogue, death and area travel should explicitly clear cached movement/jump/attack intent. Removing a mapping context alone is not enough. Rebind the new current body after possession rather than letting input closures point at a destroyed Pawn.

Paused menus need a working close/confirm path. Use focused UMG input or configure the relevant Input Action to trigger while paused, according to the actual Editor behavior you test. UI Only input and an expected Controller Enhanced Input callback are not interchangeable assumptions: prove the route you select. No close button should depend on a timer that stopped when you paused the world.

Canonical roadmap reference · PART I — Input architecture

Current guidance retains gameplay policy and incorporates the PaperZD architecture decision. Historical source text remains in the unchanged original roadmap. E-number references belong to the original roadmap; see verification notes.

Use Enhanced Input. Its Input Actions, Mapping Contexts, and Blueprint event bindings cover the confirmed controls without a custom input framework. Apply a context through the existing Enhanced Input Local Player Subsystem; you do not author a new subsystem class. [E5]

BP_PlayerController (PlayerController) owns context installation, screen focus, input mode, and routing. On possession, give it a typed BP_PlayerCharacter (PaperZDCharacter → PaperCharacter → Character) reference. Input should request movement, jumping, attacking, or interacting; the body/components determine whether the action is legal.

For IA_Move, route Triggered to horizontal movement and explicitly clear the cached axis on Completed and Canceled. Map right to +1, left to -1 with a Negate modifier. Do not multiply the input scale by Delta Seconds before Add Movement Input.

For IA_Jump, use Started for a new press and Completed/Canceled for release. Avoid adding a Hold trigger that delays the initial jump. For a single attack per press, use Started, not an unguarded per-frame Triggered event. These event states are part of Enhanced Input. [E5]

When a modal menu, conversation, death, or transition blocks gameplay, clear pending movement/jump/attack intent. Do not rely solely on hiding the widget or removing a context. Test that the control used to close a paused menu can still execute while paused; either handle it through focused UMG input or configure the relevant Input Action to trigger while paused.

Do not add dash, roll, wall-jump, crouch, double-jump, fast-travel, or map-screen actions before their mechanics are approved.
