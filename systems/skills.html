How to use this chapter

Follow the linked phase in order, then open individual asset pages for exact parents, folders, fields, functions and tests. Narrative recipes are suggested implementation details around the preserved architectural ownership rules.

Model the graph before drawing it

Create the schema, enum and three Phase 8 test definitions. TestRoot costs one point; TestBranchA and TestBranchB require TestRoot and share TestBranchChoice as an exclusive group. Their exact costs/modifiers are proposed fixture values, not final specialization design. Definitions author incoming prerequisite edges; derive visual child edges rather than storing two editable graph directions.

GetSkillAvailability(SkillId)
  if already purchased → Purchased
  if definition missing → Locked(reason)
  if any prerequisite absent → Locked(reason)
  if group/explicit exclusion conflicts → Locked(reason)
  if points below Cost → Locked(reason)
  otherwise → Available
TryPurchaseSkill
  re-run same query immediately
  if not Available → fail with no mutation
  stage points - Cost and purchased-ID insertion
  commit both → one skill/build notification → save revision

A disabled purchase button is presentation. The model must reject the same invalid request from an enabled stale widget or a development call. Zero-cost skills are legal only if deliberately authored and validated; they do not make duplicate purchases legal.

Passives and active grants are derived

Rebuild passive modifiers from the purchased set after changes and load. Do not add them into permanent base stats each time a node is drawn. Phase 9 adds TestActive and TestPulse; Profile derives granted ability IDs from purchased definitions, and Abilities holds a runtime cache rather than a second permanent purchase list.

Validate the graph and the world together

Check missing prerequisites, self-edges, cycles, negative costs, invalid grants and inconsistent exclusivity. A cycle can leave nodes permanently unavailable. Grouping a prerequisite with its mutually exclusive child can make that child impossible to buy.

Mandatory progression must remain possible for every valid irreversible specialization. Keep critical capability access common/nonexclusive, guarantee sufficient reachable points, or author an alternative route. These are content constraints to prove, not a reason to silently add respec, double jump or fast travel. The development TestActive grant is nonexclusive to avoid making the test gate depend on choosing one branch.

Only then create tree widgets

WBP_SkillTree lays out definitions and creates WBP_SkillNode children. Each node knows SkillId and asks Profile for current availability/reason; it does not implement a separate prerequisite algorithm. Bind model changes, then pull current state. Test purchases with the widget destroyed and after disk loading; persistent rules must behave identically.

Canonical roadmap reference · PART T — Skill tree

Current guidance retains gameplay policy and incorporates the PaperZD architecture decision. Historical source text remains in the unchanged original roadmap. E-number references belong to the original roadmap; see verification notes.

BPDA_SkillDefinition is a Blueprint Class derived from PrimaryDataAsset. BP_PlayerProfile is a Blueprint Class derived from Object. E_SkillAvailability is a Blueprint Enumeration asset, no parent. WBP_SkillTree and WBP_SkillNode are Widget Blueprints derived from UserWidget.

A skill definition contains SkillId, Cost, PrerequisiteSkillIds, optional ExclusiveGroupId, optional explicit incompatible skill IDs, passive modifiers, granted ability IDs/capability tags, and a UI position. Definitions describe the graph; Profile stores only purchased IDs and unspent points. Derive child edges from prerequisites rather than maintaining two independently editable graph directions.

GetSkillAvailability(SkillId) returns Purchased first, otherwise Locked with a reason when prerequisites/exclusivity/points fail, otherwise Available. TryPurchaseSkill calls the same validation again at commit time, deducts points, and inserts the ID in one synchronous operation. A disabled button is not authoritative validation.

Rebuild passive modifiers from the purchased set. Derive ability unlocks from the purchased definitions; do not persist a second purchased-ability list for the same grants. The test root and mutually exclusive branch definitions in phase 8 prove graph logic, not final specialization design.

Validate missing prerequisite IDs, cycles, negative costs, nonexistent ability grants, and contradictory exclusivity groups. A mandatory route must not depend on an irrevocably excluded specialization. Use common/nonexclusive access, sufficient guaranteed reachable points, or an authored alternative route; test every allowed specialization against required gates. This is a content constraint to validate, not a reason to invent a respec or traversal mechanic.

Warrior-oriented, magic-oriented and mixed resource builds

Reuse BPDA_SkillDefinition.PassiveModifiers and Profile.PurchasedSkillIds. Resource maximums/regeneration can be purchased through normal explicit costs/prerequisites; no fixed class selection exists. Warrior-oriented and magic-oriented describe resource emphasis, while mixed builds combine valid nonexclusive nodes/equipment. Preserve required progression for every valid branch.

Keep TestRoot and TestActive unchanged. TestBranchA retains +2 AttackPower and adds +25 MaxStamina; TestBranchB retains +2 Defense and adds +25 MaxMana. Their cost, root prerequisite and TestBranchChoice exclusion remain unchanged. Test each branch in a reset session; do not buy both exclusive branches to simulate a mixed build. For a mixed-resource proof use BranchA plus an existing development equipment fixture temporarily modified to add +10 MaxMana, retaining its original modifiers; restore the fixture after testing.

At zero test regeneration spend to 20 mana/40 stamina. BranchA produces base maximums 50/100 → 50/125 while currents remain 20/40; with +10 mana equipment maximums become 60/125. Rebuild twice, unequip, revisit and save/load. No duplicate bonuses, no ordinary free refill, removed equipment contribution disappears exactly once. Disk load rebuilds purchased/equipped maximums and deliberately starts full. Repeat separately for BranchB: 75/100. TestActive's nonexclusive capability remains obtainable from either branch.
