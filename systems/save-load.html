Three operations that must not be confused

OperationPersistent modelsRuntime bodyDestination
Normal area travelKeep current Profile and WorldStatePreserve current health, remaining effects and recharge in value handoffAuthored portal target
Death recoveryKeep current Profile and WorldState; never import an older disk snapshotFresh body, full final health and cleared temporary effects/recharge under the source baselineActive checkpoint, otherwise safe starting fallback
Load from diskImport a completely validated supported snapshotFresh clean-recovery body, not exact saved executionValidated recovery snapshot/checkpoint fallback

A checkpoint is a recovery location, not an instruction to roll the character back to the moment of activation. Earn an item after activating the checkpoint, then die. The item must remain in Profile even though the body returns to the earlier location. A crash before an outstanding save completes can still lose recent unsaved progress; that storage boundary is different from an ordinary in-game death.

Build a value-only snapshot

Create the four top-level fields on BP_SaveGame: Header, Character, World and Recovery. The first three structure pages list every nested field and allowed owner. Recovery is derived from active checkpoint/start configuration at capture; it is not a second editable checkpoint model.

  1. Call Create Save Game Object with BP_SaveGame as its class and keep the result in InFlightSnapshot.
  2. Capture PersistentRevision in a local variable and InFlightRevision before beginning I/O. During this synchronous capture no partially completed cross-model transaction may be visible.
  3. Call Profile.ExportSnapshot and WorldState.ExportSnapshot. Assign those returned values to Character and World. Fill Header with supported schema/content versions, next sequence and a diagnostic timestamp.
  4. Resolve the safe Recovery value. Validate the snapshot as a whole. No array may secretly include Actor, component, widget, executor or timer references.
  5. Once the writer starts, leave that SaveGame instance unchanged. Later gameplay changes belong to the live models and a future snapshot.

Keep asynchronous work outside model functions

Use synchronous custom functions for validation, value commits and BuildSnapshot. Wire engine Async Save Game to Slot in a custom Event Graph orchestration path, not in the middle of a Profile mutation. RequestSave can be a small synchronous function that sets flags and calls a custom event such as RunSaveIO. Its return means queued/accepted, never “the file is safely on disk.”

RequestSave
  if conflicting I/O is active:
      bSavePending = true; return
  if PersistentRevision is already saved and no explicit snapshot is needed: return
  Snapshot = BuildSnapshot(PersistentRevision)
  if invalid: show failure; keep dirty; return
  InFlightRevision = captured revision
  InFlightSnapshot = Snapshot
  bSaveInFlight = true; bSavePending = false
  RunSaveIO(Snapshot, older-or-unused physical slot)

Async Save Game to Slot.Completed
  HandleSaveCompleted(Success, captured revision, physical slot)

Do not clear a newer dirty revision when an older write succeeds. Suppose revision 12 starts writing, then revision 13 commits. Successful completion of 12 makes LastSavedRevision=12, not 13. The queue must capture and write a fresh revision-13 snapshot afterward.

HandleSaveCompleted
  if Success:
      LastSavedRevision = captured InFlightRevision
      preserve this slot as last known good generation
      advance accepted sequence bookkeeping
  else:
      keep LastSavedRevision unchanged; keep dirty state
      publish a real failure with Retry / unsaved-progress feedback
  release InFlightSnapshot; bSaveInFlight = false
  if newer changes remain and policy permits another attempt:
      capture a fresh snapshot (never edit the completed one)

Two physical generations, one logical profile

The source uses one logical player slot backed by Profile0_A and Profile0_B. Write to the older/unused generation while preserving the other valid one. On the next write, alternate. The completed snapshot carries an increasing SaveSequence. This provides a useful fallback against one interrupted or invalid generation, not a guarantee against disk failure, both files being corrupted or a crash before any save succeeds.

Use the same UserIndex convention consistently; 0 is a suggested initial single-player test value, not a universal platform-account rule. Keep physical slot selection and sequence tracking on GameInstance. Do not infer the newest valid generation from file timestamp alone.

Load candidates first; replace live state only after validation

  1. Block conflicting gameplay/I/O and settle outstanding writes. Check whether each physical slot genuinely exists. “Missing” and “load failed” are different outcomes.
  2. Load A and B sequentially. Validate returned object/class, supported SchemaVersion and ContentVersion, header sequence and all value invariants. Keep diagnostic reasons for rejected candidates.
  3. Select the highest valid supported SaveSequence. Report a rejected newer generation and an intentional fallback; do not silently erase either file or start a new game.
  4. Apply supported migrations to candidate values, then revalidate quantities, unique EntryIds, equipment ownership, skill references, progression interpretation and area/spawn identity.
  5. Only after the entire candidate is acceptable, import its character/world values while gameplay remains blocked. Recompute derived level/unlocks/stats without replaying acquisition or level-up rewards.
  6. Set DiskLoad entry reason, open the validated recovery area, apply persistent world records, create the new body/build, restore clean recovery health, bind UI and enable input.

Suggested implementation detail: stage candidate value structs or temporary candidate model Objects of the existing classes before replacing the current model references. That allows full validation without half-overwriting a running session. It does not require a new save-manager asset.

Versioning is an explicit promise you must test

SchemaVersion describes serialized layout; ContentVersion describes interpretation of IDs, progression thresholds and authored content. A filename rename is not necessarily a stable-ID rename. Changing a stable item or world ID needs a documented mapping so old progress remains attached to the intended content.

A version integer cannot magically deserialize a broken or incompatible old Blueprint Structure. Keep fixture saves before changing persistent shapes, keep a supported readable representation where required, and prove the actual migration in a packaged build. If the engine cannot deserialize the old candidate far enough to read its header, a function called Migrate does not solve that by itself. Record the limitation rather than claiming universal compatibility.

Never fix an unknown inventory definition by silently substituting another item. Report/quarantine according to a deliberate supported migration policy. Likewise, loading a modified XP curve must not run normal level-up award logic and grant points a second time.

Save-before-travel, retry and quit

The roadmap settles writes before load, new-session replacement, area teardown and final quit. Coordinate these waits with completion events and guarded pending operations. Do not busy-loop on bSaveInFlight in a synchronous graph or wait on a gameplay timer frozen by a paused menu. On failure, provide explicit Retry or an acknowledged continue-with-unsaved-progress decision; otherwise a mandatory “flush” can deadlock travel forever.

The first save-status widget is a view of coordinator state. A “Saved” label must follow a successful completion, not a queued request. Do not clear error feedback solely because the player clicked Retry. Avoid an uncontrolled infinite immediate retry loop on a failing disk.

The required recovery and failure drill

Use the same persistent pickup/checkpoint/shortcut fixture for each run. Collect once, request again, die, revisit, fully exit the executable and relaunch. Inventory quantity and collected record must agree every time. Then change state during an in-flight write, inject a failed completion in a development-only seam, and load with an invalid newer generation. Verify dirty revision retention, valid fallback, no overwritten good generation and no duplicated reward.

Test a complete fresh-process load, not merely Stop/Play with assumptions about Editor state. No game was compiled or packaged while generating this documentation: these are tests you must execute in the installed Editor and target build. Website validation in the audit is separate from game-runtime validation.

SaveGame contents and ownership

Create BP_SaveGame using Blueprint Class → All Classes → SaveGame. It contains value snapshots only. The supporting S_SaveHeader, S_CharacterSave, S_WorldSave, S_CheckpointState, S_WorldObjectRecord, S_RecoveryData, and S_InventoryEntry are Blueprint Structure assets with no parent class.

BP_SaveGame : SaveGame
  Header : S_SaveHeader
    SchemaVersion, ContentVersion, SaveSequence, SavedAt
  Character : S_CharacterSave
    TotalXP, CachedLevel, UnspentSkillPoints
    PurchasedSkillIds
    InventoryEntries
    EquippedEntryIdsBySlot
  World : S_WorldSave
    ObjectRecords
    DiscoveredRoomIds, DiscoveredAreaIds
    WorldFlags
    ActiveCheckpoint
  Recovery : S_RecoveryData
    AreaId, SpawnId

Ability unlocks are reconstructed from purchased skills; they are not saved twice. Base stats come from versioned definitions; derived stats are not stored as permanent truth. Recovery is a snapshot derived from the active checkpoint or start fallback, not an independently mutable second checkpoint system.

Do not save current attack frames, animation state, jump buffers, current AI execution, dialogue cursor, Actor references, component references, temporary projectiles, or a precise airborne transform. The player's current health/mana/stamina/effects/cooldowns are runtime state under the selected recovery policy, not a promise to restore the exact instant.

The live model is not the save object

GameInstance constructs Profile and WorldState through Construct Object from Class, sets their Outer to GameInstance, and also stores explicit object-reference variables to keep them referenced. Initialize them through your own synchronous methods; plain Objects do not get an Actor's automatic BeginPlay lifecycle. [E3]

To save, GameInstance uses Create Save Game Object, copies model values into a fresh snapshot, and calls Async Save Game to Slot. The engine supplies the serialization/I/O mechanism; your graphs supply the state selection and reconstruction. The async completion has a success result that must be checked. [E10, E11]

Transaction rule

For a one-time pickup or unique encounter:

validate source record is not already committed
validate all item/XP grants and destination state changes
enter a non-reentrant, non-latent transaction
commit Profile values + WorldState values
increment one session PersistentRevision
broadcast notifications from the complete new state; reject reentrant mutations
exit transaction
request save

No dispatcher, latent node, asset load, animation wait, or disk write belongs between those commits. Prepare required definitions before entering. A failed validation changes neither inventory nor world state. Guard against nested mutation requested by an event listener while another transaction is committing.

Default save strategy

Use one logical player slot backed by two alternating physical generations, for example Profile0_A and Profile0_B. Each successful generation has an increasing SaveSequence. Write the next snapshot into the older/unused generation; leave the other generation untouched. This is a straightforward fallback against an interrupted or invalid latest write, not a guarantee against every storage failure.

Request saving after meaningful persistent transactions: item/reward acquisition, consumption, equipment/skill changes, checkpoints, shortcut completion, unique encounters, and discovery changes. Coalesce requests while an earlier write is active. Do not save on Tick or on every health change.

Maintain PersistentRevision, LastSavedRevision, bSaveInFlight, InFlightSnapshot, and a pending-save flag. Capture a fresh immutable snapshot for a revision and keep it referenced until completion. If newer changes happened while it was writing, immediately schedule another snapshot afterward. Never clear all dirty state merely because an older revision finished.

Allow only one save/load operation at a time for this logical slot. Settle writes before loading, switching profiles/new-game state, area teardown, or final quit; the Blueprint async node warns that simultaneous loading and saving is not supported on every platform. [E11]

On failure, retain dirty state, keep the last valid generation, and expose Retry/continue-with-unsaved-progress feedback. Do not show a saved confirmation merely because a request was queued. A crash before a new snapshot completes can still lose changes since the last successful snapshot; ordinary in-game death does not.

Loading order

Load candidate generations sequentially, validate class/version/content, and select the highest valid SaveSequence. A missing slot means New Game only when it is genuinely absent. A corrupt or unsupported newer save should be reported and must not silently overwrite the old files.

Import values into the session models while gameplay is blocked. Run version migrations, validate item/skill IDs, quantities, slot references, checkpoint/map destinations, and stat/progression consistency. Preserve diagnostic information about removed content rather than silently turning it into a different item.

Resolve recovery, open the target map, apply persistent world records, reconstruct the player build/unlocks/appearance, restore clean recovery health, mana and stamina, bind UI, and then enable gameplay. There is no requirement to reproduce exact enemy positions or conversations.

Changing Blueprint Structure definitions can affect saved compatibility. Stabilize the schema early, use explicit versions and fixture saves, and test migration in a packaged executable before distributing updates. Save flags on variables are not a substitute for this explicit snapshot and restore flow.

Runtime pool travel versus clean disk recovery

Phase 3 runtime travel, not disk persistence: extend S_RuntimeTravelState with CurrentMana: Float and CurrentStamina: Float, beside CurrentHealth. Both are finite nonnegative absolute values copied from Resources.GetResourceSnapshot after suspension. Do not add Profile, Actor, component, widget, timer, dispatcher or executor references. Phase 9 ActiveEffects/AbilityStates members stay absent until their types exist.

  1. In BP_GameInstance.PrepareTravelHandoff close source-body readiness/input, stop active movement/attacks/abilities and call Resources.SuspendResources before capturing any current pools. Preserve the current Profile and WorldState objects/values. The suspension barrier discards an unfinished regeneration interval; no regeneration or spending may occur after capture.
  2. Capture CurrentHealth and the coherent mana/stamina snapshot into a local S_RuntimeTravelState. Reject invalid/nonfinite captured values or missing required initialized components; do not substitute a fresh refill for a failed normal-travel capture. Retain only supported value data in GameInstance's existing handoff, then unbind views and tear down the source body. If travel aborts before destruction, explicitly resume only the same valid living body with a new regeneration clock origin.
  3. Use the existing registered-area/bootstrap path to create exactly one destination body under bBodyReady=false. Reconstruct Stats from the current authored base, cumulative growth, equipment and purchased passives. From Phase 9 import supported effects without replaying immediate effects, then complete the final Stats rebuild before restoring/clamping health and resources. Initialize Resources while suspended using ready Stats.
  4. For NormalTravel only, call Resources.RestoreTravelResources(CurrentMana,CurrentStamina): require a newly initialized, suspended destination; reject negative/nonfinite values; assign the absolute captured amounts clamped to final maximums in one update, never add them to the initial full pools. Restore health through its existing travel path and Phase 9 charge/remaining-duration state through its existing component. Loading time grants no regeneration or recharge catch-up.
  5. Finish dependencies, establish body readiness, bind the new HUD/component observers and immediately pull snapshots, then resume Resources and allow gameplay. No late unconditional Health/Resources initialization may overwrite the restored values. Clean teardown prevents callbacks to the old body.

New game, ordinary death and disk load: create a clean body, rebuild all final stats from retained/imported progression and initialize health, mana and stamina to their final maximums. Death retains current Profile/world progress and checkpoint selection; it must not load an older disk save. Disk S_CharacterSave stores neither current pools nor calculated final stats. This change adds runtime handoff members, not new disk-resource fields. Review versioned definition interpretation and retained fixture-save compatibility before a released schema/content change; do not invent migrations for a release that does not exist.
