Persistent models and stable world identity

Keep facts when Actors disappear; reconstruct Actors without replaying rewards.

How to use this chapter

Follow the linked phase in order, then open individual asset pages for exact parents, folders, fields, functions and tests. Narrative recipes are suggested implementation details around the preserved architectural ownership rules.

An Actor can disappear while its state survives

Imagine opening a shortcut in SliceA, moving to SliceB, then returning. The original BP_Door Actor was destroyed by map travel. The new door instance asks BP_WorldState for the same authored PersistentId and reconstructs its blocker/appearance from the Opened record. The record survives; the Actor does not have to.

The player follows the same separation. BP_PlayerProfile holds lasting ownership and progression. The current BP_PlayerCharacter holds movement requests and runtime components. A new body rebuilds the same chosen equipment/skills from Profile without copying the entire old Actor graph.

Construct the two models explicitly

  1. Create BP_PlayerProfile and BP_WorldState as Blueprint Classes derived from Object using All Classes. Compile them before adding typed references on GameInstance.
  2. In GameInstance’s session initialization, call Construct Object from Class for each. Set Outer to self, assign the result to the matching typed object-reference variable, and call your explicit initializer.
  3. Keep those references for the session. Do not create fresh models in each GameMode BeginPlay. Ordinary death recovery retains the current objects.
  4. Inject model references into consumers through bootstrap or the owning body/controller. Plain Objects do not receive Actor BeginPlay and should not discover the world or own world timers.

The object’s Outer and the stored strong reference are separate concerns in the roadmap’s construction convention. Use both; do not let a temporary local return value be the only connection to the session’s state.

Actor label, runtime object name, array index and spawn order are not durable world IDs. A new Guid generated in BeginPlay or Construction Script changes the identity every reconstruction. A Guid is appropriate for an owned inventory entry only because it is generated at acquisition and subsequently saved as a value. These are not conflicting rules; they describe different lifecycles.

Make restoration boring and repeatable

Actor begins unready
  → GameMode supplies existing WorldState
  → PersistentState validates PersistentId
  → FindObjectRecord(Id) returns value + Found
  → BPI_PersistentActor.ApplyPersistentRecord
  → collision/visibility/availability reconstructed
  → subscribe once to changes for this ID
  → area readiness permits gameplay

ApplyPersistentRecord must be idempotent: applying the same record twice produces the same visible/collision state and no second permanent operation. Collected hides a pickup; it does not call TryAddItem. Completed suppresses a unique enemy; it does not call its legitimate-death reward function. Opened removes a blocker; it does not trigger the switch again.

Store actual facts only in WorldState. The door’s local bOpen is a projection useful for collision/prompt code, not another independent owner. Query the model when refreshing. A missing record selects the authored default without automatically inserting a new record.

Why cross-model changes need one coordinator

A persistent pickup changes both what the player owns and whether a source can be collected again. If inventory changes, then a dispatcher runs, then the world record changes, an observer or save can see a duplicated-reward opportunity. GI must validate and stage both sides first, mutate without any latent work or callback between them, then publish the completed operation.

validate source is unclaimed
validate complete reward and all definition lookups
enter non-reentrant guard
commit staged Profile values with notifications deferred
commit staged WorldState values with notifications deferred
increment one PersistentRevision
publish complete-state domain events (nested writes rejected)
leave guard
RequestSave

GameInstance is coordinating, not becoming the inventory implementation. Profile still validates/stores entries and WorldState still stores records. Internal deferred-commit methods let GI complete both before observation. A standalone Profile operation, such as equip, emits OnProfileCommitted once; GI must not count that again for a cross-model transaction whose notifications it deferred.

Validate the whole authored world

Duplicating a placed persistent Actor copies its ID. Change the new placement’s ID deliberately, then validate uniqueness. A query over Actors in SliceA says nothing about duplicate IDs in unloaded SliceB. Collect per-map ID/spawn/target manifests through a controlled validation pass and compare the combined results. Start with a documented manual log review if necessary; do not label a one-map scan as global proof.

Before scaling content, prove an unloaded switch target, repeated record application, duplicate IDs, missing spawn IDs, re-entry without repeated discovery and a unique encounter whose completion is applied before AI becomes active. Persistent changes must work with every UI widget removed.

Stable-ID policy

Use an instance-editable authored Name on BPC_PersistentState, a Blueprint Actor Component derived from ActorComponent. Example values are Area.Forest01.Room02.Shortcut01 and Area.Forest01.Room02.Pickup01. These are illustrative names, not a commitment to a forest biome.

The ID is a durable content key. Do not derive it from an Actor label, runtime object name, array position, memory address, or spawn order. Do not generate a new Guid in BeginPlay or Construction Script every time the actor is loaded. Do not assume an editor Actor GUID is a suitable Blueprint-accessible packaged-game save ID.

Duplicating a placed persistent Actor also duplicates its variable values. Assign a new ID and validate duplicates. Never automatically repair duplicate IDs during load; that could attach old player progress to the wrong object. An ID rename after release requires a migration/alias, not just a Content Browser rename.

World records

BP_WorldState, a Blueprint Class derived from Object, owns Map<Name, S_WorldObjectRecord>. S_WorldObjectRecord is a Blueprint Structure with no parent, containing a primary StateTag and a small set of named flags when one object needs several remembered facts. Discovered rooms/areas and global narrative flags have their own sets. The active checkpoint has its own typed record.

A missing object record means the authored default. An existing record means the actor must reconstruct that state. Ordinary enemies have no persistent record unless explicitly marked as unique. A runtime Actor's visual state is a projection of the record, not another independent persistent owner.

Initialization sequence

Actor exists but is not gameplay-ready
-> BPC_PersistentState validates stable ID
-> receives BP_WorldState reference from explicit area initialization
-> queries ObjectId
-> calls owner BPI_PersistentActor.ApplyPersistentRecord(record, found)
-> actor updates collision/visibility/availability without granting rewards
-> component binds to changes for its ID
-> area readiness allows gameplay

ApplyPersistentRecord must be idempotent. Applying Collected hides/disables the pickup without adding the item again. Applying Opened updates a door's blocker without re-running a switch interaction. Applying Completed suppresses a unique encounter before its AI/reward path starts.

A switch transaction can update an unloaded door by ID. If the door is loaded, its component observes the model event and applies the new record. If it is not loaded, it will query the record later. No cross-map Actor reference is needed.

Validation must cover all authored maps, not only the current one: duplicate/missing IDs, broken target IDs, missing spawns, invalid checkpoint destinations, and renamed content. In the baseline Blueprint test workflow, load each map in a controlled validation pass and combine its reported ID manifest. Do not claim one Get All Actors query proves uniqueness across unloaded maps.
