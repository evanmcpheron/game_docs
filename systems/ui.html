UI, input modes and observation

Widgets request and observe; destroying one cannot destroy gameplay state.

How to use this chapter

Follow the linked phase in order, then open individual asset pages for exact parents, folders, fields, functions and tests. Narrative recipes are suggested implementation details around the preserved architectural ownership rules.

Create views after their commands work

Every planned WBP_ asset derives from UserWidget. PlayerController creates/owns local screen roots and supplies current typed sources. WBP_SkillTree can create WBP_SkillNode child views while Controller owns the screen lifecycle. No widget is the authoritative inventory, health, skill graph or save object.

Bind, then pull a current snapshot

Open or replace source
  UnbindSources from old model/component
  assign new typed references
  bind each relevant dispatcher once
  RefreshView immediately from current query values
Close / replace pawn / teardown
  unbind exact subscriptions
  clear obsolete Actor/component references
  remove visual widgets without modifying authoritative models

Events that fired before a widget existed cannot be replayed merely by binding later. The initial pull is required. Conversely, constructing the same screen repeatedly without unbinding can make one change redraw several times and retain obsolete world references. Avoid using long-lived model delegates as accidental storage for old screens/Pawns.

Match each view to its source

HUD reads current Health/Stats, Profile progression and the selected interaction prompt. Inventory, Equipment and SkillTree read Profile. Abilities reads the runtime component. SaveStatus reads GI. Dialogue displays Controller conversation state. Pause/MainMenu request coordinator operations. Each page lists the exact event source and permitted request.

Use native text, progress bars, buttons, panels and scroll boxes for the first implementation. A rich UI skin, drag-and-drop inventory, extra loadout screens or new row Blueprint assets are not needed to prove the registered architecture. Do not use Tick-driven binding to recompute the whole inventory/skill tree every frame.

Modal input is a lifecycle operation

Opening a modal screen clears intent, selects the deliberate pause/input-mode policy and sets keyboard/controller focus. Closing restores the previous gameplay route and clears stale input before accepting new requests. Configure or route the close action so it still works while paused. Focus must not remain on a widget removed from the viewport.

Show returned failure reasons instead of implementing a second rule to guess why a command failed. A full-health use, incompatible slot, locked skill or unsupported save is a model/coordinator result. Closing the screen must never make an already-committed operation disappear.

Prove UI independence

Remove the HUD and close every model-backed screen, then run a combat/reward/pickup/death sequence through public commands. Rules and persistence must be identical. Reopen a screen and it should display the current correct state from its first pull, not require another unrelated event to look correct.

Canonical roadmap reference · PART Z — UI architecture

Preserved source text, with local cross-links added for this expanded chapter. E-number references belong to the original roadmap; see verification notes.

All UI assets in this plan are Widget Blueprints derived from UserWidget: WBP_HUD, WBP_SaveStatus, WBP_Inventory, WBP_Equipment, WBP_SkillTree, WBP_SkillNode, WBP_Abilities, WBP_Dialogue, WBP_PauseMenu, and WBP_MainMenu.

BP_PlayerController (PlayerController) creates/removes them and supplies typed references. The HUD observes the current body's Health/Stats and the persistent Profile. Inventory/equipment/skills observe Profile. Save status observes GameInstance. Dialogue displays the Controller's transient conversation session.

Use bind then pull an initial snapshot. On pawn replacement, disconnect from the old body and connect to the new one. Model-backed screens should bind only once per instance and unbind on teardown. Do not use persistent model delegates as accidental strong-reference storage for old world Actors/widgets.

Use change events for discrete state. A cooldown bar may run a local visual interpolation/timer after a notified recharge start; that is different from polling the entire game state every frame. Health/inventory/skills need no Tick-based binding loops.

The widget asks GetSkillAvailability or TryEquip; it does not duplicate their rules. Invalid requests return a reason that can be shown to the player. A hidden or unloaded widget must not stop progression, rewards, saving, or death recovery.

Pause/menu and dialogue entry must set input mode and focus explicitly, and closing must restore them and clear stale gameplay intent. Under this initial single-player dialogue policy, a modal conversation pauses world simulation; it does not create a separate combat mode or quest system. Clear the transient conversation on travel/recovery without granting a completion flag unless the authored completion event actually occurred.
