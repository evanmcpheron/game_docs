How to use this chapter

Follow the linked phase in order, then open individual asset pages for exact parents, folders, fields, functions and tests. Narrative recipes are suggested implementation details around the preserved architectural ownership rules.

An item definition is not an owned item

DA_Item_TestHelmet describes a kind of equipment. An S_InventoryEntry identifies the copy this player owns using EntryId, ItemId and Quantity. A placed pickup has a third identity, PersistentId, describing the world source. Saving an Actor pointer or copying an editable Data Asset into inventory confuses those jobs.

Implement addition as a staged value operation

  1. Resolve every grant ItemId and validate positive quantities before editing InventoryEntries.
  2. Copy the current inventory into a local working array. For each stackable grant, fill compatible partial stacks up to StackLimit, then create enough new entries for the remainder.
  3. Generate a new Guid once per new entry. Equipment uses quantity 1, so two identical helmets receive two different Guids.
  4. Validate the staged result, replace the authoritative array once, then publish the completed operation. Cross-model pickup claims defer that publication until WorldState also commits.

In Blueprint arrays/maps of structures, get a value, edit a local structure, then write it back to the container. Editing a copied struct is not a guaranteed edit of the stored entry. For example, StackLimit=10, existing quantity=8 and grant=5 should produce 10 in the original stack and a new quantity-3 entry, not 13 or a lost remainder.

Removal must respect equipment references

CanRemoveItem verifies EntryId, positive amount and sufficient quantity. The initial rule rejects direct removal of an equipped entry until it is unequipped. TryRemoveItem revalidates and decrements/removes once. Equipment does not hold a second owned item copy that can hide an invalid inventory removal.

Consumable use crosses persistent and runtime state

Phase 6 starts with ImmediateHealAmount on the item definition and the already-existing Health component. Do not wait for Phase 9’s effect framework to prove immediate healing, and do not invent a new consumable manager. Controller supplies EntryId and the current valid body to a suggested GI.TryUseItem coordination function.

Validate Profile owns usable entry with quantity ≥ 1
Resolve definition and validate current live target/benefit
Prepare required effect definitions before entering commit
Enter non-reentrant, non-latent operation
  decrement/remove the Profile entry with notification deferred
  apply the prevalidated Health/effect change with notification deferred
  increment persistent revision once
Publish complete inventory/runtime changes
Leave operation → request save → cosmetic use presentation

Suggested implementation detail: use internal validated mutation helpers in the existing Profile/Health/Effects Blueprints, with explicit deferred notification, so the second half cannot fail after the first half mutates. “Internal” is a calling convention; helpers called from GI need appropriate Blueprint visibility. Private variables still protect the underlying arrays from arbitrary widget edits. Do not use Delay, asset loading or dispatcher callbacks between quantity change and effect commitment.

A suggested first policy rejects a pure healing item at full health, so a rejected use consumes nothing. A timed buff with a valid refresh benefit is a separate Phase 9 case. Revalidate before commit and decide clearly whether a refresh counts as successful use. Never remove an item and then wait for animation to discover that the target is invalid.

Build the screen last

WBP_Inventory reads GetInventoryView, resolves display definitions and stores only a selected EntryId. Build a simple list with native UMG containers/text/buttons before drag-and-drop polish; the planned register does not require another custom inventory-row Blueprint. Source operations must work with the screen closed or destroyed.

Test partial/full stacks, duplicate equipment copies, missing definitions, invalid quantities, removed selections, no live body, full-health rejection and repeated clicks. Then save/relaunch and confirm entry identities and quantities, not just the number of visible rows.

Canonical roadmap reference · PART R — Inventory

Current guidance retains gameplay policy and incorporates the PaperZD architecture decision. Historical source text remains in the unchanged original roadmap. E-number references belong to the original roadmap; see verification notes.

Use BP_PlayerProfile, a Blueprint Class derived from Object, for authoritative inventory operations. BPDA_ItemDefinition is a Blueprint Class derived from PrimaryDataAsset. S_InventoryEntry is a Blueprint Structure, and E_ItemKind is a Blueprint Enumeration; those two have no parent class.

An item definition says what an item is. An entry says what this player owns: {EntryId: Guid, ItemId: Name, Quantity: Integer}. Stackables merge only with compatible entries up to the authored stack limit. Equipment initially uses quantity 1 per entry, so duplicate helmets have different EntryIds and equipment slots can identify the exact owned copy. No durability, random affixes, or rarity framework is required.

Expose TryAddItem, CanRemoveItem, TryRemoveItem, FindEntry, and CanUseItem. Validate IDs and quantities before mutation. Do not remove an equipped entry without also resolving its equipment slot in the same operation; the simplest initial rule is to reject direct removal until it is unequipped.

For consuming an item, validate both ownership and the live effect target. The Controller/body asks the GameInstance transaction facade to coordinate Profile removal and runtime application. The non-latent commit must be designed so that after successful validation it cannot partially fail. Never remove the item, wait for an animation, and only then discover that the effect is invalid.

Persist entries, not pickup Actor references or copied item definitions. WBP_Inventory is a Widget Blueprint derived from UserWidget; it reads entries, resolves display definitions, and requests operations. Profile emits OnInventoryChanged only after a committed change.

Resource build contributions and phase boundary

The existing seven-member S_StatBlock and S_StatModifier contracts include MaxMana, MaxStamina, ManaRegenRate and StaminaRegenRate. Phase 5 cumulative growth rows retain the original health/attack/defense values and append four explicit zero values until a deliberate resource-growth fixture is authored. Phase 6–7 existing item/equipment modifiers can target these stat IDs; no new item category, equipment component or resource-consumable framework is introduced. Phase 8 purchases and Phase 9 temporary effects use the same complete-input calculation.

Profile owns level/equipment/skill decisions, the body assembles effect inputs, Stats owns calculated maximums/rates and Resources owns current amounts. Test additions/removals/repeated rebuilds with zero regeneration to isolate clamping: increasing a maximum preserves current absolute amounts; decreasing it clamps downward; removing a source removes exactly its contribution. Restore provisional fixture overrides after each test. For effects test refresh-without-stacking, expiry, normal travel restoration before clamping and clean recovery without expired/transient sources.
