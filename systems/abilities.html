How to use this chapter

Follow the linked phase in order, then open individual asset pages for exact parents, folders, fields, functions and tests. Narrative recipes are suggested implementation details around the preserved architectural ownership rules.

An unlock is persistent; its current execution is not

Profile derives unlocked IDs from purchased skill definitions. BPC_Abilities owns the body’s available charges, game-time recharge deadlines and active executor references. BP_AbilityBase is one accepted use in the world. Those three lifetimes must not collapse into a single giant ability switch or a saved executor Actor.

Accept only after prerequisites can succeed

  1. Resolve unlocked definition, current body, target validity, charge and ActionState permission. Perform required asset loading before committing gameplay activation.
  2. Acquire an action token, then spawn the already-resolved executor inert. It has no effect in BeginPlay.
  3. If spawning fails, release that same token and return failure without spending a charge.
  4. Once spawning and validation succeed, consume the charge/start recharge, then call StartAbility with the accepted runtime context.
  5. Executor runs the specific operation and eventually calls its guarded FinishAbility. Cancellation clears timers/queries and ends only that token.

The source’s initial policy consumes cooldown on accepted activation even if the ability later misses or is interrupted. Do not silently refund it in an executor child. Start with one charge; additional charges are supported only where a real recharge behavior needs them. Mana/stamina are owned by BPC_Resources from Phase 2; Phase 9 ability costs complement charges and recharge.

Recharge uses game time and catches up safely

Store a deadline for the next charge on the live component. When the current game time reaches it, restore a charge and advance the deadline by the configured interval while still below MaxCharges. A delayed update may restore more than one charge; bound the loop by the missing-charge count. Stop updating full ledgers. RefreshUnlocks must preserve existing recharge for still-unlocked abilities rather than refill them on an equipment event.

Normal travel exports available charges and remaining recharge time, not old world deadlines. Restore relative to the new body’s game clock and freeze loading time out of the handoff. Death/disk recovery uses the source’s clean reset policy. UI may animate a cooldown bar locally, but only the component restores charges.

Use the existing target contracts

TestPulse finds/deduplicates valid nearby Actors. A damageable enemy receives S_DamageSpec through BPI_Damageable. The environmental receiver receives S_AbilityContext through BPI_AbilityTarget and requests a persistent world change through GI. A receiver does not need to be an enemy or ordinary interactable.

S_AbilityContext contains runtime Actor references and must never be nested into a disk snapshot or normal-travel handoff. Revalidate references after delayed execution. Query semantic capability tags through definitions/derived grants, not the name of a test animation. The pulse and receiver remain development fixtures, not final mechanics or lore.

Cancellation proof

Interrupt during every execution stage, remove the target, kill the source, pause, travel and deliver a stale completion callback. Verify one finish notification, no lingering executor/timer, no charge refund beyond policy and no release of a newer action token. A missing executor must fail before charge consumption. Save/load must retain the purchase but reconstruct a clean runtime ability state.

Primary choice: a small Blueprint runtime, not GAS

GAS provides attributes, gameplay effects, ability tasks, and a comprehensive ability execution framework. Epic's documented custom AttributeSet workflow uses native declarations and setup; it should not be presented here as a frictionless, purely Blueprint foundation. For this single-player project, the extra integration does not solve a demonstrated requirement that justifies making it foundational. [E15]

Use BPC_Abilities, a Blueprint Actor Component derived from ActorComponent, and BP_AbilityBase, a Blueprint Class derived from Actor. A per-use executor Actor is a pragmatic Blueprint choice because world traces, timers, and cancellation are straightforward there. It is hidden/non-colliding unless a particular ability needs representation; projectile Actors remain separate.

BPDA_AbilityDefinition is a Blueprint Class derived from PrimaryDataAsset. A definition references the executor subclass, recharge/cooldown settings, scaling/targeting data, and provided capability tags. S_AbilityContext is a Blueprint Structure, no parent, with runtime source/target/context values.

Activation transaction

TryActivate(AbilityId):
  validate unlocked definition, live body, target, charges, and action permission
  acquire an action token
  resolve/load executor class before committing gameplay activation
  spawn executor with no automatic effect in BeginPlay
  if spawning fails: release that token and return failure
  commit charge/cooldown consumption
  call the executor's explicit StartAbility(Context)
  broadcast runtime ability-state change

The executor calls FinishAbility exactly once. Interruption calls CancelAbility, clears timers/hit queries, and ends only its matching token. The component maintains active executor references and destroys canceled executors during death or normal map teardown. Use an activation-generation token so stale callbacks cannot complete a later ability.

The initial policy consumes cooldown once activation is accepted; missing a target or being interrupted afterward does not silently refund it. Treat that as a central configurable rule rather than scattered special cases.

Recharge and ownership

Start with one charge by default. The definition may specify additional charges only where actual recharge behavior needs them; the runtime ledger holds available charges and a next-recharge deadline. Process elapsed intervals correctly, including more than one recharge completion during a delayed update. The approved mana/stamina addition uses BPC_Resources; ability charges and recharge remain independently authoritative in BPC_Abilities.

Use game-time clocks. Pause freezes progression of these timers. Normal area travel exports remaining recharge and charge counts; it does not reset them. Death/disk recovery uses the explicit clean-recovery policy. None of the exact execution, targeting, or timer state is persisted to disk.

For enemy targets, the executor calls BPI_Damageable, a Blueprint Interface asset. For world targets, it calls BPI_AbilityTarget, also a Blueprint Interface asset. BP_Ability_TestPulse is a child Blueprint of BP_AbilityBase → Actor, and BP_AbilityTestReceiver is a Blueprint Class derived from Actor. They prove both routes and remain test-only.

World gates query the current derived capability/unlock set, not an arbitrary animation state or the name of a development ability. UI observes OnAbilityStateChanged; a cooldown progress display can animate from a notified deadline without making widgets authoritative timer owners.

Atomic resource and charge acceptance

Phase 9 only. Inject the owning Character.Resources into BPC_Abilities during ready-body setup alongside its existing ActionState/catalog references; no separate resource manager or ability framework is added. CanActivate(AbilityId: Name, Context: S_AbilityContext) retains Allowed: Boolean and Reason: Text and is read-only: distinguish missing definition, locked, unready/dead body, action/target rejection, no charge, insufficient mana and insufficient stamina. Invalid/nonfinite/negative authored costs reject; zero costs are legal. Cost checks do not replace charges, recharge, target/capability checks or action policy.

  1. Resolve the definition and derived unlock. Validate current live body, context, target/capability, action requirements, charges and Resources.CanAfford. Reject nested activation while bActivationCommitInProgress. Resolve/load the required executor assets before beginning a commit; asynchronous loading belongs outside TryActivate's synchronous acceptance path and requires fresh validation when resumed.
  2. Acquire the existing action token and prepare/spawn the executor inert: BeginPlay must not damage, query targets for effects, spend resources or start playback. Supply owner/context/token using the existing preparation fields. Keep prepared state local until accepted. If preparation fails, destroy/cancel the inert object and release only this request's still-owned token. Resources and charges are unchanged; never undo a newer token that an interruption acquired.
  3. Immediately revalidate body/readiness, definition, target, unlock, charge and affordability, and verify that the token is still current. Stage the accepted remaining-charge count, recharge deadline (start only when required by the existing ledger), and active-executor reference. Run all fallible calculations/validation before resource mutation. On rejection clean up the prepared object and matching token, without resource/charge consumption.
  4. Set bActivationCommitInProgress=true. Use the Phase 9 restricted Resources.BeginDeferredSpend(ManaCost,StaminaCost) rather than ordinary notifying TrySpend. Its shared internal spend implementation revalidates and subtracts both costs atomically without dispatch. On failure clear this guard and clean up; charge state is untouched.
  5. After a successful deferred spend, assign the already validated charge/deadline and accepted executor state synchronously. This is a nonfailing assignment of staged local values, not a second fallible command. No latent operation, external target call, asset load, animation callback or dispatcher may run between resource deduction and these assignments. The action is now accepted; miss, later target loss or interruption does not refund its resource cost or charge.
  6. Publish OnAbilityStateChanged from the complete accepted state while activation and resource commit guards remain closed to reentry. Call Resources.EndDeferredSpend to publish its coherent resource snapshot once if changed and close its deferred interval. Clear bActivationCommitInProgress after both completed-state notifications. Queries in listeners see both committed ledgers; nested mutation fails. Each successful begin has exactly one end, including a zero-cost ability.
  7. Recheck that the accepted body/executor/token remain valid after observers. Start the prepared executor through StartAbility only if still valid; otherwise cancel the accepted execution without refund. Finish/interruption releases only the matching token through the existing owner. Cancellation/death triggered by a completed-state observer must never revive an old body or release a newer action.

Failure tests: for each missing definition, locked ID, invalid target, missing executor, inert-spawn failure, lost token, invalid cost, insufficient one/both resources, and no charge, compare resource snapshot, charge/deadline state and action ownership before/after. Pre-acceptance failure consumes neither pool nor charge and cleans its prepared object. A dual-cost failure must not subtract the affordable side. Bind a listener that calls CanActivate and TryActivate during notification: queries see the accepted state and nested activation rejects. Interrupt after acceptance: no refund, no stale-token release and no orphan executor.

Use DA_Ability_TestPulse initially at ManaCost=10, StaminaCost=0; preserve all original damage/range/capability/charge/recharge values and the nonexclusive TestActive grant. In a separate reset development run temporarily set 0/20 to test stamina-only, then 10/20 for dual-resource atomicity, then restore 10/0. These are controlled fixture variants, not new final abilities or a warrior class.
