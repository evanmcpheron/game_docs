Keep one owned inventory and a slot map

Profile’s EquippedEntryIdsBySlot maps each of Shoes, Belt, Head, Gloves, Top, and Pants to an owned EntryId. The source implementation reference also calls it EquippedEntries; do not create two independent maps. The longer name is used by the ownership matrix and saved snapshot, with the alternate spelling documented in Architecture Notes.

TryEquip(EntryId, Slot)
  find exact owned entry
  resolve item definition
  require a current slot, Kind=Equipment, Quantity=1, definition.EquipmentSlot=Slot
  reject an EntryId already assigned to another slot
  reject blocked/reentrant operation
  replace Slot → EntryId without consuming the item
  commit → OnEquipmentChanged + one OnBuildChanged → revision/save
TryUnequip(Slot)
  clear slot mapping, leave owned entry intact

The current slots are Shoes, Belt, Head, Gloves, Top and Pants. Top is upper-body clothing/armor; Pants is lower-body clothing/armor. Each item declares exactly one compatible slot. Empty slots have no map entry. Equip/replace/unequip changes only the requested slot; the other five remain intact. WBP_Equipment displays all six and sends explicit enum values. Existing Head/Body assets and saves follow the enum compatibility procedure.

Rebuild stats and visuals from the same mapping

The player adapter resolves current equipped definitions, assembles modifiers once and gives resolved wearable mappings to BPC_EquipmentVisuals. It should not maintain another equipment inventory or depend on the Equipment widget to trigger the real rule. Recalculate from complete inputs instead of incrementally adding +Defense every time an equip event fires.

Add EquipmentRoot plus ShoesLayer, BeltLayer, HeadLayer, GlovesLayer, TopLayer, and PantsLayer as native components inside the existing BP_PlayerCharacter in Phase 7. Keep imported T_TestHelmet/SPR_TestHelmet in Art, FB_Helmet_Test in Animation and the two test Data Asset instances in Tests exactly as the source specifies. The folder called Equipment need not contain every piece of equipment-related content; its current registered asset is E_EquipmentSlot.

The body uses PaperZD. The layer contract uses BPDA_EquipmentAppearance and DA_Equipment_TestHelmet; the adapter has no body state selector or clock and never writes the body Sprite. For every refresh, supply the resolved appearance or clear it for each of the six slots so unequip cannot leave a stale layer. Missing wearable pose mappings hide. Native PaperZD layer/skin support is version-dependent and must be verified before replacing this small adapter.

Prove exact ownership and no free healing

With explicitly temporary matching test items, equip all six slots simultaneously; replace/unequip one at a time and round-trip the saved map. Verify the other five entries, layers and contributions remain intact, each current modifier is counted once, and missing art hides only that slot. Acquire two identical helmets. Equip one Guid in Head and verify the other remains a distinct owned copy. Unequip and confirm both still exist. Attempt a slot mismatch and direct removal of the equipped entry; both fail under the baseline rule without altering inventory.

Use a temporary +MaxHealth test modifier in a controlled test copy: equipping increases capacity but not current health, unequipping clamps downward if needed, and repeating cannot refill health. A +Defense helmet should add exactly its current contribution even after many equip/load cycles.

During Move, Rise, Attack and Death presentation, synchronize equipped visuals to PaperZD’s rendered body sequence/time and verify no collision on clothing. A static placeholder helmet is sufficient to prove the data route; full animation-compatible clothing content is a later authoring task, not an extra gameplay system.

Canonical roadmap reference · PART S — Equipment

Current guidance uses the six equipment slots and retains the single Profile-owned inventory, slot-map rules and PaperZD architecture decision. Historical source text remains in the unchanged original roadmap. E-number references belong to the original roadmap; see verification notes.

Keep equipment as a distinct category of BP_PlayerProfile (Object) rather than a second inventory. The authoritative representation is a Map<E_EquipmentSlot, Guid>, where each Guid must resolve to an owned S_InventoryEntry. E_EquipmentSlot is a Blueprint Enumeration asset, and S_InventoryEntry is a Blueprint Structure asset; no parent classes apply.

TryEquip(EntryId, Slot) verifies ownership, item kind, slot compatibility, and current operation permission. It replaces that slot's EntryId without consuming the owned item. TryUnequip(Slot) clears the reference, leaving the item owned. Do not duplicate the item into an equipment-only inventory.

WBP_Equipment (UserWidget) requests equip
-> BP_PlayerProfile (Object) validates and commits slot mapping
-> OnEquipmentChanged for UI
-> OnBuildChanged for the live player adapter
-> BPC_Stats (ActorComponent) recomputes equipment contribution
-> BPC_EquipmentVisuals (ActorComponent) copies the PaperZD-rendered body pose onto compatible clothing
-> GameInstance marks/saves the committed persistent revision

The player's adapter can refresh stats and visual layers in the same synchronous update. Avoid two independent systems each adding the same equipment modifier. On load, prune or quarantine invalid slot references with diagnostics before rebuilding stats; never dereference a missing inventory entry.

Resource build contributions and phase boundary

The existing seven-member S_StatBlock and S_StatModifier contracts include MaxMana, MaxStamina, ManaRegenRate and StaminaRegenRate. Phase 5 cumulative growth rows retain the original health/attack/defense values and append four explicit zero values until a deliberate resource-growth fixture is authored. Phase 6–7 existing item/equipment modifiers can target these stat IDs; no new item category, equipment component or resource-consumable framework is introduced. Phase 8 purchases and Phase 9 temporary effects use the same complete-input calculation.

Profile owns level/equipment/skill decisions, the body assembles effect inputs, Stats owns calculated maximums/rates and Resources owns current amounts. Test additions/removals/repeated rebuilds with zero regeneration to isolate clamping: increasing a maximum preserves current absolute amounts; decreasing it clamps downward; removing a source removes exactly its contribution. Restore provisional fixture overrides after each test. For effects test refresh-without-stacking, expiry, normal travel restoration before clamping and clean recovery without expired/transient sources.
