How to use this chapter

Follow the linked phase in order, then open individual asset pages for exact parents, folders, fields, functions and tests. Narrative recipes are suggested implementation details around the preserved architectural ownership rules.

Author two small connected maps first

Use L_Slice_A and L_Slice_B under Tests, not a World Partition template. Each has exactly one BP_AreaRoot, a corresponding area definition, a safe Start spawn and a distinct arrival spawn for the reverse connection. Put several room volumes inside an area to prove that room traversal is not the same as map traversal.

Keep transitions away from arrival spawns so possession does not immediately retrigger a return portal.

Replace automatic spawning; do not supplement it

Phase 0 uses Default Pawn Class=BP_PlayerCharacter and a native PlayerStart for the movement lab. In Phase 3 change the gameplay GameMode to Default Pawn Class=None. GameMode then explicitly waits for readiness, chooses a BP_SpawnPoint, spawns one body, initializes it and possesses it. An automatically spawned body plus a manually spawned one is a configuration bug, not a need for another manager.

TryInitializeArea

Participants may register in different orders. Retry TryInitializeArea when a prerequisite becomes ready, using bInitializing and bInitialized guards. A readiness dispatcher alone is insufficient for a late listener: bind, then query the current readiness flag. BeginPlay may register a participant, but must not later overwrite a persistent record already applied during explicit initialization.

Readiness and failure are visible states

Have the bootstrap diagnostic report the missing prerequisite: for example “SliceB: requested FromA not found; registry contains Start.” Validate a safe fallback rather than spawning at an uninitialized transform. Do not possess a failed Spawn Actor result. If no safe starting fallback is valid, keep gameplay blocked with a useful message and fix the authored map.

Preload the small required definitions and presentation assets before enabling play. A soft reference is a locator, not proof that the asset is currently loaded or cooked. Definition failures belong before mutation or teardown, not after the source map has disappeared.

Capture normal travel in the right order

Close new gameplay requests, cancel live attacks/executors, capture current health and remaining effect/recharge values, then let the old map be destroyed. The temporary handoff contains no old Actor/component references. In the new body, restore timed effect identities without replaying immediate healing, rebuild stats and maximum health, restore recharge, then clamp/restore current health. Loading time is frozen out of these remaining durations under the roadmap’s baseline.

Clear the handoff once the new body is authoritative. A stale handoff accidentally applied to the next death recovery can restore the wrong health/effects. E_EntryReason selects the policy explicitly; do not guess the reason from a nonempty struct or from whether the HUD exists.

Room context is not discovery ownership

BP_RoomVolume reports a current room to AreaRoot and a discovery request to GI. AreaRoot owns current-room/camera context; WorldState owns ever-discovered sets. Query room occupancy once after spawning as well as responding to overlaps, so spawning inside a region does not miss context initialization.

Suggested camera bounds limit the camera center, not the player’s capsule. Account for viewport coverage when tuning bounds; a narrow room may use a fixed center rather than an inverted clamp interval. Test both facing directions and do not mirror the camera with equipment visuals.

Canonical roadmap reference · PART L — World, room, and area architecture

Current guidance retains gameplay policy and incorporates the PaperZD architecture decision. Historical source text remains in the unchanged original roadmap. E-number references belong to the original roadmap; see verification notes.

Primary approach: area maps containing several rooms

Use one ordinary Level/Map asset (World) per area, with several connected rooms inside it. Group areas into biomes by BiomeId in BPDA_AreaDefinition (PrimaryDataAsset). A biome does not require a new manager class or a seamless persistent world.

Within an area, rooms are geometry plus BP_RoomVolume (Actor) instances. Crossing a room boundary updates room/camera context and discovery; it does not automatically reload a map. Between areas, BP_AreaTransition (Actor) requests Unreal's Open Level (by Object Reference) using the area's soft World reference. [E13]

This is simpler than starting with World Partition or dynamic streaming for a game that does not require one seamless world. Traditional sublevel streaming is Blueprint-compatible and remains a future option when a specific area's size/loading time justifies it; it would add load/unload readiness and Actor-lifecycle work now. [E14]

Map setup and bootstrap

Each gameplay area map has exactly one BP_AreaRoot, a Blueprint Class derived from Actor, and one or more BP_SpawnPoint instances, from a Blueprint Class derived from PlayerStart. A spawn is addressed by {AreaId, SpawnId}, not by an Actor reference stored in a save.

BP_GameMode (GameModeBase) owns a runtime Map<Name, BP_SpawnPoint reference> for the current area. Configure one spawning route: the final gameplay GameMode uses Default Pawn Class = None and spawns/possesses BP_PlayerCharacter (PaperZDCharacter → PaperCharacter → Character) explicitly after readiness. Do not combine manual spawning with an automatic default-pawn spawn. Early phase-0 automatic spawning is replaced, not supplemented, in phase 3.

Bootstrap waits for explicit prerequisites: valid session models, loaded required definitions, registered AreaRoot and PlayerController, and a validated destination. Persistent Actors default to non-interactive/unready. The bootstrap calls their persistence initialization, applies records, resolves the spawn, then creates and initializes the player body. Actors that subscribe late must query the current readiness flag as well as bind to its event.

Do not rely on arbitrary Delay(0.2) nodes or a presumed BeginPlay order. BeginPlay may register participants, but it must not overwrite a persistent state already applied by explicit initialization.

Destination and return locations

Each transition has TargetAreaId and TargetSpawnId. The reverse connection has its own authored destination. Do not guess the return position from the player's last transform. Each area's default SpawnId is a validated fallback; the project also has a validated starting-area destination.

A gate asks for its required progression/capability condition. A persistent shortcut's open record overrides its original closed presentation. Checkpoints record safe spawn identities, not a current animation or an arbitrary airborne transform.

Deliberate reset policies

Situation Persistent models Player health/effects/recharge Ordinary enemies
Move between rooms in same area Retained Retained Remain as currently simulated
Travel to another area Retained Handed off as runtime values Newly loaded area's ordinary enemies start fresh
Death recovery Retained, never rolled back Full recovery health; clear temporary effects and recharge state under this initial recovery policy Reload checkpoint area and reset ordinary enemies
Load from disk Imported from validated save Clean recovery state, not the exact saved combat instant Fresh ordinary enemies; persistent unique encounters remain completed

The recovery policy is a proposed baseline that can be changed centrally; it is not an added loss-of-progression mechanic. Normal area travel must not accidentally behave like death recovery. Capture current health, remaining effect durations, and remaining recharge/charges in S_RuntimeTravelState before teardown. Restore effects/build/max health before restoring and clamping current health. Freeze these remaining durations during the loading handoff. Clear the handoff after the new body becomes authoritative.
