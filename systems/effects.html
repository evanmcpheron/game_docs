Keep effect identity separate from its definition

DA_Effect_TestBuff says what the buff does and how long it lasts. A current S_ActiveEffect identifies one live application with EffectId, Handle and remaining-duration handoff data. BPC_StatusEffects owns active handles and game-time expiration. Profile owns whether the consumable was acquired or consumed.

CanApplyEffect → resolve/validate definition and target
ApplyEffect
  if same EffectId already active:
      refresh duration for existing Handle; do not add magnitude again
  else:
      create Handle once and active entry
  publish completed effect collection change
Body → GetStatModifiers → rebuild complete Stats cache
Expiry → remove matching Handle → rebuild once

Refresh-only is the starting stacking rule

The roadmap chooses refresh duration, no magnitude stacking for the same effect. You do not need a general stacking language, effect subclass hierarchy or permanent-stat subtraction system to prove that. A debug SourceId derived from the live Handle makes it clear which contribution disappears on expiry.

While effects exist, a controlled timer/update checks game time. Pause freezes the intended clock. Stop the update when empty. Never clear a timer by string guesswork when you can hold its TimerHandle; clear it on teardown and avoid callbacks retaining the old body.

Travel must not replay immediate effects

Export positive remaining durations and identity values. Import reconstructs active timed modifiers and deadlines but must not call a general ApplyEffect path that replays immediate healing. Restore effects before final stats and current-health clamping. Clean death/disk recovery clears effects; the consumed item remains consumed because Profile was not rolled back.

Immediate healing changes CurrentHealth through Health. A timed MaxHealth modifier changes capacity through Stats. These are different routes with different acceptance tests. A consumable that requests both must validate every intended result before any quantity mutation and publish only after the coherent operation.

Canonical roadmap reference · PART V — Buffs and temporary effects

Preserved source text, with local cross-links added for this expanded chapter. E-number references belong to the original roadmap; see verification notes.

BPC_StatusEffects is a Blueprint Actor Component derived from ActorComponent. BPDA_EffectDefinition is a Blueprint Class derived from PrimaryDataAsset. S_ActiveEffect is a Blueprint Structure asset with no parent class.

A definition contains an ID, a duration, stat modifiers, and an immediate health effect when needed for a consumable. A runtime effect contains its definition ID, unique handle, and remaining duration/deadline. Keep definitions immutable. An initial same-effect rule is refresh duration, do not stack magnitude; do not build a general stacking-rule language until a real effect requires it.

Applying/removing/expiring a timed modifier requests one Stats recalculation. The modifier source is the effect handle, so expiration removes the correct source. Never add a temporary bonus directly into permanent base stats and try to subtract it later.

Process expiry with a controlled component timer/update while effects exist. Clear it when empty. Use game time so menus and deliberate pause behave consistently. Export remaining durations on normal area travel; restore them before final health clamping. Clear effects on the chosen death/disk-recovery path.

Immediate healing goes to BPC_Health (ActorComponent), not to MaxHealth. A timed max-health buff goes through Stats. Validate both paths before consuming an inventory item. Gameplay does not wait for a consumable animation to finish before determining whether the use transaction succeeded.
