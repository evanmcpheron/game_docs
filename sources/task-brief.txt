# 2. OVERALL GAME DESCRIPTION

The completed documentation must begin with a clear description of the game being built.

This game is a:

**2D side-scrolling exploration-focused action-platforming RPG.**

Its world structure is closer to **Hollow Knight-style interconnected exploration** than a linear sequence of levels.

The game consists of:

- interconnected areas;
- rooms inside areas;
- areas grouped into larger biomes;
- branching routes;
- loops;
- shortcuts;
- gated paths;
- backtracking;
- discoveries that remain meaningful when areas are revisited.

It is **not intended to be one seamless open world**.

The player controls one persistent RPG character whose long-term progression survives normal traversal and death.

The intended experience combines:

**precision platforming + fluid movement + exploration + backtracking + real-time combat + RPG leveling + equipment + meaningful character builds + skill-tree progression + active abilities + persistent world changes + NPC interaction + gradual narrative discovery.**

## Movement

Movement is one of the highest-priority parts of the game.

The committed foundation includes:

- horizontal movement;
- responsive acceleration;
- responsive deceleration;
- responsive starting and stopping;
- responsive turning;
- jumping;
- variable jump height;
- coyote time;
- jump buffering;
- deliberate rising behavior;
- deliberate falling behavior;
- landing behavior;
- responsive airborne control;
- interruption handling;
- clean state transitions.

Movement should prioritize **player intent, responsiveness, consistency, and predictability** over unnecessary realism.

The animation system may eventually contain animations for things such as:

- sprinting;
- crouching;
- sliding;
- rolling;
- dashing;
- wall traversal;
- ledge traversal.

These are **future-compatible animation targets only**.

They are **not automatically approved gameplay mechanics**.

Do not add traversal mechanics merely because the animation architecture could support them.

## Exploration and world state

The player can:

- move between connected areas;
- explore rooms;
- revisit previous areas;
- discover shortcuts;
- activate checkpoints;
- use switches;
- interact with world objects;
- permanently open appropriate passages;
- collect persistent items;
- discover progression-gated routes;
- return after gaining abilities, equipment, progression, or knowledge.

Meaningful world changes should persist.

Ordinary enemies may reset after area reloads.

Specifically designated encounters and world events may remain permanently completed.

## RPG progression

The player has:

- character levels;
- XP/progression rewards;
- character stats;
- level-based stat growth;
- temporary buffs;
- inventory;
- consumables;
- equipment;
- armor;
- skill points;
- a skill tree;
- passive skills;
- active abilities.

Death must not erase normal persistent progression.

## Skill tree

The skill tree must support:

- explicit skill-point costs;
- prerequisites;
- Locked state;
- Available state;
- Purchased state;
- passive upgrades;
- active abilities;
- specialization;
- mutually exclusive branches where appropriate.

Build decisions should matter.

However, choosing a valid specialization must not make mandatory game progression impossible.

The final skill catalog is not yet decided.

## Equipment

Equipment can:

- modify stats;
- provide defensive benefits;
- influence builds;
- visually alter the player's character.

The character is specifically intended to support **layered visual equipment**, including clothing, armor, hats, helmets, and similar equipment.

## Combat

Combat is real-time and integrated with exploration and platforming.

The game supports:

- player attacks;
- grounded combat;
- appropriate airborne combat;
- enemy health;
- enemy damage;
- melee enemies;
- ranged enemies;
- projectiles;
- readable attack telegraphs;
- player damage;
- death;
- enemy death;
- combat rewards;
- attack interruption.

Enemy behavior should be readable enough that players can understand threats and react to them.

## Health, death, and checkpoints

The player has health.

Damage can come from:

- enemies;
- projectiles;
- environmental hazards.

After death, the player returns to the active checkpoint or the appropriate starting location.

Persistent progression survives death, including:

- character progression;
- inventory;
- equipment;
- skills;
- meaningful world changes;
- discovered locations;
- checkpoint state.

## Active abilities

The skill tree can grant active abilities.

Abilities may:

- affect enemies;
- affect world objects;
- participate in progression gating;
- use cooldowns or recharge behavior;
- use player stats;
- participate in character builds.

Development test abilities are not automatically final abilities.

## NPCs

The world contains non-hostile NPCs.

NPCs support:

- conversations;
- repeat conversations;
- condition-sensitive dialogue;
- persistent awareness of relevant player/world state.

Do not automatically introduce:

- a quest framework;
- faction reputation;
- morality;
- persuasion;
- procedural narrative;
- formal faction systems.

Those systems have not been committed.

## Saving

The game remembers meaningful player and world progress.

Loading should restore the player into a **valid recovery state**, not attempt to recreate the exact millisecond of gameplay in which the save occurred.

# 5. THE CENTRAL ARCHITECTURAL IDEA MUST BE EXPLAINED VERY CLEARLY

Make sure the reader understands the separation between:

## Authored definitions

These answer:

> What is this thing allowed to be?

Examples:

- item definitions;
- attack definitions;
- skill definitions;
- ability definitions;
- enemy definitions;
- animation sets;
- area definitions;
- dialogue definitions.

These are read-only game content.

They do not own the player's mutable progress.

## Persistent player state

`BP_PlayerProfile`

This owns persistent character progression such as:

- XP;
- skill points;
- purchased skills;
- inventory;
- equipment.

## Persistent world state

`BP_WorldState`

This owns persistent world facts such as:

- opened passages;
- collected one-time objects;
- activated checkpoints;
- discovered areas;
- discovered rooms;
- persistent encounter completion;
- relevant NPC/world flags.

## Session coordinator

`BP_GameInstance`

This survives ordinary level travel and coordinates:

- persistent models;
- cross-model transactions;
- transitions;
- recovery;
- save/load operations.

It must not become the implementation location for every gameplay feature.

## Runtime player/enemy bodies

Actors and Actor Components execute temporary live gameplay:

- movement;
- current health;
- attacks;
- temporary buffs;
- current ability recharge;
- enemy AI;
- animation presentation.

They may be destroyed and recreated.

## SaveGame

`BP_SaveGame`

This is a disk snapshot.

It is **not** the live gameplay model.

## UI and animation

UI and animation observe state and request actions.

They do not own the gameplay rules.

This separation is one of the most important lessons in the guide.

# 24. CROSS-MODEL TRANSACTIONS

```text
Validate pickup is not already collected
→ validate reward
→ grant reward to Profile
→ mark object collected in WorldState
→ commit one persistent revision
→ broadcast resulting changes
→ request save
```

There must not be an animation delay or asynchronous save in the middle of that state mutation.

Completion + reward should be committed coherently.

The switch may update a door that is not currently loaded.
