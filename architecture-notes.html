Preserved architecture, explicit issues

The original roadmap and historical manifest remain byte-for-byte preserved. The current 164-asset register adopts Paper2D + PaperZD and records the six retired plans in the decision/compatibility record. Other ownership and gameplay policies retain their existing meaning. The notes below identify aliases and implementation gaps; they are not proof of compiled systems.

Fields that arrive after a class is first created

GameInstance exists in Phase 0, while Profile/WorldState/catalog types arrive in Phase 3 and SaveGame in Phase 4. Compile a small shell first and add later typed fields when those types exist. Likewise, S_RuntimeTravelState starts with health in Phase 3; active-effect/recharge fields arrive only in Phase 9. GameCatalog adds typed maps when their schema classes exist. This is intentional staged construction, not an instruction to reorder phases.

Ability presentation has no dedicated source enum value

E_ActionState includes Ability. The current PaperZD graph uses the Attack presentation branch for that accepted action until a dedicated cosmetic requirement is approved. No additional gameplay state or traversal ability is implied. The historical animation enum has been retired; graph nodes carry presentation selection.

The ranged active-entry hook needs a concrete implementation

The source calls for ranged attacks/projectiles but does not spell out every schema field/hook. This manual suggests ProjectileClass/ProjectileSpeed on the existing attack schema from Phase 5 and a per-execution bProjectileSpawned guard. A valid projectile route spawns once at active entry instead of also applying the melee hit query. No new attack-type enum, manager or folder is required.

Deferred notifications require actual helper design

“Atomic” is an application convention here, not an Unreal database feature. Cross-model/consumable commits need validated staged changes and internal mutation helpers that suppress notifications until all intended state has changed. A helper called from GI cannot be inaccessible due to Blueprint private-function visibility; “internal” describes permitted callers in this project. Keep value collections private, expose controlled APIs and reject reentrant writes while publishing completed changes.

Save versions do not guarantee deserialization

Blueprint Structure changes can break compatibility before a migration function can inspect the header. Test retained fixture saves in the actual packaged build. Preserve a readable supported representation or implement an explicit compatibility path when a real change requires it. This manual does not invent speculative legacy assets or claim universal migration success.

A mandatory save flush must have a failure decision

Waiting indefinitely for a successful save can trap a paused menu or travel request when storage fails. Use completion-driven orchestration and visible Retry / acknowledged unsaved-progress handling. Do not busy-loop in a function or depend on a paused gameplay timer to make the decision. The exact UI choice is an implementation detail, not a new loss-on-death mechanic.

Development cook versus production cook

DA_GameCatalog currently references slice definitions and DA_PlayerBaseStats references test animation content. Therefore blanket-excluding Tests breaks the development slice. Include its required fixtures for packaged proof. Only after approved production content and references replace those dependencies should the final cook exclude development-only content. Preserve fixture folder assignments; do not move them into production folders as a workaround.

Engine evidence boundary

Official mechanism documentation was consulted, but the retrieved pages identify the Unreal 5.8 documentation family, not a demonstrated 5.8.3 test run. Blueprint menu wording, PrimaryDataAsset instance creation in your installation, launch/movement observation ordering, packaged soft references and platform save behavior remain Editor/build validation tasks. No compiled Blueprint, playable Unreal project, final artwork or engine test results are included in this ZIP.

Later use of lab/system-test maps is underspecified

The register includes L_MovementLab and L_SystemTests, but no separate area-definition instances for either. After Phase 3 replaces automatic spawning, the original lab is not automatically a valid gameplay area. Preserve a Phase 0–2 source-control snapshot for that original lab or run its obstacle course inside registered SliceA for current-build movement regression. For L_SystemTests, this manual suggests native GameModeBase and harness-only value/content tests; run player/travel end-to-end scenarios in SliceA/B. These explicit test arrangements add no asset, folder or persistent owner and do not claim the source supplied an unlisted area definition.

Incremental integration and test-world workflow

CREATE → COMPILE → CONFIGURE → INTEGRATE → EDIT TEST WORLD → RUN → VERIFY → CONTINUE. A phase is complete only after its new runtime feature reaches the real consumer and passes a playable or controlled system scenario. Use development test environments for map roles, stable fixture identity and bootstrap boundaries.

Current integration clarification: Phase 2 explicitly attaches Stats/Resources/Health/Combat and routes RequestAttack; Phase 3 replaces early automatic spawning with registered readiness and explicit single-player spawning. Unregistered L_MovementLab is not an end-to-end current gameplay area after that transition. The generated assignment contracts label proposed property names and keep every later extension phase-gated.

Mana/stamina ownership and approved scope

Approved architecture addition · 08 October 2026. One new production asset, BPC_Resources, is a Phase 2 Blueprint Actor Component (ActorComponent) in Content/Game/Combat/. Preserve every existing asset identity, phase and Content folder. This addition does not alter the historical original roadmap.

OwnerAuthoritative responsibilityExplicit exclusion
BP_PlayerProfilePersistent progression, purchased skill IDs/points, inventory/equipment decisionsNo current mana/stamina or duplicate class/bonus ledger
BPC_StatsComplete calculated seven-stat cache; final resource capacities and regeneration ratesNo current pools, resource spending or per-frame build reconstruction
BPC_ResourcesCurrent runtime mana/stamina, atomic spend/restore, game-time regeneration, clamp and suspensionNo purchases, inventory, abilities, levels, UI drawing or disk truth
BPC_HealthCurrent health, damage acceptance and deathNot merged with Resources
BPC_Combat / BPC_AbilitiesAction execution and matching token ownership; Phase 9 Abilities validates and commits resource costsNo direct resource-variable writes; basic attacks stay free
WBP_HUD / WBP_AbilitiesRead-only snapshot display and validated requests to ownersNo resource authority or per-frame stat recalculation
S_RuntimeTravelState / BP_SaveGameExisting in-memory handoff carries current pools; disk snapshot carries persistent build decisionsNo old body references; no current-resource fields in S_CharacterSave

Authored definitions describe balance, Profile holds session decisions, Stats is a derived cache, Resources is a replaceable body component, UMG is a view, disk save is a value snapshot, and normal travel is a separate in-memory runtime handoff. Do not introduce GAS, a generic attribute framework, separate Mana/Stamina components or a GameInstance resource manager. New/death/disk recovery is full; normal travel preserves and clamps absolute current values. Every valid build retains resource-free basic movement and attacks.
