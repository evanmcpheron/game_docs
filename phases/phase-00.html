Phase 0 of 0–118 new assets

Goal and why this phase comes now

Prove: Prove one configured player receives horizontal input in a stable side-on lab.

Every later system needs the configured local Controller, one body, working collision and a camera.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Implementation sequence

01. Configure the project

Open the existing project without moving its Content/Game folders. Verify Paper2D and Enhanced Input are enabled, then save/restart only if the Editor requests it. Record the actual installed engine version; the documentation targets 5.8.3 but has not run that Editor.

02. Create and compile framework shells

Create BP_GameInstance, BP_PlayerCharacter, BP_PlayerController and BP_GameMode with their exact parents. Compile each blank shell first. Now assign Game Instance Class, default GameMode, Player Controller Class and the lab Default Pawn Class. Do not add future Profile variables before those types exist.

03. Build a physical lab

Create the ordinary empty L_MovementLab, add a floor, several ledges, a ceiling test and one native PlayerStart. Use native geometry Actors for these temporary obstacles; no new custom Blueprint asset is required. Keep enough Y thickness for capsule collision.

04. Set camera and movement plane

On the player use inherited capsule/movement/Sprite, add CameraArm and Camera, constrain normal (0,1,0), and check screen direction against +X. Do not flip the camera when changing FacingSign.

05. Create input intent

Create IA_Move Axis1D, IA_Jump Boolean and IMC_Player. Add right/left mappings with the correct sign. Controller installs the context and obtains the current body; Triggered caches movement and Completed/Canceled clears it.

06. Prove the skeleton

Apply horizontal intent through one Add Movement Input path. Route jump press/release to small named request functions; the complete jump policy is Phase 1. PIE must create exactly one controllable player and repeat cleanly after Stop/Play.

Connections to wire in this phase

Controller → current Character; GameMode → configured controller/pawn; GameInstance → application session. There are no RPG models yet.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Input intent and routing, Movement.

Prerequisites

None beyond a working 5.8.3 Blueprint project and the built-in plugins.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

PIE spawns exactly one controllable player. Horizontal motion stays in XZ. The camera remains side-on. Stop and restart PIE and confirm the correct configured classes are used.

Stop condition

A deterministic empty project foundation with one player and no accidental default/template pawn.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Inventory, skill tree, ability framework, enemy AI, save logic, custom subsystems, final artwork.
