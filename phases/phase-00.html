Phase 0 of 0–118 new assets

Goal and why this phase comes now

Prove: Prove one configured player receives horizontal input in a stable side-on lab.

Every later system needs the configured local Controller, one body, working collision and a camera.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Existing assets to modify in this phase

Follow this operational sequence with the detailed implementation notes below. The creation table is the new-asset list, not permission to leave runtime assets disconnected. Development test environments and fixture rules.

No earlier-phase assets exist. Configure the new shells together now; future session functionality remains explicitly staged.

Configure the new assets and required references

  1. Create and compile the four Blueprint shells using the listed parents. BP_PlayerCharacter uses PaperZDCharacter; retain its inherited Capsule, CharacterMovement, Sprite and PaperZD Animation component. Add only the documented camera components. Do not add a second movement or animation driver.
  2. Open BP_GameMode → Class Defaults: set Player Controller Class to BP_PlayerController and Default Pawn Class to BP_PlayerCharacter for the Phase 0–2 lab. Open Project Settings → Maps & Modes and select BP_GameInstance as Game Instance Class and the intended gameplay GameMode. These are project assignments, not new classes.
  3. Open IA_Move and set Axis1D. Open IA_Jump and set Boolean with immediate/default press behavior. Open IMC_Player and add A and D mappings to IA_Move (Negate on A), and Space to IA_Jump. These are suggested development controls; do not create later actions yet.

Hook the feature into the existing game

  1. Open BP_PlayerController. Obtain the existing Enhanced Input Local Player Subsystem for the local player, and add IMC_Player once. Retain a typed CurrentBody after possession; clear it on replacement. Do not construct a custom input subsystem.
  2. Add the Enhanced Input action events: IA_Move Triggered forwards its value to the current body; Completed and Canceled clear it. IA_Jump Started forwards press intent, and Completed/Canceled forward release. In this phase the Character entry points may be compiled shells or diagnostic intent logging: the committed jump policy is implemented in Phase 1.
  3. Configure the existing CharacterMovement plane constraint for X/Z gameplay with Y as the constrained axis. Keep capsule collision separate from noncolliding Sprite presentation. Position the camera to observe the plane, not to follow mirrored sprite transforms.
  4. Compile Controller, Character and GameMode after assigning their references. Save All. BP_GameInstance remains a session shell; do not call Phase 3 Profile/WorldState initialization that has not been built.

Connections established: the edits above must reach the current ready owner, not just a compiled shell. Use each linked asset’s integration reference for the same component, interface, input and widget contract. Names newly proposed by this audit are labeled Suggested implementation detail; existing suggested field/function names retain that status. Editor/plugin behavior still requires validation in the installed project.

Update the test world

  1. Open L_MovementLab. In World Settings confirm BP_GameMode is the effective GameMode. Add native floor geometry with blocking collision, a ledge and low ceiling for the coming movement tests, and a native PlayerStart on clear supported floor. Use the documented X/Z plane and enough Y collision thickness; no prescribed world coordinates are required.
  2. Do not place an additional auto-possessed BP_PlayerCharacter alongside the GameMode-spawned player. Preserve an open floor section for later combat fixtures. This is a development lab, not an authored final area. Save the map.

Run the feature now

  1. Open L_MovementLab, choose Play In Editor with the normal player spawn rather than Play From Here, and inspect the World Outliner: one BP_PlayerController possesses exactly one BP_PlayerCharacter. Confirm the intended camera and collision orientation.
  2. Press/release A, D and Space and inspect the routed intent or debug output. Expect one jump-press request per press, signed horizontal values, and cleared values on release. Full movement feel is not a Phase 0 acceptance claim.

Failure and rejection tests

  1. Temporarily remove the effective GameMode override or an input mapping, observe the missing spawn/input route, then restore it. Stop on a duplicate pawn or failed cast; do not compensate by placing a second player.

Regression gates

  1. Stop and restart PIE twice. The same map/player/controller assignments must still work without an extra mapping installation or extra pawn.

Intentionally staged or not connected yet

BP_GameInstance is intentionally a staged session shell until Phase 3. IA_Jump is connected to an intent entry point now, but launch/buffer/coyote/variable-height behavior becomes active in Phase 1. No Stats, Health, Combat, interaction, session models or test harness is added yet.

Integrated completion gate

Stop: do not advance if one required connection or integrated gate fails, even when all new assets compile. These are expected results to run, not a claim that this documentation audit executed Unreal. Full validation suite · Project checklists.

Implementation sequence

01. Configure the project

Open the existing project without moving its Content/Game folders. Enable Paper2D, PaperZD and Enhanced Input; record the third-party plugin version and installed-build compatibility, then save/restart only if the Editor requests it. Record the actual installed engine version; the documentation targets 5.8.3 but has not run that Editor.

02. Create and compile framework shells

Create BP_GameInstance, BP_PlayerCharacter, BP_PlayerController and BP_GameMode with their exact parents. Compile each blank shell first. Now assign Game Instance Class, default GameMode, Player Controller Class and the lab Default Pawn Class. Do not add future Profile variables before those types exist.

03. Build a physical lab

Create the ordinary empty L_MovementLab, add a floor, several ledges, a ceiling test and one native PlayerStart. Use native geometry Actors for these temporary obstacles; no new custom Blueprint asset is required. Keep enough Y thickness for capsule collision.

04. Set camera and movement plane

On the player use inherited capsule/movement/Sprite, add CameraArm and Camera, constrain normal (0,1,0), and check screen direction against +X. Do not flip the camera when changing FacingSign.

05. Create input intent

Create IA_Move Axis1D, IA_Jump Boolean and IMC_Player. Add right/left mappings with the correct sign. Controller installs the context and obtains the current body; Triggered caches movement and Completed/Canceled clears it.

06. Prove the skeleton

Apply horizontal intent through one Add Movement Input path. Route jump press/release to small named request functions; the complete jump policy is Phase 1. PIE must create exactly one controllable player and repeat cleanly after Stop/Play.

Connections to wire in this phase

Controller → current Character; GameMode → configured controller/pawn; GameInstance → application session. There are no RPG models yet.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Input intent and routing, Movement.

Prerequisites

A working 5.8.3 project with Paper2D, Enhanced Input and an installed compatible PaperZD plugin. Create the player shell from PaperZDCharacter.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

PIE spawns exactly one controllable player. Horizontal motion stays in XZ. The camera remains side-on. Stop and restart PIE and confirm the correct configured classes are used.

Stop condition

A deterministic empty project foundation with one player and no accidental default/template pawn.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Inventory, skill tree, ability framework, enemy AI, save logic, custom subsystems, final artwork.
