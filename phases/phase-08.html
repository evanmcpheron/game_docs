Phase 8 of 0–118 new assets

Goal and why this phase comes now

Prove: Prove the skill graph validates real costs/prerequisites/exclusions before its UI asks for purchases.

Level points and equipment/passive source rebuilding exist, so skill rules can be implemented without duplicate authority.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Configure the new assets and required references

  1. Compile E_SkillAvailability and BPDA_SkillDefinition, then create the three test skill instances. Use explicit positive costs, TestRoot as both branches’ prerequisite, and the shared TestBranchChoice exclusion group. Keep GrantedAbilityIds and capability requirements empty in this phase.
  2. Assign all three definitions in DA_GameCatalog.Skills under matching SkillIds. Validate missing/self/cyclic prerequisites, negative costs and contradictory exclusions before enabling purchases.
  3. Create WBP_SkillTree and WBP_SkillNode. Controller owns the tree screen; the tree creates node widgets as children with SkillId/Profile references and adds them to its native panel, not separately to the viewport. Map IA_Skills (suggested K) in IMC_Player.

Hook the feature into the existing game

  1. Controller routes IA_Skills Started to OpenSkills, clears gameplay intent, creates/retains the screen, binds Profile then immediately pulls points/purchased definitions/availability, Add to Viewport and focus. Provide a native close route that works under the current modal policy.
  2. Implement Profile.GetSkillAvailability once and call the same query again inside TryPurchaseSkill. Stage point deduction and insertion into PurchasedSkillIds, then commit both and publish one build/progression change. Widgets only display the returned state/reason and request SkillId.
  3. Connect the body’s existing build observer to complete passive modifiers from purchased definitions, alongside current level/equipment inputs. Rebuild Stats once and apply the established no-free-heal clamp. GI observes the standalone committed Profile change for revision/save; do not count it twice.
  4. On load/travel bind to the existing session Profile, derive build state without replaying purchases, and refresh all node views from current values. Compile/save model, body, Controller and widgets.

Connections established: the edits above must reach the current ready owner, not just a compiled shell. Use each linked asset’s integration reference for the same component, interface, input and widget contract. Update the test world

  1. Open registered SliceA and preserve its enemy/reward/shortcut/checkpoint route. No skill-tree Actor or new map is needed. Earn sufficient points through the Phase 5 reward path, or use an explicitly labeled development public reward command for repeatable graph tests.
  2. Record initial TotalXP, UnspentSkillPoints and PurchasedSkillIds for each isolated test Profile. Keep mandatory slice connections reachable for either valid branch choice; do not solve an inaccessible route by adding an unapproved traversal ability or respec.

Run the feature now

  1. PIE: open the tree and observe locked branches before TestRoot. Earn points, buy TestRoot, buy exactly one branch, and inspect the precise point deduction and passive stat change. Close/reopen, travel and save/relaunch; purchases and points remain coherent.
  2. Run purchases through the same public model command without the tree widgets present. Reopen them and confirm immediate correct state rather than requiring a fresh unrelated event.

Failure and rejection tests

  1. Attempt insufficient-point, missing-prerequisite, excluded-branch, repeated and stale-widget purchases. No failed request changes either points or purchased IDs. Validate a deliberate cyclic/missing graph in isolated test content, then restore it.
  2. Inspect required slice routes for both legal irreversible specializations. A valid purchase must not make required progression impossible; correct test gate requirements rather than adding respec.

Regression gates

  1. Re-run equipment refresh without accumulation, Health capacity clamping, all-crossed XP awards and import without awards. Confirm inventory/combat still work with the skill UI absent.

Intentionally staged or not connected yet

GrantedAbilityIds is intentionally an empty schema field until Phase 9 supplies actual ability definitions/components. Do not add final skill catalog/balance, classes, respec or mutually exclusive required traversal gates.

Integrated completion gate

Stop: do not advance if one required connection or integrated gate fails, even when all new assets compile. These are expected results to run, not a claim that this documentation audit executed Unreal. Full validation suite · Project checklists.

Implementation sequence

01. Author the minimal graph

Create BPDA_SkillDefinition and E_SkillAvailability, then TestRoot/BranchA/BranchB. Use costs/prerequisite arrays and the same branch exclusive-group ID. These are rule fixtures, not final skills.

02. Validate without UI

Implement GetSkillAvailability and test Purchased-first, prerequisites, exclusions and points. Detect missing IDs/self-edges/cycles. Do not maintain duplicate authoritative child-edge lists.

03. Commit purchase atomically

TryPurchaseSkill rechecks the same query immediately before deducting points and inserting the ID. Failed/duplicate/reentrant calls change nothing; one completed change triggers build/save.

04. Rebuild passives

Assemble passive modifiers from the entire purchased set, replacing old inputs. Load recomputes without granting or charging again. GrantedAbilityIds may remain empty until Phase 9.

05. Draw the tree

Create WBP_SkillNode then WBP_SkillTree, add IA_Skills and wire request/observe flow. Test with stale/multiple clicks and with widgets removed. A mandatory route may not depend on an excluded specialization.

Connections to wire in this phase

Progression supplies points; Profile validates purchases; build events recalculate Stats; widgets observe and request; saves persist purchased IDs.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Skill graph and specialization, XP and leveling.

Prerequisites

Leveling, persistent Profile transactions, equipment/stat source separation.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

Insufficient points, missing prerequisites, duplicate purchase, mutually exclusive choices, multi-click purchase, passive modifier reapplication, and save/load. No test may require the widget to stay alive for the rule to work.

Stop condition

The tree is a validated graph with meaningful purchasable state, not a visual list that grants unchecked bonuses.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Final skill catalog, respec, character classes, huge passive effect engines.
