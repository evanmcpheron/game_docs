Phase 1 of 0–1116 new assets

Goal and why this phase comes now

Prove: Prove responsive single-jump movement with buffering/coyote/cut edge cases and independent visuals.

Bad movement cannot be repaired by a larger inventory or prettier skill tree. This establishes the action/presentation boundary.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Configure the new assets and required references

  1. Compile E_ActionState and BPC_ActionState. Open BP_PlayerCharacter → Components → Add → BPC_ActionState and rename the instance ActionState. Do not move velocity/floor integration out of inherited CharacterMovement.
  2. Import/configure T_TestPlayer, create SPR_TestPlayer, assign that sprite to the documented Idle/Move/Rise/Fall/Land test flipbooks, and save them. Static placeholder frames are sufficient to prove state selection; they are not finished animation.
  3. Create AS_Player as the native PaperZD Flipbook Animation Source. In its editor create each current ASQ_Player sequence and assign its corresponding FB_Player clip. Create ABP_Player using AS_Player, compile it, then open the player’s inherited Animation component and set AnimInstanceClass to ABP_Player.

Hook the feature into the existing game

  1. Open BP_PlayerController and route IA_Move to BP_PlayerCharacter.SetMoveIntent, IA_Jump Started to RequestJump, and release/cancellation to ReleaseJump. Resolve the current possessed body, not a placed map actor or stale cached body.
  2. Open BP_PlayerCharacter. Implement one cached movement application, one TryConsumeJumpRequest path, one jump budget and one variable-height cut. Use the existing buffer/coyote/native-floor policy and ExecuteJump launch path; remove any parallel native Jump binding that could issue a second impulse.
  3. Query ActionState before accepting movement/jump as prescribed. On blocking action, death/travel later, or possession loss, clear the stored intent and pending jump/cut state through the same Character cleanup path.
  4. Open ABP_Player. Read movement/floor/rise/fall/landing facts from its owning body and use the current sequences for Idle, Move, Rise, Fall and short interruptible Land. The AnimBP never calls the gameplay jump or becomes a second movement clock. Compile both modified owners.

Connections established: the edits above must reach the current ready owner, not just a compiled shell. Use each linked asset’s integration reference for the same component, interface, input and widget contract. Names newly proposed by this audit are labeled Suggested implementation detail; existing suggested field/function names retain that status. Editor/plugin behavior still requires validation in the installed project.

Update the test world

  1. Open L_MovementLab and preserve the Phase 0 floor, PlayerStart and camera. Add short/long jump gaps, a walk-off ledge, low ceiling and landing floor at meaningful distances for the current tuning. Keep their blocking collision on the same gameplay plane.
  2. Leave a clear side section unused for Phase 2 dummy/hazard tests. Do not add traversal fixtures that require double jump, dash, wall traversal or ledge traversal. Save the map.

Run the feature now

  1. PIE from L_MovementLab. Test starting, stopping, reversing and airborne steering; then compare a tap jump with a held jump. Observe the matching PaperZD states while the capsule follows the same gameplay movement.
  2. Walk off a ledge and press within/outside coyote time. Press shortly before landing to test buffering, including a buffered tap already released before landing. Hit the low ceiling and repeat landing-to-jump without a stuck Land presentation.
  3. Repeat the movement acceptance cases at the documented 30/60/120 frame-rate settings. Record expected versus observed behavior and tuning; do not infer timing correctness from a single run.

Failure and rejection tests

  1. Press jump repeatedly while already airborne, hold the key across landing, and release after a ceiling hit. Verify no extra jump impulse, no repeated cut and no free rearm before a real floor/mode transition.
  2. Block/clear input and re-enable it; the old held axis or buffered jump must not replay. Temporarily remove an animation clip and verify movement still executes, then restore the assignment.

Regression gates

  1. Restart PIE and verify Phase 0 still produces exactly one possessed player with the same camera and signed input. Changing facing must not mirror the camera or leave the Y plane.
  2. Preserve movement/jump/coyote/buffer/collision/facing and PaperZD behavior; resource specialization is not approval for sprint, dash, wall or ledge mechanics.

Intentionally staged or not connected yet

ActionState has its current movement/permission implementation now; later Attack, hit and death consumers are not yet attached. Do not add Stats, Health or Combat until Phase 2, or future-compatible unapproved traversal mechanics.

Integrated completion gate

Stop: do not advance if one required connection or integrated gate fails, even when all new assets compile. These are expected results to run, not a claim that this documentation audit executed Unreal. Full validation suite · Project checklists.

Implementation sequence

01. Create the value vocabulary

Create E_ActionState and compile BPC_ActionState. Presentation will use native PaperZD source/sequence/Blueprint assets; no parallel animation enum, snapshot or body coordinator is required. Do not add dash or double-jump states as gameplay commitments.

02. Finish horizontal feel

Separate start, stop and reversal tests. Tune native MaxWalkSpeed, MaxAcceleration, braking/friction and air control while geometry/art are simple. Save a reference tuning set before RPG systems can obscure changes.

03. Implement a single jump

RequestJump creates a pending press; TryConsumeJumpRequest validates support, budget and permission; ExecuteJump consumes via one Launch Character path. Remove any native Jump binding. Debug-print the rejection reason and launch count.

04. Add release behavior

Implement bPendingJumpCut and bJumpCutConsumed. Test press/release before native velocity becomes visible and release before a buffered landing. Cut only positive Z once, never falling velocity.

05. Add coyote and buffering

Track genuine last ground support and walk-off permission; do not refresh ground time while launch is pending. Re-arm on confirmed Walking after landing, then consume a still-valid request. Test expired requests and no second airborne jump.

06. Connect presentation

Create the registered Paper2D clips, AS_Player, five locomotion sequences and ABP_Player in that order. Build Idle/Move/Rise/Fall/Land graph nodes, connect Output Animation and assign AnimInstanceClass on the inherited PaperZD Animation component. Query movement/action facts and prove Land cannot delay new input.

07. Run interruption and frame-rate tests

Clear stale intent for blocked states. Test walk-off versus knockback, ceiling hits, short taps/holds and 30/60/120 FPS. Do not continue because the animation looks attractive; continue only when movement is predictable.

Run the phase tests

Run all Part J edge cases at multiple frame rates. In particular, test release before a buffered landing, walk-off versus knockback, no repeated coyote jumps, and landing presentation interrupted by a new jump.

Stop condition

The movement course feels responsive with placeholder art and produces no unexplained jump or input locks.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Optional traversal, movement stats tied to RPG level, combat combos, animation-driven gameplay decisions.
