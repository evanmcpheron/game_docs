Phase 3 of 0–1132 new assets

Goal and why this phase comes now

Prove: Prove lasting values survive Actor replacement during travel and death within one session.

In-memory truth must survive travel and recovery before disk serialization can be trusted to capture it.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Configure the new assets and required references

  1. Create/compile the listed value schemas, E_EntryReason, interfaces, model Objects and world Actor shells in creation order. Build only fields whose types exist. E_EquipmentSlot defines exactly Shoes, Belt, Head, Gloves, Top, and Pants; its empty equipped map and the empty inventory/purchase collections reserve later persistent shape; they do not activate equipment or skills yet.
  2. Open DA_GameCatalog and assign CharacterDefinition=DA_PlayerBaseStats, Areas entries matching SliceA/SliceB to DA_Area_SliceA/DA_Area_SliceB, and the validated StartingAreaId/StartingSpawnId. In each Area definition assign its actual L_Slice_A or L_Slice_B World and safe default spawn ID. Optional Attacks lookup may reference the Phase 2 definitions; direct player assignments still work.
  3. Open BP_GameInstance → Class Defaults and assign GameCatalog=DA_GameCatalog. In InitializeSession use Construct Object from Class for BP_PlayerProfile and BP_WorldState, Outer=self, retain typed strong references and explicitly initialize them once. Plain Objects do not receive Actor BeginPlay; GameMode must not recreate them on each map.
  4. Open BP_PlayerCharacter → Components → Add BPC_Interaction, rename Interaction and configure the documented bounded query/radius. Suggested implementation detail: use a native query shape owned by the body or an explicit bounded overlap query from the component; normalize hits to Actors and maintain only nearby candidates. No new Blueprint query-manager asset is needed.
  5. Append CurrentMana:Float and CurrentStamina:Float to S_RuntimeTravelState; refresh all Make/Break/Split/Set Members operations and recompile BP_GameInstance/BP_PlayerCharacter. Do not add Phase 9 ActiveEffects/AbilityStates types early.

Hook the feature into the existing game

  1. Open BP_GameMode → Class Defaults and set Default Pawn Class=None for registered gameplay areas. Preserve BP_PlayerController as controller class. Register Controller, exactly one AreaRoot and the spawn registry; TryInitializeArea must wait for all prerequisites and bSessionReady, with initializing/initialized guards.
  2. Implement InitializePersistentActors before gameplay readiness. Inject existing WorldState into each PersistentState, validate its authored ID and BPI_PersistentActor adapter, apply the found/default record idempotently and subscribe once. Apply must only change local projection, never replay a reward, switch or death.
  3. Adapt BP_PlayerCharacter.InitializeFromProfile to reuse the Phase 2 setup order: validate/inject current references, rebuild Stats from current supported inputs, initialize Health, initialize Combat/Interaction and presentation, then mark ready. GameMode spawns/initializes/possesses one body and tells Controller to bind. Do not keep a second automatic Phase 2 BeginPlay initializer that refills health after a travel handoff.
  4. Open IMC_Player and map IA_Interact (suggested E). In BP_PlayerController use Started → current body Interaction.TryInteract. RefreshTarget reads GetInteractionInfo without mutation; TryInteract revalidates range/readiness/interface and calls one target Interact. HUD observes OnTargetChanged and pulls PromptText immediately.
  5. Implement BPI_Interactable on BP_InteractableBase, inherited by Checkpoint/Switch/Door. Add PersistentState and BPI_PersistentActor to the persistent children. Checkpoint.Interact asks GI.ActivateCheckpoint; Switch asks GI.CommitSwitchAndTargets; Door projects Opened/collision from WorldState and cannot bypass its switch merely because it has an interaction interface.
  6. Wire BP_AreaTransition to GI.RequestAreaTravel with authored target AreaId/SpawnId. Validate destination before blocking input; suspend old-body mutation and capture health values, then open the resolved area and consume the handoff during ready reconstruction. Actor/component references do not travel.
  7. Wire player lethal events through current GameMode/GI checkpoint recovery, retaining current Profile and WorldState. ActivateCheckpoint chooses recovery location without rolling progression back or silently healing. Recovery uses active checkpoint or validated starting fallback. Compile all modified owners and save both maps.
  8. PrepareTravelHandoff closes source body readiness and suspends Resources before capturing current health/mana/stamina. Destination builds final Stats, initializes Resources suspended, imports absolute captured pools through RestoreTravelResources with clamping, finishes body readiness, binds new observers and resumes. Dead/new-game bodies use full final resources; do not reuse an unconditional BeginPlay refill.

Connections established: the edits above must reach the current ready owner, not just a compiled shell. Use each linked asset’s integration reference for the same component, interface, input and widget contract. Names newly proposed by this audit are labeled Suggested implementation detail; existing suggested field/function names retain that status. Editor/plugin behavior still requires validation in the installed project.

Update the test world

  1. Open L_Slice_A and L_Slice_B. Each uses BP_GameMode, exactly one BP_AreaRoot with its matching AreaDefinition, native blocking floor and authored BP_SpawnPoint instances. Use a safe Start spawn and explicit arrival spawns as needed; IDs must be unique within their area. No placed auto-possessed player remains.
  2. Place BP_RoomVolume instances with unique room identities, query collision and the current AreaRoot reference. Put reverse BP_AreaTransition fixtures at reachable exits. Configure target AreaId/SpawnId in Details; position arrival spawns outside the reverse trigger to prevent immediate travel loops.
  3. In a development section of registered SliceA reproduce the movement course plus BP_TrainingDummy and BP_Hazard. Place BP_Checkpoint on safe reachable floor, a BP_Switch and a BP_Door controlling a shortcut. Assign globally unique stable PersistentId values on their PersistentState components; set switch TargetPersistentIds to the actual door IDs and checkpoint Area/Spawn fields to registered safe destinations.
  4. Use a SliceB door as an unloaded-target test where appropriate, while retaining a playable route independent of that gate. Triggers are query-only; door Blocker supplies blocking collision separately. Save both maps and keep a combined ID/spawn/target log. These are slice/development fixtures, not final world design.
  5. Copy the development resource command sequence, not a new asset framework, into a gated development section of registered L_Slice_A; keep valid AreaRoot/rooms/spawns/catalog and BP_GameMode Default Pawn=None. The old L_MovementLab remains an early-phase reference.

Run the feature now

  1. PIE from registered L_Slice_A with a deliberately new test session. Confirm session models exist once, area projection finishes before input/AI, one player is possessed, and the first HUD snapshot/prompt is correct.
  2. Interact with the switch and checkpoint, travel A → B → A and observe the opened shortcut and selected checkpoint persist. Verify the unloaded door target reflects the committed record on arrival without replaying the switch.
  3. Take nonlethal hazard damage before normal travel: the new body keeps reduced health. Die after another meaningful world change: recover at the chosen safe checkpoint while retaining that later change. Repeat movement, attack and prompt selection on the replacement body.
  4. Travel resource case: in valid SliceA temporarily zero both regen rates through complete Stats inputs, set currents20/40, then use the real SliceA→SliceB exit. Source capture must equal destination20/40 (clamped only if its final max is lower); verify old body cannot spend/regenerate. Return through the reverse exit and repeat. Inject a missing destination or invalid capture and confirm rejection does not replace progress or silently refill. Restore original inputs and repeat from a fresh session.
  5. Death case: retain acquired progression/checkpoint/world flags, drain pools and die in the registered slice. The new recovery body starts at its full rebuilt health/mana/stamina; no older disk save is loaded. Repeat after both forward and reverse travel and verify exactly one body/HUD subscription set.

Failure and rejection tests

  1. Test duplicate root/ID/spawn, unknown AreaId/SpawnId, missing catalog and an unready or vanished interaction target. Reject/report the failing readiness/transaction; do not fall back to an unregistered lab or spawn a second pawn.
  2. Apply a persistent record twice; attempt an already completed operation; leave target range after the prompt appears. There must be no duplicate side effect, stale request or direct persistent mutation from the query.
  3. Open L_MovementLab under the new registered-area GameMode as a deliberate negative check: it is not an initialized gameplay area. Use a preserved early-phase revision for isolated old-lab tests, not a production readiness bypass.
  4. A source resource mutation after handoff capture, old Actor reference in S_RuntimeTravelState or destination refill of an ordinary travel handoff is a failed test.

Regression gates

  1. In registered SliceA re-run the Phase 1 movement cases and Phase 2 attack/damage/interruption cases. Travel twice and verify no duplicate HUD/model bindings, auto-heal, stale input or old-body callbacks.

Intentionally staged or not connected yet

Disk saving is Phase 4. Inventory entry/character/world/recovery schemas support current session data, but item acquisition activates in Phase 4, full inventory operations in Phase 6, equipment in Phase 7 and skill purchases in Phase 8. Keep unsupported collections empty.

S_RuntimeTravelState carries health now; timed effect/recharge fields are added in Phase 9, not placeholder references to unavailable types. L_SystemTests and its harness do not exist until Phase 11.

Import effects/charge state before final resource clamping only when Phase 9 runtime types and systems exist.

Integrated completion gate

Stop: do not advance if one required connection or integrated gate fails, even when all new assets compile. These are expected results to run, not a claim that this documentation audit executed Unreal. Full validation suite · Project checklists.

Implementation sequence

01. Create leaf and composite value types

Create E_EquipmentSlot and E_EntryReason, then inventory/world/checkpoint/recovery leaf structs before S_CharacterSave, S_WorldSave and transition/handoff composites. Inventory/equipment fields are schema only; timed handoff fields wait for Phase 9.

02. Create Object models and catalog

Compile Profile/WorldState shells, area schema and GameCatalog schema. Fill only phase-available typed catalog maps. GI constructs the two Objects once with Outer self and explicit strong references, then initializes them synchronously.

03. Build interaction and persistent application

Create interface/component shells, then implement candidate queries and stable-ID adapter injection. Persistent Actors start unready; ApplyPersistentRecord updates projection only. Add guarded switch/target transactions before disk I/O exists.

04. Author two area maps

Create L_Slice_A/B and their area definition instances in Tests. Add exactly one AreaRoot per map, safe named spawns, room volumes and separate forward/reverse transitions. Register actual map refs and start destination in DA_GameCatalog.

05. Replace spawning

Set gameplay Default Pawn Class=None. Register root/controller/spawns and retry guarded bootstrap until ready. Initialize persistent Actors, spawn/init/possess one body and bind then pull UI. Do not supplement automatic spawning.

06. Implement distinct travel and recovery

Normal travel preserves current health, mana and stamina through S_RuntimeTravelState. Checkpoint activation stores IDs; death retains current models and reloads checkpoint area for clean runtime recovery. Do not call Load Game from Slot.

07. Prove in-memory persistence

Open a shortcut, travel A→B→A, discover rooms repeatedly, activate checkpoint and die after another temporary test profile change. Model values stay while Actors are replaced. Missing/duplicate IDs/spawns must report useful failure.

Connections to wire in this phase

Interaction → target operations → GameInstance → WorldState. GameMode rebuilds Actors/body from models. Area transitions move value-based destination requests through GameInstance, not old Actor references.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Persistent models and stable world identity, Interaction, Areas, rooms, travel and bootstrap.

Prerequisites

Phase 2 health/death/locking and functioning player input.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

Open a shortcut, travel A→B→A, and confirm it remains open. Discover rooms twice without duplicate state. Activate a checkpoint, die, and return to it while model values remain unchanged. Travel with partial health, mana and stamina and verify no refill. Test missing/duplicate SpawnIds and persistent IDs.

Stop condition

In one running session, area travel and death replace Actors without losing persistent records or carrying stale world references.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Disk promises, save-menu polish, complex inventory rules, whole-biome streaming, fast travel.
