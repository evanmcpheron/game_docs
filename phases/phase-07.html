Phase 7 of 0–118 new assets

Goal and why this phase comes now

Prove: Prove equipment changes stats and appearance without copying ownership or compounding bonuses.

Equipment depends on stable inventory EntryIds and a stat cache that can be rebuilt rather than incremented.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Hook the feature into the existing game

  1. Wire WBP_Equipment selected EntryId/slot commands to Profile.TryEquip or TryUnequip. Profile validates owned quantity-one equipment and slot compatibility, replaces the slot map atomically, and publishes the completed build change. Unequip leaves the owned entry intact. Accept exactly Shoes, Belt, Head, Gloves, Top, and Pants, require definition.EquipmentSlot=Slot, and change only that slot. Reject unknown slots or an EntryId already assigned elsewhere; preserve the other five slots.
  2. On the player’s build refresh, obtain all current Profile modifiers/appearance mappings, rebuild Stats once, clamp current Health only downward if needed, and set EquipmentVisuals appearances from those same inputs. Do not make widget redraw initiate the mandatory rebuild or add the bonus repeatedly.
  3. InitializeLayers with the inherited Sprite and slot-to-layer references; SetAppearance must immediately sync to the last rendered pose. Extend ABP_Player.OnTick as documented to sample the rendered PaperZD sequence and body playback position and call SyncToBodyPose. Verify ordering against the installed plugin; this callback is a presentation integration point, not a gameplay guarantee. Map Shoes → ShoesLayer, Belt → BeltLayer, Head → HeadLayer, Gloves → GlovesLayer, Top → TopLayer and Pants → PantsLayer using six distinct component references. Initialize empty layers hidden; on every build refresh set or clear all six appearances so no removed item leaves a stale layer.
  4. Keep EquipmentVisuals autonomous Tick disabled; no independent wearable clock or duplicate Health/Combat subscriptions. Missing/incompatible sequence mappings hide deterministically. Clear layers/references on teardown, then reconstruct from Profile on the new ready body. Compile/save consumers and presentation.

Connections established: the edits above must reach the current ready owner, not just a compiled shell. Use each linked asset’s integration reference for the same component, interface, input and widget contract. Names newly proposed by this audit are labeled Suggested implementation detail; existing suggested field/function names retain that status. Editor/plugin behavior still requires validation in the installed project.

Update the test world

  1. Open SliceA and preserve the movement/combat/consumable route. Place two BP_PickupBase instances with ItemId=TestHelmet, Quantity=1 and different authored PersistentIds. Their acquired entries must receive different Profile EntryIds even though ItemId matches.
  2. Retain open floor, ledge and hazard for grounded/airborne/facing/hit/death visual tests. Do not add final armor sets or alter the canonical player dummy artwork. The fixtures remain development content.

Run the feature now

  1. Acquire both helmets, equip the exact first EntryId in Head and compare Defense before/after. Replace it with the second, repeatedly refresh/reopen UI, then unequip. Expected: one current bonus, no consumed helmet and no accumulated modifier.
  2. Observe the layer during Idle/Move/Rise/Fall and both facings. Expect deterministic hiding during unsupported Land/Attack/Hit/Death, not an invented matching animation. Test immediate equip while airborne, pause, restart and 30/60/120 rendering behavior.
  3. Travel/death/load and confirm owned/equipped EntryIds rebuild the same stats and supported appearance. Temporarily remove EquipmentVisuals: stats and ownership still work. Restore it afterward.
  4. In an explicitly temporary test copy, author one compatible equipment definition/owned entry per current slot using diagnostic modifiers and optional placeholder appearances. Equip all six together, replace/unequip each in turn, then export/import and travel. Expected: distinct slot/layer bindings, one contribution per equipped entry, unchanged other five slots and inventory ownership. These temporary fixtures do not add registered production assets or claim finished wardrobe art.

Failure and rejection tests

  1. Try wrong slot, missing/removed EntryId and direct removal of an equipped entry. Reject with no partial ownership/stat change. Test a missing appearance/mapping: hide the layer while retaining valid equipment stats.
  2. Using an explicitly labeled temporary capacity modifier fixture, increase/decrease MaxHealth and repeat equip cycles. Increased capacity is not free healing; lowering capacity clamps existing health once.
  3. Try the Head-only helmet in Shoes, Belt, Gloves, Top and Pants; reject every mismatch. Exercise unknown/legacy keys and duplicate-entry placement. With legacy save fixtures, verify only explicit versioned item/slot migrations are accepted and ambiguous/unsupported candidates never replace current models.

Regression gates

  1. Repeat consumable use, attack interruption and reduced-health normal travel. Verify cosmetic synchronization never grants damage, changes ActionState or writes the body flipbook.

Intentionally staged or not connected yet

E_EquipmentSlot was staged in Phase 3 and becomes an active equipped mapping now. Skills/ability grants wait until Phases 8/9. All six current slots (Shoes, Belt, Head, Gloves, Top, and Pants) are active; the committed helmet art fixture remains Head-only. Fully animated clothing, slots beyond these six, loadouts, durability, classes and respec are not implied by this fixture.

Integrated completion gate

Stop: do not advance if one required connection or integrated gate fails, even when all new assets compile. These are expected results to run, not a claim that this documentation audit executed Unreal. Full validation suite · Project checklists.

Implementation sequence

01. Validate equipment ownership first

Implement TryEquip/TryUnequip on the existing Profile. Slots reference owned Guids; no second inventory. Use E_EquipmentSlot (Shoes, Belt, Head, Gloves, Top, and Pants) already created as schema in Phase 3.

02. Create exact helmet fixtures

Create BPDA_EquipmentAppearance and BPC_EquipmentVisuals in Animation. Create DA_Item_TestHelmet and DA_Equipment_TestHelmet in Tests, import T_TestHelmet/create SPR_TestHelmet in Art and FB_Helmet_Test in Animation. Do not move them into Equipment just because of their purpose.

03. Assemble one build refresh

Resolve current equipped definitions and replace modifier input on each rebuild. Publish one OnBuildChanged after the slot change. Increasing maximum health does not refill current health.

04. Add synchronized native layers

Add EquipmentRoot plus ShoesLayer, BeltLayer, HeadLayer, GlovesLayer, TopLayer, and PantsLayer inside BP_PlayerCharacter. Disable visual collision and initialize BPC_EquipmentVisuals layer refs. Resolve appearance through definition references and immediately align to the last PaperZD-rendered body pose, then update from ABP_Player.OnTick.

05. Add screen and prove identity

Create WBP_Equipment with model queries/requests. Acquire two identical helmets, equip/replace/unequip/load and compare exact EntryIds and final stats. No bonus accumulation or ownership loss is acceptable.

Connections to wire in this phase

Equipment request → Profile mapping → OnBuildChanged → Stats and EquipmentVisuals → UI/save update.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Equipment and visible layers, Animation and layered presentation, Stats and build reconstruction.

Prerequisites

Inventory identity, stat rebuilding, and PaperZD body presentation.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

Equip, replace, unequip, acquire two identical helmets, and reload. Verify no duplicated modifiers, invalid slot references, free healing, or disappearing ownership. Change equipment mid-jump/attack and confirm layers remain synchronized and non-colliding.

Stop condition

Equipment changes character stats and appearance through data, with one authoritative ownership record.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Multiple loadouts, cosmetic overrides as a separate system, durability, item randomization.
