Phase 9 of 0–1117 new assets

Goal and why this phase comes now

Prove: Prove derived ability unlocks, accepted execution, safe cancellation and timed-effect travel policy.

Purchased skills now supply unlock truth, while proven action/interaction/persistence contracts support actual execution.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Configure the new assets and required references

  1. Compile the current ability/effect schemas, runtime value structs, BPI_AbilityTarget and component/executor shells before typed assignments. Open BP_PlayerCharacter → Components and add BPC_Abilities as Abilities and BPC_StatusEffects as StatusEffects.
  2. Configure DA_Skill_TestActive as the documented nonexclusive active test grant, DA_Ability_TestPulse with ExecutorClass BP_Ability_TestPulse and legal charge/recharge/range values, DA_Effect_TestBuff with the refresh-only timed modifier, and DA_Item_TestBuffConsumable with TimedEffectId=TestBuff and no duplicate immediate heal. Register all matching IDs in DA_GameCatalog.
  3. The original three-row level fixture grants only two skill points, while TestRoot + either branch + TestActive costs three. Suggested development fixture extension: reopen DT_LevelProgression and add the next valid Level row with a strictly greater TotalXPRequired, coherent CumulativeStatGrowth and SkillPointsAwardedOnEnteringThisLevel sufficient for the remaining grant. Put the threshold above the recorded current test Profile XP, or start a fresh isolated test Profile. Earn the new entry award through the existing enemy/XP path; do not replay awards on import or directly overwrite points. This extends test data, not final balance or a respec system.
  4. Create BP_AbilityTestReceiver with its query Trigger and PersistentState. Add BPI_AbilityTarget and BPI_PersistentActor in Class Settings; set RequiredCapability=Capability.TestPulse using the project’s registered tag workflow. This is a development capability/receiver, not a final ability or world mechanic.
  5. Add ManaCost and StaminaCost Float fields default0 to BPDA_AbilityDefinition; require finite nonnegative values. Set DA_Ability_TestPulse to10/0, preserving MaxCharges1/RechargeDuration2 and its original target/capability/damage setup. Inject Character.Resources into BPC_Abilities and WBP_Abilities.

Hook the feature into the existing game

  1. During explicit player setup inject ActionState and GameCatalog into Abilities, catalog into StatusEffects, and current Profile-derived unlocks through RefreshUnlocks. Keep existing valid charge/recharge ledgers on ordinary build refresh; equipping an item must not refill abilities.
  2. Map IA_AbilityPrimary (suggested Q) in IMC_Player. Controller Started → ready current body → Abilities.TryActivate with the configured development AbilityId and freshly built S_AbilityContext. Suggested implementation detail: use a single PrimaryAbilityId=TestPulse test slot on the body; this does not grant its unlock or bypass purchased-skill checks.
  3. TryActivate validates unlock, live body/context/target, definition/class, charges and ActionState before acceptance. Resolve/preload first, acquire token, spawn inert executor, release only that token on preparation failure, then commit charge/recharge and explicitly StartAbility. BeginPlay is not an effect trigger.
  4. TestPulse performs the documented bounded/deduplicated query: damageable enemy → existing S_DamageSpec/Health route; eligible environmental receiver → BPI_AbilityTarget.ReceiveAbility → GI.CommitWorldRecord. Revalidate targets and select the intended route per Actor, avoiding unintended double effects. Finish/cancel exactly once; accepted miss/interruption does not refund the charge.
  5. Connect StatusEffects.OnEffectsChanged to one complete body build refresh. Same EffectId refreshes duration without magnitude stacking; modifiers use live handles. GI.TryUseItem validates effect resolution/benefit before the coherent quantity/effect commit, with no latent work or observer between mutations.
  6. Extend travel export/import with positive remaining durations and charge/recharge values. Suspend old body, export before cancellation/teardown, import timed effects before final Stats/Health clamping, and rebuild deadlines relative to new game time without replaying immediate healing. Death/disk load retains purchases/consumed quantities but resets the documented transient effects/charges.
  7. Controller creates/retains WBP_Abilities after body readiness, binds Abilities then pulls state and adds the nonmodal view to the viewport. ABP_Player observes accepted ability facts through the existing presentation policy. Neither UI progress nor animation restores charges, applies effects or releases tokens. Compile and Save All.
  8. Follow BPC_Abilities resource-and-charge acceptance transaction exactly: resolve/unlock/body/target/charge/affordability checks → preload → action token → inert executor preparation → immediate revalidation → guarded BeginDeferredSpend → prevalidated charge/deadline/executor commit without callbacks → complete ability/resource notifications → StartAbility if still valid. Preacceptance rejection cleans prepared state/matching token with no resource/charge consumption; accepted miss/interruption does not refund.
  9. Extend WBP_Abilities.BindSources with Resources. Bind charge and resource events once, pull immediately, distinguish locked from insufficient-resource/charge/target/action availability, and unbind old bodies. UI never directly spends. During normal travel restore effects and final Stats before current health/mana/stamina clamp, then restore supported recharge state and resume.

Update the test world

  1. Open SliceA and retain all existing acceptance fixtures. Place BP_AbilityTestReceiver within the test pulse’s documented range from a safe standing area; give it a unique authored PersistentId, query collision covering gameplay depth and the matching RequiredCapability. Keep it distinct from damageable enemies.
  2. Place a BP_PickupBase for TestBuffConsumable with a different stable ID and positive quantity. Retain a dummy/enemy and hazard nearby but not overlapping spawn or receiver. A development gate may observe the receiver’s persistent result, but keep required slice travel reachable for every valid branch.
  3. Save both registered slices and record charge counts/effect remaining durations before travel. Do not place an auto-started BP_Ability_TestPulse executor in the level; it must be spawned by an accepted Abilities command.

Run the feature now

  1. PIE: retain the chosen Phase 8 branch, earn the documented additional entry award through the reachable enemy/reward route, and purchase TestActive through the real skill path. Then press the ability control near damageable and environmental targets. Observe one accepted execution, one charge consumption, gameplay damage/persistent receiver change and bounded recharge.
  2. Use the buff consumable, verify one quantity decrement and one modifier source, then refresh the same effect. Travel while its duration/recharge remains active; the new body preserves remaining values without double healing or free refills.
  3. Die and then save/relaunch: purchases, consumed items and the receiver’s completed record persist; temporary runtime state follows the clean recovery policy. Remove ability UI/presentation and repeat authoritative requests.
  4. Ability cost case: unlock nonexclusive TestActive through the existing real progression fixture and start with full50/100, available charge. TestPulse consumes10 mana and one charge exactly once. Failed target, missing/preparation-failed executor, lost token, locked ID or insufficient mana leaves both pools/charge unchanged. Trigger interruption after acceptance: no refund. Bind a completed-state listener that queries both ledgers and attempts nested activation: coherent committed state, nested rejection. Reset charge through the real recharge path or fresh body, restore full pools and repeat.
  5. Stamina/dual fixture case: outside Play record TestPulse definition, temporarily set costs0/20, then in a separate reset run10/20. Test stamina-only deduction and fail a dual request with one pool insufficient: neither resource/charge changes. Test both costs0 (charge rules still apply, no meaningless resource event), then restore10/0 and all original fixture fields. Do not create a new final warrior ability.
  6. Effect/travel case: temporarily append a resource-maximum/rate modifier to an existing timed effect fixture and apply through its approved owner. Refresh it twice (no magnitude stacking), spend pools, travel SliceA↔SliceB while active, and verify effect restoration precedes absolute pool clamping with no loading-time regeneration. Let it expire: contribution removed once/current clamped, no permanent bonus. Die/load: transient effects cleared, final resources full. Restore definition/rates and reset the fixture.

Failure and rejection tests

  1. Test locked ability, wrong capability, absent executor/definition, unsupported target, no charge and invalid/dead body. Failure before acceptance consumes nothing and leaves no action lock. Once accepted, miss/interruption follows the no-refund baseline.
  2. Cancel during execution, remove a target, kill the source, pause and travel, then deliver an obsolete completion callback. No lingering executor/timer or release of a newer token is permitted. An equipment/skill refresh cannot reset a still-valid cooldown.
  3. Use an unknown effect item and repeat a same-effect application. Unknown data consumes nothing; valid refresh never stacks magnitude. Restore deliberately altered fixture definitions afterward.
  4. No latent work or dispatcher/target callback between resource deduction and charge commit. Prepared executor BeginPlay must have no gameplay effect. A cost failure must not consume charge, keep a token, or destroy unrelated active execution.

Regression gates

  1. Repeat complete stat rebuild/no-free-heal, atomic pickup/use, normal reduced-health travel, checkpoint-no-rollback and save import without purchase/reward replay. Existing attacks and movement must remain responsive under ability interruption.

Intentionally staged or not connected yet

BP_AbilityBase is an inert executor base, not placed content. S_AbilityContext is runtime-only and never enters save/travel snapshots. TestPulse/TestBuff/capability tags are development fixtures, not approved final abilities or traversal mechanics. Mana/stamina is the separately approved resource architecture.

Integrated completion gate

Stop: do not advance if one required connection or integrated gate fails, even when all new assets compile. These are expected results to run, not a claim that this documentation audit executed Unreal. Full validation suite · Project checklists.

Implementation sequence

01. Create runtime types and shells

Create S_AbilityContext, S_AbilityRuntimeState and S_ActiveEffect, then interface/component/executor/schema shells. Compile mutually referring class shells before filling typed variables. No new persistent purchased-ability list is added.

02. Derive unlocks

Create TestActive and register the TestPulse definition. Profile derives unlocked IDs from purchased skills. RefreshUnlocks preserves existing still-valid recharge rather than resetting on every build event.

03. Accept one executor safely

Validate definition/body/target/charge/action and required class availability. Spawn inert executor, handle failure before charge commitment, then consume/start cooldown and call explicit StartAbility. Finish/Cancel are token-guarded and idempotent.

04. Prove enemy and world targets

Implement TestPulse and AbilityTestReceiver in Tests. Use Damageable for health and AbilityTarget for world effects, deduplicate targets, persist environmental result through GI and never replay on restoration.

05. Add refresh-only timed effects

Create TestBuff and its consumable, resolve effect before quantity commit. StatusEffects owns handles/deadlines; same effect refreshes duration without stacking magnitude. Rebuild Stats after complete changes.

06. Extend normal travel only

Add ActiveEffects and AbilityStates fields to S_RuntimeTravelState now. Export remaining time/charges; restore effects before final stats/health/mana/stamina clamping and do not replay immediate effects. Disk snapshot remains recovery-state, not exact timer state.

07. Test cancellation and progress safety

Test locked/missing/failed activation, delayed recharge, repeated finish, dead target/source, travel while recharging, paused clocks and effect expiry. Verify mandatory capability access is not accidentally excluded by specialization.

Connections to wire in this phase

Purchased skill → derived unlock → Abilities → executor → damage/world interface. Effects → Stats. Travel export/import preserves durations and recharge; death/disk recovery resets them according to policy.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Active abilities and capability gates, Temporary effects.

Prerequisites

Actions/combat, skills, data catalog, persistence, and transactional consumable use.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

Locked ability, missing executor, failed target validation, successful use, cooldown, delayed recharge updates, cancellation, stale callbacks, death during execution, normal travel during cooldown, and effect expiration. Reapplying a refresh-only buff does not stack magnitude. A world effect survives a restart without replaying the ability.

Stop condition

A new ability can be added as a definition and shallow executor child without editing one giant switch graph or the save schema.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

GAS migration, a competing resource framework, unapproved traversal and final ability balancing.
