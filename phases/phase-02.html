Phase 2 of 0–1124 new assets

Goal and why this phase comes now

Prove: Prove an authoritative damage/action loop without AI or RPG complexity.

A dummy isolates hit acceptance and action timing before moving targets, AI and rewards make failures harder to locate.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Configure the new assets and required references

  1. Create/compile the enums, value structs, BPI_Damageable and the data schemas before filling typed component references. Compile BPC_Stats, BPC_Health and BPC_Combat shells, then implement their current-phase contracts. Shell compilation is only a dependency checkpoint, not phase completion.
  2. Open BP_PlayerCharacter → Components → Add: add BPC_Stats as Stats, BPC_Health as Health, and BPC_Combat as Combat. Keep the existing ActionState instance. Compile. In Class Settings → Implemented Interfaces add BPI_Damageable, then compile again.
  3. Create DA_PlayerBaseStats using BPDA_CharacterDefinition and configure the documented base stats (initial MaxHealth 100, AttackPower 10, Defense 0) and AnimInstanceClass ABP_Player. Create DA_Attack_PlayerGroundTest and DA_Attack_PlayerAirTest from BPDA_AttackDefinition; set their grounded/airborne eligibility oppositely and retain the documented provisional timing/query values.
  4. Suggested implementation detail: add CharacterDefinition, GroundAttackDefinition and AirAttackDefinition object-reference properties to BP_PlayerCharacter. In Class Defaults assign DA_PlayerBaseStats, DA_Attack_PlayerGroundTest and DA_Attack_PlayerAirTest respectively. These are proposed property names, not verified game-code fields. Do not assign an idle default into Combat.AttackDefinition: that field describes the current accepted execution.
  5. Open BP_TrainingDummy. Add native Hurtbox query collision plus Stats and Health, implement BPI_Damageable in Class Settings, and use the documented dummy BaseStats and Enemy combat side. It does not need Combat, AI, a persistent ID or rewards. Open BP_Hazard and configure its native Trigger, DamageSpec and positive RepeatInterval; it is a damage source, not a second Health authority.

Hook the feature into the existing game

  1. Suggested implementation detail: create one explicit InitializeCombatBody function on BP_PlayerCharacter and call it from the early lab body setup. Keep gameplay unready until it succeeds. Get the owned component references directly from Components variables: validate CharacterDefinition and attack definitions; pass base stats, zero level growth and an empty modifier array to Stats.Recalculate; initialize Health with that ready Stats reference and its initial capacity; inject the same Stats and ActionState references into Combat. Do not depend on component BeginPlay order or a global discovery scan.
  2. Open BPC_Stats.Recalculate and call the documented BFL_GameRules.CalculateStat with explicit per-stat base/growth/flat/percentage/minimum values. Open BPC_Health.TryReceiveDamage and call BFL_GameRules.CalculateDamage once after validating raw input. These suggested pure function names are the existing reference contract; do not duplicate mitigation in Combat or the Character. EvaluateCondition is a Phase 10 extension, not an early typed function.
  3. Bind Health.OnDamageAccepted/OnDied to the Character adapter and ActionState.OnInterrupted to the matching Combat cancellation path. Accepted damage alone can request hit response/knockback; lethal damage establishes Dead and cancels the matching attack. Clear movement requests and hit queries on interruption. Health keeps current health/death detection; the Character does not duplicate those variables.
  4. Implement BPI_Damageable on the Character: GetCombatSide returns Player; ReceiveDamage validates readiness, forwards the unchanged S_DamageSpec to Health.TryReceiveDamage, and returns S_DamageResult. Health queries Stats for capacity/defense and applies mitigation once. Implement the same forwarding adapter on the dummy with Enemy side. Hazard overlap/repeat calls this interface on supported actors; do not bypass it by directly subtracting health.
  5. Open IMC_Player → add a mapping for IA_Attack (suggested J). Open BP_PlayerController and add the IA_Attack Started event, not an unguarded per-frame Triggered attack. Validate CurrentBody/readiness and call BP_PlayerCharacter.RequestAttack. Suggested implementation detail: RequestAttack selects GroundAttackDefinition or AirAttackDefinition from the actual movement mode, then calls Combat.TryStartAttack(Definition) and returns its result/reason. It never sets an action lock or damage itself.
  6. Combat validates the definition/body/mode, requests ActionState.TryBeginAction, snapshots stats and advances authoritative Windup → Active → Recovery. During the active interval it performs the blocking-aware hit query, normalizes/deduplicates Actors, records each target attempt before BPI_Damageable.ReceiveDamage, and eventually finishes or cancels only its matching token. Include crossed-active-window handling under hitches; do not make notifies necessary for queries or cleanup.
  7. Open AS_Player and assign the documented FB_Player_LandTest placeholder to the new Attack/Hit/Death sequences. Extend ABP_Player with Death → Hit → Attack priority over locomotion. Read current gameplay facts and token/body identity, rather than using animation completion to authorize damage or release actions.
  8. Open BP_PlayerController. After possession and successful InitializeCombatBody, create WBP_HUD with this Controller as Owning Player, retain HUD, supply current Health/Stats, bind once, immediately refresh, and Add to Viewport. Readiness and possession may arrive in either order: both call the same guarded setup check. Unbind the old body before replacing it. Compile all modified consumers and Save All.

Connections established: the edits above must reach the current ready owner, not just a compiled shell. Use each linked asset’s integration reference for the same component, interface, input and widget contract. Names newly proposed by this audit are labeled Suggested implementation detail; existing suggested field/function names retain that status. Editor/plugin behavior still requires validation in the installed project.

Update the test world

  1. Open L_MovementLab and preserve every Phase 1 movement obstacle. In the reserved open-floor section drag BP_TrainingDummy from Content Browser into the level. Give it enough clearance for both facing directions and repeated grounded swings. Add another target at a reachable ledge/platform height for the already-committed airborne attack; do not invent a new traversal move.
  2. Place BP_Hazard off the main spawn/movement route so damage and lethal tests are deliberate. Select each fixture and check its documented stats/damage/repeat properties in Details. Keep all query shapes on the X/Z gameplay plane with adequate Y thickness. Dummy Hurtbox must respond to the attack query; hazard Trigger must generate the intended overlaps with the player capsule. Sprite collision stays disabled.
  3. Verify World Settings still resolves BP_GameMode, its Default Pawn still supplies one player, and PlayerStart is outside hazards and blocking geometry. Preserve camera orientation. Save the level. These are development fixtures: retain the movement course, and reproduce this test section in registered SliceA after Phase 3 rather than bypassing area readiness.

Run the feature now

  1. Open L_MovementLab, Save All, then PIE. Move next to the dummy and press the mapped attack control once. Inspect Combat phase/token and dummy Health before/after. Expected: Windup → Active → Recovery and at most one target attempt/damage result for this swing, even while remaining overlapped.
  2. Start a second swing after recovery: the same target can be damaged again. Attack while jumping using the airborne definition, face the other direction and repeat. With the unchanged suggested player/dummy values, raw damage is 5 + 1 × 10 = 15 before the dummy’s zero defense; record actual values if tuning differs.
  3. Walk into the hazard, then leave and re-enter. Confirm accepted damage arrives through the player interface/Health path and sustained overlaps obey the repeat/acceptance policy, not frame rate. Test interruption during windup, active and recovery.
  4. Apply lethal hazard damage. Expected: Health reports death once, ActionState becomes Dead, current attack/query cleanup completes, and new attack requests fail. Phase 2 recovery is Stop/Play to restart the lab; checkpoints do not exist yet.
  5. Temporarily remove HUD/animation presentation and repeat a nonlethal attack/damage case using component debug values. Gameplay must still work. Restore presentation, then repeat the Phase 1 tap/held jump, coyote, buffer, turn and landing cases.

Failure and rejection tests

  1. Attack with a missing definition, during recovery/hit response, while dead, and against an Actor without BPI_Damageable. Requests must fail or skip unsupported targets without partial locks, damage or Accessed None errors. Restore deliberately cleared test references.
  2. Place blocking geometry between attacker and target and verify no through-wall hit. Simulate a coarse update crossing the whole Active interval: the documented query policy must still be evaluated. Deliver an old cancellation/completion token and verify it cannot release a newer action.
  3. Remain overlapped with an invulnerable/rejecting target for one swing. The initial policy records the attempt once even if rejected; that swing must not retry continuously until invulnerability ends.

Regression gates

  1. Re-run single-jump, buffered tap, ceiling, grounded/airborne turning and interrupted Land cases in the unchanged movement course. Check movement request clearing after Hit/Dead and exactly one player after PIE restart.

Intentionally staged or not connected yet

S_StatModifier exists and is passed as an empty array now; equipment/passive/effect contributions arrive in Phases 7/8/9, with level growth in Phase 5. WBP_HUD initially shows Health/Stats only; Profile/interaction arrive in Phase 3 and ability panels in Phase 9.

Do not add Interaction, Profile, WorldState, checkpoint recovery, enemy AI, inventory, EquipmentVisuals, Abilities or StatusEffects in Phase 2. Attack ProjectileClass/ProjectileSpeed are Phase 5 extensions; do not add typed projectile references before that class exists.

Integrated completion gate

Stop: do not advance if one required connection or integrated gate fails, even when all new assets compile. These are expected results to run, not a claim that this documentation audit executed Unreal. Full validation suite · Project checklists.

Implementation sequence

01. Build Stats first

Create enums and value structures, compile BFL_GameRules, define one transparent test damage/stat formula and initialize BPC_Stats from DA_PlayerBaseStats. Use zero growth and no equipment/passive/effect sources yet.

02. Build Health and a target adapter

Inject Stats into BPC_Health, initialize health/readiness, implement BPI_Damageable on player and BP_TrainingDummy. Send a known test packet directly before introducing attack timing. Check lethal once-only behavior.

03. Add action arbitration

Implement the explicit permission table and generation tokens in BPC_ActionState. Verify an old EndAction cannot release a newer action, Transition or Dead.

04. Execute one attack

Create grounded and airborne attack instances. Route IA_Attack Started to TryStartAttack, acquire token, snapshot raw damage and run one elapsed clock through Windup/Active/Recovery. Draw hit shapes and phase text.

05. Handle hits once

Normalize targets to Actors, filter contract/side/obstruction and use one per-swing Set. Test multiple target collision components and a delayed update spanning the active interval.

06. Wire reactions, hazard and HUD

Health events drive body interruption/knockback/death; they do not choose a checkpoint yet. Add BP_Hazard repeat policy and WBP_HUD event-driven health display. Lethal player damage may remain dead until lab restart in this phase.

07. Cancel every stage

Interrupt Windup, Active and Recovery and inspect no later hit/query/token release. Remove HUD/animation and verify the rules still work. No enemy AI or equipment is needed to pass.

Connections to wire in this phase

Attack input → Character → ActionState/Combat → BPI_Damageable → Health → events. Stats supplies max health and combat values.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Stats and build reconstruction, Combat, damage and action ownership.

Prerequisites

Movement quality and interruption contract from phase 1.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

One swing hits a dummy once despite multiple overlaps. A new swing can hit again. Attacks fail while dead. Interrupt an attack during each phase. Ensure a low-frame-rate update crossing the entire active window still performs the intended hit test. Hazards and enemy-style damage use one acceptance path.

Stop condition

A coherent action/damage loop without AI or progression, and no damage caused by animation callbacks.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Complex enemy behavior, elaborate damage types, equipment, skills, per-weapon frameworks, GAS.
