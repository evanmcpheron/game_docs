Phase 2 of 0–1121 new assets

Goal and why this phase comes now

Prove: Prove an authoritative damage/action loop without AI or RPG complexity.

A dummy isolates hit acceptance and action timing before moving targets, AI and rewards make failures harder to locate.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Implementation sequence

01. Build Stats first

Create enums and value structures, compile BFL_GameRules, define one transparent test damage/stat formula and initialize BPC_Stats from DA_PlayerBaseStats. Use zero growth and no equipment/passive/effect sources yet.

02. Build Health and a target adapter

Inject Stats into BPC_Health, initialize health/readiness, implement BPI_Damageable on player and BP_TrainingDummy. Send a known test packet directly before introducing attack timing. Check lethal once-only behavior.

03. Add action arbitration

Implement the explicit permission table and generation tokens in BPC_ActionState. Verify an old EndAction cannot release a newer action, Transition or Dead.

04. Execute one attack

Create grounded and airborne attack instances. Route IA_Attack Started to TryStartAttack, acquire token, snapshot raw damage and run one elapsed clock through Windup/Active/Recovery. Draw hit shapes and phase text.

05. Handle hits once

Normalize targets to Actors, filter contract/side/obstruction and use one per-swing Set. Test multiple target collision components and a delayed update spanning the active interval.

06. Wire reactions, hazard and HUD

Health events drive body interruption/knockback/death; they do not choose a checkpoint yet. Add BP_Hazard repeat policy and WBP_HUD event-driven health display. Lethal player damage may remain dead until lab restart in this phase.

07. Cancel every stage

Interrupt Windup, Active and Recovery and inspect no later hit/query/token release. Remove HUD/animation and verify the rules still work. No enemy AI or equipment is needed to pass.

Connections to wire in this phase

Attack input → Character → ActionState/Combat → BPI_Damageable → Health → events. Stats supplies max health and combat values.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Stats and build reconstruction, Combat, damage and action ownership.

Prerequisites

Movement quality and interruption contract from phase 1.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

One swing hits a dummy once despite multiple overlaps. A new swing can hit again. Attacks fail while dead. Interrupt an attack during each phase. Ensure a low-frame-rate update crossing the entire active window still performs the intended hit test. Hazards and enemy-style damage use one acceptance path.

Stop condition

A coherent action/damage loop without AI or progression, and no damage caused by animation callbacks.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Complex enemy behavior, elaborate damage types, equipment, skills, per-weapon frameworks, GAS.
