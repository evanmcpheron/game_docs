Goal and why this phase comes now

Prove: Prove readable melee/ranged threats, once-only rewards and multi-level progression integrate with persistence.

Enemies now reuse proven combat and rewards can rely on a coherent persistent transaction/save path.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

  1. Create S_LevelProgressionRow before DT_LevelProgression. Select that exact row structure and author the documented cumulative fixture thresholds/growth/entry awards. Assign the table to DA_GameCatalog.LevelProgression; validate explicit Level ordering rather than row-name enumeration order.
  2. Compile BP_EnemyBase and BP_EnemyAIController before children/data. On EnemyBase add Stats, Health, ActionState and Combat; implement BPI_Damageable. Retain inherited PaperZD Animation.   3. Create AS_EnemyTest, its five sequences and ABP_EnemyTest using the documented placeholder clips. Assign ABP_EnemyTest to both enemy definitions and the inherited Animation component setup. Configure the melee/ranged child EnemyDefinition defaults and the definitions’ Attacks arrays.

Hook the feature into the existing game

  1. InitializeEnemy validates its definition, recalculates Stats, initializes Health, injects ActionState/Stats into Combat, and applies any unique persistent record before enabling AI. The damage interface forwards to Health exactly as the player/dummy adapters do.
  2. AIController possession obtains its controlled enemy and waits for bReady. Its think timer selects target/movement/attack intent; the body applies movement every simulation update and Combat owns windup/active/recovery. Subscribe to Combat completion/cancellation rather than adding an AI attack timer.
  3. At ranged Active entry spawn one inert projectile from the accepted execution, initialize its snapshotted S_DamageSpec/shooter/direction/speed, then enable its movement/collision. Mark the per-execution spawn guard before callbacks. This path replaces the melee query for that execution; it does not run both.
  4. Connect Health.OnDied → EnemyBase guarded legitimate-death adapter: stop AI and actions, set reward guard before callbacks, then ordinary enemy → GI.GrantReward or unique encounter → GI.CommitUniqueEncounter. Persistent record application and EndPlay never grant rewards.
  5. Wire Profile.AwardXP to validated cumulative thresholds and all crossed entry awards once. Import recomputes CachedLevel without awards. Body observes completed build/progression changes → complete Stats rebuild → Health.ClampToMaximum; HUD separately observes. Finish the melee architecture slice before adding ranged complexity, then finish ranged tests before marking Phase 5 complete.

Update the test world

  1. Open registered SliceA and preserve dummy, hazard, pickup, checkpoint and switch route. Place BP_Enemy_MeleeBasic on supported clear floor with a valid EnemyDefinition, readable approach distance and safe separation from the player spawn. Confirm enemy capsule collision and local floor/wall probes.
  2. Add a separately identified unique test placement using the documented PersistentState/BPI_PersistentActor setup; assign an authored globally unique PersistentId and enable the unique-encounter policy. Keep the ordinary placement transient. Do not label every enemy persistent.
  3. Place BP_Enemy_RangedBasic in a clear development lane with a blocking wall/thin-obstacle case and reachable player positions. Use SliceB if that keeps the existing route readable. Confirm projectiles and targets overlap the same Y depth; retain reverse travel and safe spawn separation.

Run the feature now

  1. Run the first vertical slice in registered areas: move, take damage/travel, defeat a melee enemy, cross an XP threshold, collect pickup/open shortcut, activate checkpoint, earn another reward, die, travel and save/relaunch. Compare persistent values at each step.
  2. Defeat ordinary and unique enemies, travel A → B → A and reload from disk. Expected: ordinary encounters may reset; completed unique placement is suppressed before AI and pays no repeated reward.
  3. Run the ranged fixture: observe telegraph, one projectile per accepted attack, shooter exclusion, wall impact, accepted player damage and interruption cleanup. Repeat without HUD and without animation notifies.
  4. Level-growth resource test: in the existing progression fixture temporarily author Level02 cumulative resource growth(+5 MaxMana,+10 MaxStamina,0,0), retain original fields and award XP through the real owner to cross its threshold once. With zero regen and spent pools, maximums rise by5/10 but current amounts do not refill. Rebuild twice and import saved progression: no duplicate growth or awarded points. Restore the original zero resource-growth row/Stats rates and start a fresh test session.

Failure and rejection tests

  1. Apply repeated death callbacks, unload an enemy without killing it and reapply a unique Completed record. None may duplicate rewards. Missing EnemyDefinition, attack/projectile class or progression rows must fail validation before active AI/reward mutation.
  2. Use the documented 130-XP fixture award with the three-row curve: level 3 and two entry awards, once. Export/import and repeated build refresh do not add points again. Test projectile duplicate hit/overlap callbacks and thin walls.

Regression gates

  1. Repeat one-swing target deduplication and stale action token rejection, reduced-health travel, atomic pickup and checkpoint-no-rollback tests. Level capacity growth cannot provide free healing.

Intentionally staged or not connected yet

Enemy art and melee/ranged numbers remain development fixtures; no faction system, complex navigation framework, new damage taxonomy or loot economy is introduced. Skill points accumulate now, but purchases wait until Phase 8.

Implementation sequence

01. Initialize the enemy family

Create enemy base/controller shells, enum and enemy schema. Add shared components and damage adapter. Configure AI possession but wait for readiness and optional unique record suppression before thinking.

02. Prove melee decisions

Create DA_Enemy_MeleeTest and DA_Attack_EnemyMeleeTest. Use simple target/range/floor/wall decisions. Body applies cached movement every update; Combat owns telegraph and recovery.

03. Create ordered progression

Create S_LevelProgressionRow then DT_LevelProgression, author a few explicit cumulative thresholds and register the table. AwardXP processes every crossed threshold once, with bounded traversal.

04. Connect legitimate death rewards

EnemyBase sets its local guard before calling GI. Ordinary enemies grant once per live instance; unique encounters commit completion and reward coherently. Loaded completion suppresses without death/reward replay.

05. Stop for the first architecture slice

Use phases 0–4 plus melee/rewards/leveling: traverse two areas, take damage, earn XP/item, open shortcut, activate checkpoint, earn later reward, die, restart and verify everything. Do this before expanding enemy variety.

06. Add the ranged route

Create BP_ProjectileBase with native collision root and projectile movement. Add typed projectile fields/hook to existing attack schema now. Ranged child spawns once at active entry; it does not also run melee damage.

07. Finish Phase 5 proof

Test shooter exclusion, thin walls and duplicate impacts. Test large XP awards, load without point replay and ordinary-versus-unique encounter reset. No generic Behavior Tree task library is required.

Connections to wire in this phase

AI intentions → EnemyBase movement/Combat; enemy death → GameInstance reward transaction → Profile → build/stat/UI changes.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Enemy bodies, decisions and rewards, XP and leveling, Combat, damage and action ownership.

Prerequisites

Combat, persistent transaction facade, and disk save/load from phases 2–4.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

Melee telegraphs are readable. Ranged shots cannot hit their owner or trigger duplicate impacts. Large XP awards cross several levels and grant each point award once. Load does not replay point grants. Ordinary enemies reset; completed unique enemies do not return or reward again.

Stop condition

Movement, melee/ranged threats, progression awards, persistent unique completion, and death/load recovery work together.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Behavior-tree task libraries, specialized navigation across platforms, enemy class hierarchies for simple stat variants, randomized loot.
