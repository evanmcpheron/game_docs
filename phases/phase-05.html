Phase 5 of 0–1113 new assets

Goal and why this phase comes now

Prove: Prove readable melee/ranged threats, once-only rewards and multi-level progression integrate with persistence.

Enemies now reuse proven combat and rewards can rely on a coherent persistent transaction/save path.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Implementation sequence

01. Initialize the enemy family

Create enemy base/controller shells, enum and enemy schema. Add shared components and damage adapter. Configure AI possession but wait for readiness and optional unique record suppression before thinking.

02. Prove melee decisions

Create DA_Enemy_MeleeTest and DA_Attack_EnemyMeleeTest. Use simple target/range/floor/wall decisions. Body applies cached movement every update; Combat owns telegraph and recovery.

03. Create ordered progression

Create S_LevelProgressionRow then DT_LevelProgression, author a few explicit cumulative thresholds and register the table. AwardXP processes every crossed threshold once, with bounded traversal.

04. Connect legitimate death rewards

EnemyBase sets its local guard before calling GI. Ordinary enemies grant once per live instance; unique encounters commit completion and reward coherently. Loaded completion suppresses without death/reward replay.

05. Stop for the first architecture slice

Use phases 0–4 plus melee/rewards/leveling: traverse two areas, take damage, earn XP/item, open shortcut, activate checkpoint, earn later reward, die, restart and verify everything. Do this before expanding enemy variety.

06. Add the ranged route

Create BP_ProjectileBase with native collision root and projectile movement. Add typed projectile fields/hook to existing attack schema now. Ranged child spawns once at active entry; it does not also run melee damage.

07. Finish Phase 5 proof

Test shooter exclusion, thin walls and duplicate impacts. Test large XP awards, load without point replay and ordinary-versus-unique encounter reset. No generic Behavior Tree task library is required.

Connections to wire in this phase

AI intentions → EnemyBase movement/Combat; enemy death → GameInstance reward transaction → Profile → build/stat/UI changes.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Enemy bodies, decisions and rewards, XP and leveling, Combat, damage and action ownership.

Prerequisites

Combat, persistent transaction facade, and disk save/load from phases 2–4.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

Melee telegraphs are readable. Ranged shots cannot hit their owner or trigger duplicate impacts. Large XP awards cross several levels and grant each point award once. Load does not replay point grants. Ordinary enemies reset; completed unique enemies do not return or reward again.

Stop condition

Movement, melee/ranged threats, progression awards, persistent unique completion, and death/load recovery work together.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Behavior-tree task libraries, specialized navigation across platforms, enemy class hierarchies for simple stat variants, randomized loot.
