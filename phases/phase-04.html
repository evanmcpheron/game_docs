Phase 4 of 0–119 new assets

Goal and why this phase comes now

Prove: Prove a fresh process restores coherent player/world progress without duplicate claims.

One persistent claim proves the disk contract before dozens of world objects can duplicate rewards or lose state.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Configure the new assets and required references

  1. Create/compile BPDA_ItemDefinition, E_ItemKind, S_ItemGrant, S_Reward, S_SaveHeader and BP_SaveGame. Configure DA_Item_TestReward with its documented TestReward ItemId and add it to DA_GameCatalog.Items. Use zero reward XP until Phase 5.
  2. Create BP_PickupBase from the documented parent. Add PersistentState and BPI_PersistentActor while retaining inherited interaction. Set ItemId, positive Quantity and authored PersistentId; this placement ID is not an inventory EntryId or definition ID.
  3. Configure WBP_SaveStatus with current GI as its source. The early screen needs actual Saved/Saving/Failed/dirty state, not a green indicator set when RequestSave was merely called.

Hook the feature into the existing game

  1. Connect Pickup.Interact → GI.TryClaimWorldReward. Validate unclaimed source and all item grants first; use one non-latent, non-reentrant operation to stage/commit Profile acquisition and WorldState.Collected with notifications deferred. Publish complete state and increment one persistent revision only after both agree.
  2. Wire standalone Profile/WorldState commits to the coordinator’s revision/save request path without double-counting GI-deferred transactions. Keep stacking in the single Profile implementation reused by TryAddItem/TryAddItems; the pickup does not edit InventoryEntries itself.
  3. Connect RequestSave → immutable BuildSnapshot → the documented one-writer queue. Run Async Save Game to Slot from the supported custom-event graph (RunSaveIO), not a Blueprint function with a latent node. Completion records the captured revision; an older write cannot mark newer state clean. SaveGame only contains Header/Character/World/Recovery values.
  4. Connect TryLoadProfile to validation of candidate generations before importing either model. Reject unsupported/corrupt data or use the documented valid generation fallback; distinguish missing from invalid saves. Reconstruct registered area and safe recovery through the existing bootstrap, never resume mid-attack or restore a saved Actor pointer.
  5. Suggested implementation detail, development-only fixture: add native buttons labeled Test Save, Test Load and Retry to the existing WBP_SaveStatus. Its request handlers forward to the supplied Controller/GI public RequestSave, TryLoadProfile and RetrySave operations; the widget does not build snapshots or mutate models. Create/bind this view even when a load fails and the session is not ready. No new Input Action, widget Blueprint or harness asset is needed; remove these temporary controls in Phase 10. During these UI tests, Controller shows the cursor and uses Game and UI input mode. A native Return to Gameplay button restores Game Only input, hides the cursor and clears held intent; recreate the temporary test panel on the next isolated test launch.
  6. Suggested implementation detail for a fresh-process load before menus: add a clearly labeled bDevelopmentLoadOnStart Boolean to the existing GI startup setup. Set it explicitly for the test before launch. The load branch calls TryLoadProfile before new-model initialization, discovery commits or automatic saves can overwrite the test snapshot; failure stays unready and displays the retry/error view, with no implicit New Game. The other branch is an explicitly selected new test session. Phase 10 replaces this test-only switch with real menu choices.
  7. Controller creates/retains WBP_SaveStatus, supplies GI, binds its completed save-state notifications, immediately pulls state and Add to Viewport. Ensure a failed save offers a real Retry or acknowledged-unsaved continuation rather than silently claiming success or waiting forever. Compile and Save All.

Connections established: the edits above must reach the current ready owner, not just a compiled shell. Update the test world

  1. Open L_Slice_A. Place BP_PickupBase within the working interaction range along the established route, outside the spawn/hazard and door blocker. In Details set ItemId=TestReward, Quantity=1 and a unique stable PersistentId such as the documented area/room/pickup naming pattern.
  2. Keep L_Slice_B’s reverse travel and existing persistent target fixtures. Confirm pickup query collision, PersistentState readiness, catalog reference and area/spawn IDs. Record the pre-test Profile/WorldState values and use isolated test save slots/user data, never the developer’s valuable saves.

Run the feature now

  1. PIE in SliceA: collect the pickup, request it again, travel away/back, and inspect one inventory grant plus one Collected record. Open/close the save view; underlying values must not depend on it.
  2. Click Test Save in the development WBP_SaveStatus controls and observe actual success for the intended revision. Set the explicit development startup selection to load, end the application session and launch a fresh Standalone/test process. Its startup load must validate before new-session writes. Compare entry identity/quantity, world records, checkpoint and safe recovery location; use Retry on a deliberate failure, not implicit New Game.
  3. Earn/claim a persistent change after activating a checkpoint, then die. Recovery retains the later change; it must not call disk load to roll back to checkpoint time.
  4. Resource disk recovery: equip/purchase only features currently available in this phase, save valid persistent progress, drain current mana/stamina, exit fully and load in a fresh process. Reconstruct Stats from saved progression and authored inputs, then start full final mana/stamina. Verify S_CharacterSave/BP_SaveGame contain no current-resource or final-stat fields and normal area travel still preserves rather than refills. Restore fixture inputs; repeat with invalid newer save generation to test existing fallback without resource-specific migrations.

Failure and rejection tests

  1. Attempt a claim with an unknown ItemId, invalid quantity or already-collected ID. Fail without either inventory or world mutation. Corrupt only an isolated test save generation and verify fallback/error, never implicit New Game.
  2. Request another persistent mutation while a save is in flight, then complete the older write. Dirty/newer state must remain pending. Exercise write failure, Retry and acknowledged-unsaved cancellation, including a pending travel/quit request.

Regression gates

  1. Repeat reduced-health normal travel, checkpoint death without rollback, one-time switch projection and Phase 2 combat in registered slices. Confirm loading does not replay pickup actions or duplicate model/UI subscriptions.

Intentionally staged or not connected yet

The shared item schema supports minimal acquisition now; immediate consumable use is Phase 6, equipment behavior/typed Appearance is Phase 7, timed effects are Phase 9. Do not add unavailable schema types early. XP rewards remain zero until the Phase 5 curve exists.

Full inventory widgets, final save slots UX and menus are later. Keep the development save/load entry route visibly temporary and do not treat static documentation checks as proof of serialization compatibility.

Do not invent save migrations for unreleased resource disk fields; none are added by this policy.

Integrated completion gate

Stop: do not advance if one required connection or integrated gate fails, even when all new assets compile. These are expected results to run, not a claim that this documentation audit executed Unreal. Full validation suite · Project checklists.

Implementation sequence

01. Add minimal item acquisition

Create E_ItemKind, S_ItemGrant, S_Reward and BPDA_ItemDefinition; compile the schema and make DA_Item_TestReward. Add only required item catalog entries. XP in rewards may remain zero until Phase 5 leveling.

02. Make the first atomic pickup

Create BP_PickupBase as a child of BP_InteractableBase. Place with authored PersistentId/ItemId/Quantity. GI validates complete reward and source, commits Profile plus Collected record with notifications deferred, then publishes one revision.

03. Build the disk snapshot

Create S_SaveHeader and BP_SaveGame fields Header/Character/World/Recovery. BuildSnapshot exports only value data from one committed revision. Save recovery identity rather than an airborne transform.

04. Implement the one-write queue

Add revision/in-flight/pending variables to GI. Wire a custom Event Graph save sequence to Async Save Game to Slot. Keep the snapshot referenced and immutable; completion records the captured revision and actual success result.

05. Add physical generations and load validation

Alternate Profile0_A/B, preserving last good data. Load sequential candidates and choose highest valid supported sequence. Missing saves differ from corrupt/unsupported saves; no automatic overwrite-as-NewGame fallback.

06. Display real save state

Create WBP_SaveStatus and bind GI status. Queued/Writing/Succeeded/Failed are different. Retry retains dirty progress and a blocked travel/quit sequence must have an explicit error decision rather than hang forever.

07. Run a fresh-process proof

Collect once, repeat request, die, revisit, save, exit and relaunch standalone/packaged test. Verify quantity/claim coherence, no award replay, changes while writing, failed completion and invalid latest-generation fallback.

Connections to wire in this phase

Profile + WorldState → immutable SaveGame snapshot → disk. Loaded snapshot → model import → phase-3 bootstrap. Pickup uses both Profile and WorldState atomically.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Disk saving, loading and death recovery, Persistent models and stable world identity.

Prerequisites

In-memory persistence already passes phase-3 tests; definition IDs and world IDs are stable.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

Collect once, trigger the pickup again, die, revisit, quit the application, and relaunch: quantity must remain correct and the pickup absent. Change state while a save is in flight and verify a later revision also saves. Exercise a failed write and an invalid latest generation. Verify loading does not re-grant pickups or checkpoint rewards.

Stop condition

A packaged or standalone restart restores meaningful character/world progression into a valid recovery state.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Large inventory UI, skill catalog, large world content, one-frame exact-state snapshots, migrations for speculative future features.
