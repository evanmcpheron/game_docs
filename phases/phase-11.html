Phase 11 of 0–112 new assets

Goal and why this phase comes now

Prove: Prove content, save recovery and lifecycle behavior in a fresh packaged executable before scaling.

All confirmed systems exist in a representative slice; now real packaging and bad-data/lifecycle tests can expose integration defects.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Configure the new assets and required references

  1. Create BP_ArchitectureTestHarness and L_SystemTests in their registered folders. Configure harness GameCatalog=DA_GameCatalog where the existing test contract requires it. The harness issues public commands and compares typed results; it does not own replacement gameplay state.
  2. Keep L_SystemTests a controlled system/model harness. Suggested implementation detail: use native GameModeBase for a no-player harness map where appropriate; never bypass BP_GameMode readiness and call that an integrated player/world test.
  3. Review packaging settings, actual map inclusion and soft-reference cooking for L_Frontend and both registered slices. Keep referenced Tests definitions/animation/executor fixtures included in the development cook. Do not exclude the whole Tests folder just because it is named Tests.

Hook the feature into the existing game

  1. Wire harness RunScenario to explicit initial values and public model/coordinator/component commands, with assertions for returned result plus authoritative values. Continue asynchronous scenarios from actual save-completion/area-readiness events, not fixed Delay guesses.
  2. Collect a controlled per-map manifest of PersistentIds, Area/Room/Spawn IDs and transition/switch targets from every authored slice, then compare the combined values. A scan of the currently loaded map cannot validate unloaded-map uniqueness. A documented combined manual log is acceptable; no production manifest manager is required.
  3. Exercise value-only schemas, compatibility generations, old callbacks and teardown through existing owners. Keep deterministic system assertions in L_SystemTests and run real spawn/possession/travel/UI/physics in registered slices or frontend.
  4. Package a Development executable to a separate output directory, inspect packaging logs and run from isolated test user data. Record build identifier, content/schema version, expected/observed result and date. Correct failures in their owning assets; do not weaken a test or add a replacement architecture.

Connections established: the edits above must reach the current ready owner, not just a compiled shell. Use each linked asset’s integration reference for the same component, interface, input and widget contract. Names newly proposed by this audit are labeled Suggested implementation detail; existing suggested field/function names retain that status. Editor/plugin behavior still requires validation in the installed project.

Update the test world

  1. Open L_SystemTests and place/configure BP_ArchitectureTestHarness once for controlled cases. No universal player playground or new map asset is needed.
  2. Open registered SliceA/B and review the retained movement course, dummy, hazard, checkpoint, shortcut, pickup, ordinary/unique enemies, equipment/consumables, ability receiver and NPC fixtures. Confirm stable IDs, definitions, collision, safe spawns and required-route reachability are still coherent.
  3. Open L_Frontend for the end-to-end launch/load path. Retain fixture labels and document which development content must eventually be replaced before a production cook; do not rename/move canonical Content folders to hide references.

Run the feature now

  1. Run deterministic harness assertions, then the complete first-vertical-slice acceptance in registered areas extended with inventory, equipment, both valid skill specializations, abilities/effects and dialogue. Repeat with relevant UI/presentation absent.
  2. Run the packaged executable in a fresh process: New Game, traverse A/B, mutate progress after checkpoint activation, die, save with actual completion, exit, relaunch and load. Compare persistent values/identities and clean recovery state, not an exact old animation or conversation frame.
  3. Repeat key movement/visual/action tests at documented frame rates and under coarse updates. Record observed failures separately from static documentation/build checks; a compiled Blueprint or successful cook alone is not integrated gameplay proof.

Failure and rejection tests

  1. Run isolated bad-data cases: duplicate IDs across maps, missing spawns/executor/definition, malformed skill/level graph, incompatible visual layout, corrupt/unsupported save and failed write. Expect actionable rejection/fallback without partial progress or indefinite blocking.
  2. Test stale body/action/session callbacks, repeated initialization/record application/death, missing widgets/notifies and teardown during accepted execution. No duplicate award, hidden gameplay authority or stale reference may remain.

Regression gates

  1. Use the full validation/checklist suites rather than copying every historic test onto every phase. Required gates include fluid movement, action/health integrity, coherent rewards, persistence/recovery, complete stat rebuilds, skill reachability, effects/recharge handoff and safe modal input.

Intentionally staged or not connected yet

This phase validates the committed game; it does not authorize new gameplay features or claim runtime success in advance. Stop expansion until actual integrated and packaged results are recorded. Production content remains separate from test fixtures.

Integrated completion gate

Stop: do not advance if one required connection or integrated gate fails, even when all new assets compile. These are expected results to run, not a claim that this documentation audit executed Unreal. Full validation suite · Project checklists.

Implementation sequence

01. Create the development harness/map

Create BP_ArchitectureTestHarness and L_SystemTests in Tests. Use public commands and read-only assertions. Scenario setup is explicit; diagnostic code does not become a production manager.

02. Run data validators

Check definitions, row ordering, skill graph/exclusions, equipped entry references and animation compatibility. Each failure prints stable ID, expected condition, actual value and relevant area/version.

03. Combine all-map manifests

Load every authored test area in a controlled pass, report persistent/spawn/target IDs and compare the combined results. State whether this combination is manual or automated; do not pretend one loaded-map scan covers everything.

04. Keep compatibility fixtures

Retain supported schema/content save fixtures and test migration/fallback, unknown IDs, write failure and unsupported versions. Never destroy real user saves during development tests.

05. Package the actual slice

Include maps and soft-referenced fixtures required by current catalog. Use a clean test data location, fully exit/relaunch and run the complete acceptance sequence. Do not exclude Tests while production-config assets still depend on its fixtures.

06. Repeat lifecycle regressions

Repeatedly travel, respawn, open/close widgets and cancel abilities. Look for duplicate callbacks, stale references, growing memory and altered movement at frame-rate targets.

07. Scale only after proof

Record actual test results before authoring large content. Replace fixtures through data references when production content is approved; preserve canonical folder assignments. No speculative C++/streaming rewrite is part of this gate.

Connections to wire in this phase

Validation checks the existing architecture; it must not become a second implementation of gameplay rules.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Validation and packaged proof, Disk saving, loading and death recovery.

Prerequisites

All earlier phases and a stable representative content slice.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

Repeat the end-to-end suite in Part AB, test two supported save generations, and exercise deliberate bad data. Check frame-rate-sensitive movement/hits, increasing memory after travel, duplicated UI callbacks, and stale Actor references after unload.

Stop condition

A packaged build reconstructs valid player/world state reliably, reports actionable errors, and passes regression fixtures before larger content production.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Speculative optimization, blanket conversion to C++, multiplayer assumptions, or uncommitted game systems.

Exercise missing/interrupting notifies, stale callbacks, equipment changes and travel. Website checks below do not establish plugin compatibility or runtime success.
