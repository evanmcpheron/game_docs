Phase 6 of 0–113 new assets

Goal and why this phase comes now

Prove: Prove owned-entry and consumable operations work independently of the inventory screen.

Acquisition and disk identity already work, so stacking/removal/use can be expanded without widget-owned state.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Configure the new assets and required references

  1. Configure DA_Item_TestConsumable with ItemId TestConsumable, Kind Consumable, legal StackLimit and the documented ImmediateHealAmount (initial 25). Add it to DA_GameCatalog.Items. Keep TimedEffectId empty; no StatusEffects component exists yet.
  2. Build WBP_Inventory with native UMG list/text/button controls; no extra custom row Blueprint is required. Store selection as EntryId, not a copied authoritative entry. Configure a Close button that works through the actual chosen focus/pause route before full IMC_UI arrives.
  3. Open IMC_Player and map IA_Inventory (suggested I). In Controller, Started calls OpenInventory after validating session sources. Clear gameplay intent, create/retain the widget with Owning Player=self, bind Profile then pull GetInventoryView, Add to Viewport and set focus.

Hook the feature into the existing game

  1. Keep one TryAddItems stacking implementation: stage local values, fill partial stacks, split remainder and create each new Guid once; write changed structs back into the array. TryAddItem delegates rather than duplicating rules. TryRemoveItem revalidates exact ownership/quantity/equipped references.
  2. Suggested early-screen input setup: use Set Input Mode Game and UI with the inventory widget focused, show the mouse cursor for its native buttons, and block gameplay requests through the existing Controller modal guard. Retain the documented pause policy. Close restores game input/focus/cursor and clears cached requests; it does not depend on the Phase 10 UI Input Actions existing yet.
  3. Wire the inventory Use button → Controller.RequestUseItem(SelectedEntryId) → GI.TryUseItem(EntryId, CurrentBody). GI asks Profile.CanUseItem and validates the live Health target/benefit before any mutation. A pure healing item at full health is rejected under the suggested baseline.
  4. Inside the existing coordinator’s non-reentrant, non-latent transaction, commit the staged quantity decrement and prevalidated Health heal with publication deferred; then publish coherent inventory/health change and one persistent revision/save request. Do not consume first and wait for an animation, asset load or future effect component.
  5. Unbind exact widget subscriptions on Close/replacement; Controller reconnects to the newly ready body after travel/recovery. Inventory is still Profile-owned when the window is absent. Compile existing owners and Save All.

Connections established: the edits above must reach the current ready owner, not just a compiled shell. Editor/plugin behavior still requires validation in the installed project.

Update the test world

  1. Open SliceA and preserve the original persistent pickup and combat route. Place additional BP_PickupBase fixtures for TestConsumable with positive quantities and distinct stable IDs; use quantities that exercise a partial stack plus remainder (the documented 8 + 5 at limit 10 case).
  2. Keep a hazard reachable to reduce health deliberately, outside pickup/spawn overlaps. Record starting entries/quantities and use an explicit new isolated test Profile when repeating one-time pickup scenarios; never regenerate placement IDs to reset a test.

Run the feature now

  1. PIE: acquire the consumables, open inventory using the mapped control and confirm the first rendered snapshot. Take damage, select the exact EntryId and use once. Observe one quantity decrement, bounded Health restoration and the correct returned result.
  2. Close/destroy the inventory view and invoke the same public use/acquisition commands from the development test route. Reopen the view and compare current values immediately. Travel, die and save/relaunch; owned entry identities and committed quantities persist.

Failure and rejection tests

  1. Test full-health use, missing/dead body, unknown definition, removed/stale selection, invalid amount and repeated clicks. A rejected request changes neither quantity nor Health. Exercise partial/full stacks and splitting, not just one item in an empty inventory.

Regression gates

  1. Re-run atomic one-time pickup, save revision/failure, checkpoint-no-rollback and damage acceptance. Verify opening/closing the screen clears held movement/jump and restores a usable gameplay input route.
  2. Existing item modifiers recognize the four new stat IDs; no resource-consumable category or instant-restoration effect schema is added. Inventory ownership/consumption transactions remain unchanged.

Intentionally staged or not connected yet

No equipment operation or visible wearable layer is required until Phase 7. Timed effects and buff consumables wait until Phase 9. No crafting, merchant, drag-and-drop framework, rarity, economy or new inventory component is added.

Integrated completion gate

Stop: do not advance if one required connection or integrated gate fails, even when all new assets compile. These are expected results to run, not a claim that this documentation audit executed Unreal. Full validation suite · Project checklists.

Implementation sequence

01. Complete Profile operations

Implement staged stacking, exact EntryId lookup, removal validation and no direct removal of equipped entries. Use internal helpers for deferred commit notifications where GI coordinates runtime consumption.

02. Create the healing fixture

Create DA_Item_TestConsumable using the existing item schema; suggested ImmediateHealAmount=25 and no timed effect. Grant it through the real acquisition path. Final item balance is not decided.

03. Coordinate use

Controller supplies selected EntryId and current body to GI.TryUseItem. Profile validates ownership, Health validates benefit, then quantity and healing commit synchronously before events/save. A rejected use consumes nothing.

04. Create the view

Create WBP_Inventory and IA_Inventory; use native UMG list/layout controls and selected EntryId. Bind Profile inventory changes, pull initial view and route use requests back to owners.

05. Test boundaries

Test partial/full stacks, duplicate equipment identities, unknown IDs, nonpositive quantities, empty inventory, missing body, full-health policy and repeated clicks. Destroy/reopen the widget and repeat after load.

Connections to wire in this phase

WBP_Inventory (UserWidget) → Profile requests; consumption coordinates Profile and the live Health component; inventory events refresh UI and saving.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: Inventory and consumables, UI, input modes and observation.

Prerequisites

Phase 4 acquisition/save semantics and phase 5 persistent progression.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

Partial/full stacks, invalid IDs, nonpositive quantities, empty inventory, no target body, using an item at full health under the selected validation policy, and repeated clicks. A rejected use consumes nothing; a successful use consumes once and restores health once.

Stop condition

Owned-item operations remain correct with the inventory screen open, closed, destroyed, and after disk loading.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Crafting, shops, currencies, rarity, durability, randomized attributes, drag-and-drop polish.
