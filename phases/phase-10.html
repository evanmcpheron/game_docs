Phase 10 of 0–1116 new assets

Goal and why this phase comes now

Prove: Prove condition-sensitive NPC conversations and a complete front-end/menu lifecycle.

Dialogue conditions can query working progression/world state, and menus can request tested save/recovery operations.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Configure the new assets and required references

  1. Create/compile E_ConditionKind, S_Condition, S_DialogueLine and S_DialogueVariant before BPDA_DialogueDefinition and DA_Dialogue_TestNPC. Author obvious FirstVisit and Repeat test variants, nonempty lines and explicit CompletionFlags; labels/text are fixtures, not final lore.
  2. Create BP_NPCBase directly from Actor, add its native visual/query Trigger and BPI_Interactable, and assign NPCId plus DialogueDefinition=DA_Dialogue_TestNPC. A local PersistentState is optional only when local NPC presentation projects a world record; global completion flags alone do not require it.
  3. Create BP_MenuGameMode, keep Default Pawn Class=None and use BP_PlayerController. Create L_Frontend with that GameMode, not gameplay BP_GameMode/AreaRoot bootstrap. Configure the intended Game Default Map to L_Frontend when menu launch is ready.
  4. Create IMC_UI and map IA_UIConfirm/IA_UICancel (suggested Enter/Escape). Map IA_Pause in IMC_Player. Choose and validate one concrete modal route: suggested Game and UI input mode with appropriate UI context priority, focused controls and trigger-while-paused settings for Controller-handled UI actions. Do not assume UI Only delivers Controller Enhanced Input callbacks.

Hook the feature into the existing game

  1. NPC.GetInteractionInfo evaluates eligibility without mutations; Interact requests Controller.BeginDialogue with NPCId/definition. Controller selects the highest-priority eligible variant using the documented stable tie break, initializes its transient cursor, clears gameplay intent, pauses simulation and displays the first line.
  2. Wire confirm to one Controller.AdvanceDialogue; only authored final completion requests GI.CommitWorldFlags. Cancel, widget destruction, travel and teardown close without completion flags. WorldState owns memory; neither NPC nor widget persists a duplicate cursor.
  3. Controller creates/retains WBP_Dialogue, WBP_PauseMenu and WBP_MainMenu as needed, binds current typed sources then pulls snapshots, Add to Viewport and focus. Unbind/remove the old screen before replacement and restore input mode/context/focus before accepting gameplay again.
  4. Frontend InitializeFrontend registers Controller once and requests MainMenu without a player. New Game and Load buttons call existing GI operations explicitly. Invalid/unsupported save is an error choice, not an automatic new Profile. Pause Save/Retry/quit commands observe actual completion and failure policy.
  5. On entering/leaving modal screens or swapping worlds clear cached gameplay intent and cancel/close transient interactions as required. Ensure one Escape cannot trigger both a stale Pause-open and UI-cancel action; remove/block the gameplay context while modal or guard its handler consistently.
  6. Replace the Phase 4 temporary WBP_SaveStatus Test Save/Test Load controls and GI development startup switch with these real menu commands. Keep actual save/recovery/interaction transactions unchanged; retain legitimate save-status/Retry feedback. Compile all modified Controllers/Actors/widgets, save the frontend and slices.

Connections established: the edits above must reach the current ready owner, not just a compiled shell. Update the test world

  1. Open L_Slice_A and place BP_NPCBase on reachable clear floor outside combat/hazard/transition triggers. In Details set a stable authored NPCId and DA_Dialogue_TestNPC; configure its query-only interaction Trigger. Keep enemies distinct from NPCs.
  2. Open L_Frontend and confirm BP_MenuGameMode, no auto-possessed player and no AreaRoot/spawn registry requirement. Keep registered SliceA/B as gameplay destinations through the existing catalog; frontend is not a new gameplay area.
  3. Preserve existing slice fixtures and reverse travel so the NPC can be revisited after progression, completion and reload. Do not add final narrative, formal quests, factions, morality or reputation.

Run the feature now

  1. Start from L_Frontend: explicitly New Game or Load, reach the registered slice, move next to the NPC and press interaction. Read first-visit lines, advance once per confirm, complete the authored last line, then reopen and observe the repeat variant.
  2. Cancel before completion and verify no completion flag. Change a supported level/world condition through its real gameplay operation and reopen. Save/relaunch and confirm remembered facts restore without a mid-conversation cursor.
  3. Open/close pause, inventory, equipment and skills while holding movement/jump; verify paused confirm/cancel works, focus returns, stale movement does not replay and gameplay resumes. Exercise save failure and an explicit Retry or acknowledged-unsaved quit.
  4. Pause resource test: in a registered slice spend from50/100 under original5/15 rates, open a menu that uses global game pause, record snapshot/game time, wait and use confirm/cancel while paused. Pools and game time stay fixed; after resume regeneration advances only by gameplay time and no held ability/movement press replays. For a deliberately nonpausing modal, resources continue according to that existing policy. Close/reopen UI and travel/replace the body: one current source set, no stale callbacks. Restore full pools and repeat.

Failure and rejection tests

  1. Test missing/empty/no-eligible dialogue, duplicate confirm, invalid save, canceled conversation and old widget callbacks after travel. No failure commits memory, starts an unintended new session or leaves simulation/input permanently blocked.
  2. Confirm menus remain usable with no CurrentBody in the frontend and after body teardown. Hidden HUD/views must not be required to make save, load, dialogue completion or other gameplay rules correct.

Regression gates

  1. Repeat registered spawn, combat/ability interruption, persistent reward/equipment/skill reconstruction and reduced-health travel after modal closure. Confirm only one current screen subscription and one player remain after repeated frontend → gameplay cycles.

Intentionally staged or not connected yet

Only the documented condition vocabulary is supported. No quest/reputation/faction/narrative framework is added. Test NPC dialogue remains temporary content; full production story, art and text are not established by this phase.

Integrated completion gate

Stop: do not advance if one required connection or integrated gate fails, even when all new assets compile. These are expected results to run, not a claim that this documentation audit executed Unreal. Full validation suite · Project checklists.

Implementation sequence

01. Create dialogue leaf data first

Create E_ConditionKind, S_Condition and S_DialogueLine before S_DialogueVariant. Compile BPDA_DialogueDefinition and create DA_Dialogue_TestNPC with first/repeat fixture variants.

02. Implement stationary NPC interaction

Create BP_NPCBase directly from Actor, add visual/interaction region and implement BPI_Interactable. Do not inherit enemy AI. Controller selects the eligible highest-priority variant from model queries.

03. Keep cursor transient

Implement BeginDialogue/AdvanceDialogue/CloseModalScreen on Controller. Commit completion flags only at authored final completion, not cancel or widget destruction. Modal pause must preserve a working confirm/cancel input route.

04. Finish the menu map

Create BP_MenuGameMode, WBP_MainMenu, WBP_PauseMenu, WBP_Dialogue and L_Frontend. Front-end override has Default Pawn=None and no gameplay AreaRoot bootstrap.

05. Wire real I/O requests

NewGame/Load/Retry/save-before-quit go through GI. Input Actions Pause/UIConfirm/UICancel and IMC_UI control the selected focus route. Reject or report unsupported saves rather than silently resetting.

06. Run the whole user-facing loop

From fresh executable front end, start/load, interact, pause/resume, cancel/complete dialogue, change world conditions, save and return/quit. Test held inputs, focus restoration and pending/failed writes.

Connections to wire in this phase

NPC → Controller dialogue session → condition evaluation against models; completion → WorldState transaction. Widgets → requests; model/component events → widgets.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: NPCs and conditional dialogue, UI, input modes and observation, Input intent and routing.

Prerequisites

Interaction, world flags, progression queries, save lifecycle, and gameplay locks.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

First/repeated conversations, changed world/level conditions, interrupted conversation, unloaded/reloaded NPC, pause/resume, held input during screen changes, fresh-start load, and quit while a save is pending. Unsupported save versions do not silently become New Game.

Stop condition

The full confirmed system set can be exercised from a front end through gameplay and back without special editor-only setup.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Formal quests, factions, reputation, morality, merchants, procedural narrative, UI features unrelated to confirmed mechanics.

Source and follow-through

This page follows the current asset manifest and preserves the gameplay phase intent from Part AA of the original roadmap. The PaperZD decision updates animation assets, character bases and creation order; finer recipes remain suggested implementation detail. Open the full asset index when an unfamiliar name appears; use troubleshooting when the observed result differs.

Choose the NPC render integration

Keep the stationary BP_NPCBase Actor. Animated NPCs use the native PaperZD Animation component linked to their Sprite and a source-compatible AnimInstanceClass. The static dialogue fixture needs no unapproved talking/emote state catalog. Use PaperZDCharacter only when native character movement is needed; animation never controls conversation completion or modal unlock.
