Phase 10 of 0–1116 new assets

Goal and why this phase comes now

Prove: Prove condition-sensitive NPC conversations and a complete front-end/menu lifecycle.

Dialogue conditions can query working progression/world state, and menus can request tested save/recovery operations.

Recommended asset-creation order

Create every listed asset in its exact folder. For classes/components, the first pass creates and compiles shells; fill cross-referencing variables/graphs after their types exist. This avoids a circular “create A before B before A” problem without changing the architecture. A data instance requires its compiled schema; a child Blueprint requires its compiled parent. Creating a shell does not implement later-phase mechanics.

Implementation sequence

01. Create dialogue leaf data first

Create E_ConditionKind, S_Condition and S_DialogueLine before S_DialogueVariant. Compile BPDA_DialogueDefinition and create DA_Dialogue_TestNPC with first/repeat fixture variants.

02. Implement stationary NPC interaction

Create BP_NPCBase directly from Actor, add visual/interaction region and implement BPI_Interactable. Do not inherit enemy AI. Controller selects the eligible highest-priority variant from model queries.

03. Keep cursor transient

Implement BeginDialogue/AdvanceDialogue/CloseModalScreen on Controller. Commit completion flags only at authored final completion, not cancel or widget destruction. Modal pause must preserve a working confirm/cancel input route.

04. Finish the menu map

Create BP_MenuGameMode, WBP_MainMenu, WBP_PauseMenu, WBP_Dialogue and L_Frontend. Front-end override has Default Pawn=None and no gameplay AreaRoot bootstrap.

05. Wire real I/O requests

NewGame/Load/Retry/save-before-quit go through GI. Input Actions Pause/UIConfirm/UICancel and IMC_UI control the selected focus route. Reject or report unsupported saves rather than silently resetting.

06. Run the whole user-facing loop

From fresh executable front end, start/load, interact, pause/resume, cancel/complete dialogue, change world conditions, save and return/quit. Test held inputs, focus restoration and pending/failed writes.

Connections to wire in this phase

NPC → Controller dialogue session → condition evaluation against models; completion → WorldState transaction. Widgets → requests; model/component events → widgets.

Read the APIs on each asset page for the caller, explicit inputs/outputs and allowed state changes. The linked system chapters give the end-to-end call flow: NPCs and conditional dialogue, UI, input modes and observation, Input intent and routing.

Prerequisites

Interaction, world flags, progression queries, save lifecycle, and gameplay locks.

Future typed dependencies shown on an asset reference page are staged extensions, not a requirement to implement later phases now.

Run the phase tests

First/repeated conversations, changed world/level conditions, interrupted conversation, unloaded/reloaded NPC, pause/resume, held input during screen changes, fresh-start load, and quit while a save is pending. Unsupported save versions do not silently become New Game.

Stop condition

The full confirmed system set can be exercised from a front end through gameplay and back without special editor-only setup.

Do not move on with an unexplained failure

A checked box should mean you ran the test in your project. Website audit results are not Blueprint test results. Record the actual expected/observed value, current phase, engine build and relevant stable ID/token.

Do not build yet

Formal quests, factions, reputation, morality, merchants, procedural narrative, UI features unrelated to confirmed mechanics.

Source and follow-through

This page follows the current asset manifest and preserves the gameplay phase intent from Part AA of the original roadmap. The PaperZD decision updates animation assets, character bases and creation order; finer recipes remain suggested implementation detail. Open the full asset index when an unfamiliar name appears; use troubleshooting when the observed result differs.

Choose the NPC render integration

Keep the stationary BP_NPCBase Actor. Animated NPCs use the native PaperZD Animation component linked to their Sprite and a source-compatible AnimInstanceClass. The static dialogue fixture needs no unapproved talking/emote state catalog. Use PaperZDCharacter only when native character movement is needed; animation never controls conversation completion or modal unlock.
