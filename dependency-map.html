The system dependency route

Canonical roadmap reference · PART AC — System dependency graph

Current guidance retains gameplay policy and incorporates the PaperZD architecture decision. Historical source text remains in the unchanged original roadmap. E-number references belong to the original roadmap; see verification notes.

Presentation grows alongside these phases, rather than blocking their rules. Basic animation starts with movement; equipment layers arrive with equipment; UI follows working model operations.

Forbidden direct dependencies: a skill widget must not be required by Profile; Health must not choose a checkpoint; an item definition must not depend on the player Actor; Stats must not mutate inventory; an enemy must not know the inventory widget; a switch must not require a reference to an unloaded door Actor; SaveGame must not be the live simulation owner; Profile and WorldState must not invoke each other to complete cross-model transactions.

Type creation is not gameplay initialization

Two Blueprint classes can need references to one another. Create and compile blank class shells first, then add the typed fields. Runtime initialization still injects only the relationships the owner needs and waits for explicit readiness. A compile-time reference does not justify a circular persistent ownership design.

Phase 0 GameInstance exists before Phase 3 Profile/WorldState types; add those fields later. Composite structs require their current leaf types first. Data Asset instances require compiled schema classes; child Blueprints require compiled parent classes. The phase tables show an actual creation order that respects those distinctions.

Common dependency questions

QuestionAnswer / entry point
What must exist before Profile’s typed fields?Compile BP_PlayerProfile shell, BPDA_GameCatalog and the Phase 3 value types: S_InventoryEntry, E_EquipmentSlot and S_CharacterSave. Inventory/equipment/skill logic still arrives in its specified later phases.
What reads the item definition?Profile inventory/equipment/use validation, GI rewards, the body build/visual adapter and relevant UI. Open BPDA_ItemDefinition for direct consumers and its stable-ID contract.
What depends on Health?Damageable bodies, HUD, accepted-damage/death adapters and runtime consumption/recovery. Health itself must not depend on checkpoint maps or inventory UI.
What changes when S_InventoryEntry changes?Profile fields/APIs, S_CharacterSave, equipment Guid validation, inventory/equipment UI and save migration tests. Trace direct consumers, then their consumers; old save compatibility must be tested.
When is WBP_Equipment safe to build?Phase 7, after acquisition/entry identity, removal rules and stat rebuilding exist. The view follows model validation rather than implementing it.

Read the phase labels

A later-phase dependency on an asset page is an extension to add later, not a request to create the entire architecture on day one. This table is documentation-derived relationship guidance, not an exported Unreal Reference Viewer graph.

Incremental integration and test-world workflow

CREATE → COMPILE → CONFIGURE → INTEGRATE → EDIT TEST WORLD → RUN → VERIFY → CONTINUE. A phase is complete only after its new runtime feature reaches the real consumer and passes a playable or controlled system scenario. Use development test environments for map roles, stable fixture identity and bootstrap boundaries.

Dependency edges include assigned component classes, interfaces, data instances, input actions and created widgets. The per-phase activation/assignment tables distinguish compile/type dependencies from runtime use. A later-phase dependency in a complete asset reference does not require adding it while compiling an earlier shell.
