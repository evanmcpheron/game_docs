Open the manual, then open the project

Extract the whole Blueprint_RPG_Development_Guide directory and open index.html in a desktop browser. Keep the HTML pages, site folder and asset folders together so relative links remain valid. The guide is not an Unreal project, and opening it does not create Blueprint assets or compile graphs. You will build the registered assets in your existing project.

Use Phase 0 as your first working session. Do not create all 149 assets on day one. In each phase create leaf enums/structures, compiled class/interface shells, then dependent fields/instances; implement a small path, test it and only then expand.

Check the actual Editor before changing settings

  1. Make a source-control commit or backup of the existing project. Preserve Content/Game and its existing folders exactly.
  2. Check the installed Unreal version in the Editor’s version/about display and record it. This guide targets the requested 5.8.3; official mechanism pages retrieved for this manual identify the 5.8 documentation family. Hotfix-specific menus and runtime behavior remain installation checks.
  3. Verify Paper2D and Enhanced Input in the plugin/project configuration. Restart only if the Editor requests it. No PaperZD, GAS or custom subsystem is required for the baseline.
  4. Open Project Settings → Maps & Modes. Configure BP_GameInstance as Game Instance Class and BP_GameMode as gameplay GameMode after those shells are compiled. Configure BP_PlayerController inside GameMode.
  5. For the Phase 0 lab use Default Pawn Class=BP_PlayerCharacter with one native PlayerStart. At Phase 3 replace this with Default Pawn Class=None and manual readiness-based spawning.
  6. Save L_MovementLab under Content/Game/Tests and use it as the initial Editor/startup lab map. L_Frontend becomes the user-facing starting map in Phase 10. World Settings may override a map’s GameMode, so verify both project and map settings when spawning is wrong.

A repeatable Blueprint work session

  1. Open the current asset page. Read Identity, Purpose and “must not own” before adding nodes.
  2. Create the current-phase fields with their types/containers. Compile/save the referenced enum/struct/schema first. For two classes that refer to each other, compile empty shells for both before adding typed fields; that does not mean both must execute gameplay yet.
  3. Create a small named custom function, select its inputs/outputs and add the validation branch first. A false result should leave state unchanged.
  4. Add the permitted mutation, then the completed-change dispatcher. In a cross-model operation defer those dispatchers until the full commit is complete.
  5. Use graph comments, function categories and local variables for staged struct changes. Prefer a pure query for a read-only value; do not hide mutation behind something presented as a query.
  6. Place the described fixtures, select the correct debug instance in the Blueprint debugger and inspect pins/watch values. Use Print String for contextual development logs and breakpoints to find the first wrong owner/value.
  7. Run the page’s success and failure tests. Save/commit a known-good checkpoint in source control before the next phase.

Reading pseudo-flow correctly

Arrows describe responsibilities and calls, not a promise that every named box is a built-in node. Launch Character, Add Movement Input, Construct Object from Class, Spawn Actor from Class, Possess and Async Save Game to Slot are engine mechanisms. TryClaimWorldReward, RefreshBuildFromProfile and TryConsumeJumpRequest are custom functions you create. Event Dispatchers must also be created with agreed signatures.

Latent or asynchronous work belongs in appropriate Actor/GameInstance Event Graph orchestration, not inside a synchronous model transaction. A normal Blueprint function returns outputs now; a later completion callback is not that return value.

Keep proof notes

Record test values, observed results and your installed build version. The checklist controls can remember progress when your browser permits local-file storage, but browser behavior and moved folders may affect that storage. Export the progress JSON from the Checklist page as a portable backup; import restores only this manual’s checkbox states. It does not read or modify Unreal saves.
