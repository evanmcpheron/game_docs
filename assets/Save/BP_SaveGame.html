Purpose and boundaries

Its job: The serializable snapshot accepted by Unreal save/load nodes.

Why this exists separately: A fresh passive snapshot isolates a committed revision from gameplay changes that occur while disk writing is still active. Live gameplay keeps using Profile and WorldState.

What it must NOT own or do

Do not make this the live inventory object, add Actor/timer/animation references, or mutate a snapshot while a write is in flight.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Save/. Save the asset with the exact name BP_SaveGame. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click empty space → Blueprint Class → All Classes if necessary → search SaveGame. Select that native parent, not a similarly named project class.
  3. Compile the shell, save it, then add current-phase variables/functions and component instances listed below. If a referenced project class does not exist yet, compile both shells before adding cross-references. Add later-phase features only when their phase arrives. Runtime instances are created with engine Create Save Game Object. No Actor components, BeginPlay or gameplay Tick belong here.

Components and composition

No additional manually added gameplay component is required for this framework/Object/snapshot asset. Native inherited framework behavior remains; plain Object/GameInstance/SaveGame models are not Actors to which you attach Actor Components.

When and where to connect this asset

Value snapshot container. GI BuildSnapshot constructs the supported Header/Character/World/Recovery values and sends an immutable instance to the one-writer save queue. TryLoadProfile validates candidate generations before replacing both models. Do not store actor/component/UI references or a live authoritative model here.

Creation phase: Phase 4. World setup · Run-now proof · Which test map to use.

Only the current phase’s connections are active. The full reference/dependency list can include later schema extensions; it is not an instruction to add them early. Suggested properties/graph calls are implementation guidance, not verified existing game fields. Compile/configure the real consumer, save its world fixture, and record the linked scenario’s observed result before marking this asset done.

Functions and request contracts

No gameplay functions, BeginPlay or custom dispatchers are required. GameInstance creates, fills, validates and writes the snapshot. Keep the object passive and immutable while writing.

Events, dispatchers and observers

No additional custom dispatcher is required for this asset’s first version. Use the referenced model/component events or native lifecycle/input/collision events when relevant. Do not invent a global event bus merely to broadcast every local call.

On reinitialization, remove the old subscription before binding the new source, then pull current values. On EndPlay or widget teardown, remove the exact subscription and clear old world references. The command must remain correct with no presentation listener.

Interfaces and delegation

No required implemented Blueprint Interface beyond an explicitly inherited contract or a future conditional use described in the source. Owned component/model relationships normally use direct typed references, not a new interface for every call.

Concrete tests

Debug output pattern: [BP_SaveGame] Case=<name> Id=<stable ID or token> Expected=<value> Actual=<value> Result=PASS/FAIL. Include revision/area where relevant; output is a diagnostic, not a substitute for comparing typed values.

Common mistakes

Do not make this the live inventory object, add Actor/timer/animation references, or mutate a snapshot while a write is in flight.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.

Definition of done

Continue with the Phase 4 checklist and Disk saving, loading and death recovery. Canonical identity comes from the original placement index and phase register; detailed contracts/fields labeled suggested are the expansion, not a claim of engine execution.
