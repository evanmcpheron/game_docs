Purpose and boundaries

Its job: Content asset; use temporary artwork you own, then replace it without changing gameplay.

Why this exists separately: This is authored visual content consumed by Paper2D presentation, separate from collision, gameplay permission and saved progress. It is deliberately temporary test art.

What it must NOT own or do

Do not make a sprite silhouette or flipbook completion authoritative for collision, jumping, attacks or rewards. Do not claim the manual supplies final artwork.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Art/. Save the asset with the exact name T_TestHelmet. The folder already exists; do not move the asset into a different generic folder.
  2. Use Import in the exact Art folder with temporary artwork you own. Rename the resulting Texture2D asset to the registered name through the Content Browser.
  3. Inspect transparency/canvas dimensions and choose sampling appropriate to the test art. Body/equipment must share a compatible layout. This documentation contains no final art or required external download.

Authoring boundary

The exact registered asset is required, but the final artwork is not supplied or chosen here. Use a small image you own, the same frame layout and deliberate scale/pivot conventions. A static placeholder can prove the asset/render route. High-quality final animation frames remain an art-authoring task; do not create new traversal gameplay merely because a future visual state is possible.

Functions and request contracts

No executable gameplay API belongs on this authored content/value asset. Use its field/value editor and the linked consuming system. Schema classes need editable fields, not player-state mutation or world timers.

Events, dispatchers and observers

No additional custom dispatcher is required for this asset’s first version. Use the referenced model/component events or native lifecycle/input/collision events when relevant. Do not invent a global event bus merely to broadcast every local call.

Interfaces and delegation

No required implemented Blueprint Interface beyond an explicitly inherited contract or a future conditional use described in the source. Owned component/model relationships normally use direct typed references, not a new interface for every call.

Common mistakes

Do not make a sprite silhouette or flipbook completion authoritative for collision, jumping, attacks or rewards. Do not claim the manual supplies final artwork.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
