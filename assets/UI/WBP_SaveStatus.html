Purpose and boundaries

Its job: Displays saving, success, and failure state.

Why this exists separately: Displays saving, success, and failure state. Keeping it as a view allows screens to open/close independently of lasting progress and body simulation.

What it must NOT own or do

Do not own authoritative inventory/health/skills/save state, duplicate validation rules or require a widget listener for a transaction to finish.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/UI/. Save the asset with the exact name WBP_SaveStatus. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click → User Interface → Widget Blueprint → choose UserWidget as parent. In Designer add simple native panels/text/buttons/bars appropriate to the view.
  3. Compile/save, then let PlayerController create the screen with Create Widget, supply typed references, bind once and immediately pull a snapshot. SkillTree may create SkillNode children. Wire buttons to requests, never direct inventory/skill-array edits.

Components and composition

Use a UMG Designer widget tree, not Actor Components. The separate Designer section lists native controls and screen ownership. A widget owns no Health/Inventory component substitute.

Designer tree and screen ownership

Status Text, optional activity indicator, and Retry button when failed. Display the coordinator’s completed result; a local spinner has no save authority.

Native Designer controls: UTextBlock ↗ · UButton ↗.

PlayerController owns the screen-root reference and creates/removes it; the tree owns its node children. Supply sources through initialization or appropriate exposed creation parameters. For Phase 6–9 screens, native focused UMG controls can handle Close before the Phase 10 IMC_UI exists; do not pull later input assets forward just to display inventory.

Events, dispatchers and observers

Observed sources: GameInstance.OnSaveStatusChanged.

No additional widget-owned gameplay dispatcher is required in the first implementation. Native button click events request the indicated operations. Bind/unbind on screen and source lifecycle; do not let a view become the event owner of inventory or purchases.

On reinitialization, remove the old subscription before binding the new source, then pull current values. On EndPlay or widget teardown, remove the exact subscription and clear old world references. The command must remain correct with no presentation listener.

Interfaces and delegation

No required implemented Blueprint Interface beyond an explicitly inherited contract or a future conditional use described in the source. Owned component/model relationships normally use direct typed references, not a new interface for every call.

Common mistakes

Do not own authoritative inventory/health/skills/save state, duplicate validation rules or require a widget listener for a transaction to finish.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
