Purpose and boundaries

Its job: Displays health, prompt, progression, and later ability panels.

Why this exists separately: Displays health, prompt, progression, and later ability panels. Keeping it as a view allows screens to open/close independently of lasting progress and body simulation.

What it must NOT own or do

Do not own authoritative inventory/health/skills/save state, duplicate validation rules or require a widget listener for a transaction to finish.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/UI/. Save the asset with the exact name WBP_HUD. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click → User Interface → Widget Blueprint → choose UserWidget as parent. In Designer add simple native panels/text/buttons/bars appropriate to the view.
  3. Compile/save, then let PlayerController create the screen with Create Widget, supply typed references, bind once and immediately pull a snapshot. SkillTree may create SkillNode children. Wire buttons to requests, never direct inventory/skill-array edits.

Components and composition

Use a UMG Designer widget tree, not Actor Components. The separate Designer section lists native controls and screen ownership. A widget owns no Health/Inventory component substitute.

Designer tree and screen ownership

A root overlay/panel, Health progress bar plus numeric text, interaction prompt text, and later level/ability display regions. No full-screen focus grab or pause for the HUD.

Native Designer controls: UTextBlock ↗ · UProgressBar ↗.

PlayerController owns the screen-root reference and creates/removes it; the tree owns its node children. Supply sources through initialization or appropriate exposed creation parameters. For Phase 6–9 screens, native focused UMG controls can handle Close before the Phase 10 IMC_UI exists; do not pull later input assets forward just to display inventory.

Events, dispatchers and observers

Observed sources: Health.OnHealthChanged, Stats.OnStatsChanged, Profile.OnProgressionChanged and Interaction.OnTargetChanged (as those phases exist).

No additional widget-owned gameplay dispatcher is required in the first implementation. Native button click events request the indicated operations. Bind/unbind on screen and source lifecycle; do not let a view become the event owner of inventory or purchases.

On reinitialization, remove the old subscription before binding the new source, then pull current values. On EndPlay or widget teardown, remove the exact subscription and clear old world references. The command must remain correct with no presentation listener.

Interfaces and delegation

No required implemented Blueprint Interface beyond an explicitly inherited contract or a future conditional use described in the source. Owned component/model relationships normally use direct typed references, not a new interface for every call.

Health, mana and stamina Designer and observer contract

Phase 2 Editor configuration: open the existing WBP_HUD Widget Blueprint. Retain its existing root and later prompt/progression containers. Under the root Canvas Panel add/retain an upper-left anchored Vertical Box named VitalsBox (offset 24,24 as provisional layout). Add three Horizontal Boxes: HealthRow, ManaRow, StaminaRow. Each contains a Text Block label (Health/Mana/Stamina), a Size Box (provisional width 220, height 18) wrapping a Progress Bar, and a Text Block numeric readout. Name the variable controls HealthBar, ManaBar, StaminaBar, HealthValueText, ManaValueText, StaminaValueText; enable Is Variable. Reuse an existing equivalent Health control rather than duplicating it. No progress-bar Percent or text property binding executes gameplay logic.

Existing root Canvas Panel
  VitalsBox : VerticalBox
    HealthRow : HorizontalBox → Label / SizeBox(HealthBar) / HealthValueText
    ManaRow : HorizontalBox   → Label / SizeBox(ManaBar) / ManaValueText
    StaminaRow : HorizontalBox→ Label / SizeBox(StaminaBar) / StaminaValueText
  Existing prompt/progression containers (phase-gated)

BindSources(Health: BPC_Health Object Reference, Stats: BPC_Stats Object Reference, Resources: BPC_Resources Object Reference) → None in Phase 2: call UnbindSources, validate the three injected sources, assign private runtime refs, bind the existing health/stat events and one HandleResourcesChanged(CurrentMana: Float, MaxMana: Float, CurrentStamina: Float, MaxStamina: Float) event to Resources.OnResourcesChanged, set bBound=true, then call RefreshView. Invalid sources leave bBound=false and display an unavailable readout (for example “—”), with zero fills; do not treat this presentation fallback as a valid player snapshot. Phase 3 adds the existing Profile/Interaction parameters without removing these three.

RefreshView() → None calls Health.GetHealthSnapshot (Valid, CurrentHealth, MaxHealth) for the health row and Resources.GetResourceSnapshot exactly once for both pools; on Valid=true pass its four numbers to RefreshResourceView(CurrentMana: Float, MaxMana: Float, CurrentStamina: Float, MaxStamina: Float) → None. The resource dispatcher handler passes its coherent payload directly to the same refresh function. For health, pass Health.GetHealthSnapshot or the existing OnHealthChanged payload to a private RefreshHealthView(CurrentHealth: Float, MaxHealth: Float) → None that only sets HealthBar/HealthValueText. OnStatsChanged calls RefreshView after the body components have received the completed stat update. Both refresh functions mutate only widgets. For each resource use a Branch: if Maximum > 0, Set Percent to Clamp(Current / Maximum,0,1); otherwise Set Percent=0 without performing division. Format the supplied values as current / maximum (provisional one decimal place); a valid zero capacity reads 0 / 0. Apply the same safe formula to HealthBar.

UnbindSources() → None: if each previous source is valid, Unbind Event from its dispatcher using the exact custom event delegate installed here, never Unbind All Events. Clear Resources/Health/Stats and bBound; also clear Phase 3 model/interaction subscriptions when present. Call from Controller close/replacement and Event Destruct. Repeated unbind is safe; repeated bind first removes old subscriptions. Do not spend, restore, regenerate, recalculate Stats or set gameplay readiness in any UMG handler.

In L_MovementLab use the documented development resource cases to see 50/50 mana and 100/100 stamina, partial depletion and restoration, and max=0 without invalid fills. Remove the HUD and repeat the requests: resource changes and regeneration must remain correct. Replace the pawn/Stop-Play, bind twice and check one subscription/event refresh, not duplicate callbacks. Pause must stop gameplay-time regeneration even while a menu can redraw.

Common mistakes

Do not own authoritative inventory/health/skills/save state, duplicate validation rules or require a widget listener for a transaction to finish.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
