Purpose and boundaries

Its job: Uses native CharacterMovement and PaperZD integration over the inherited Paper2D Sprite.

Why this exists separately: A PaperZDCharacter combines native Character Movement and a Paper2D visual body. Your Blueprint decides player intent and the custom single-jump budget; native movement still integrates velocity and collision. The body is intentionally replaceable.

What it must NOT own or do

Do not keep the only inventory/XP copy here, implement a second movement integrator, fire native Jump alongside ExecuteJump, or let animation determine gameplay permission.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Player/. Save the asset with the exact name BP_PlayerCharacter. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click empty space → Blueprint Class → All Classes if necessary → search PaperZDCharacter. Select that native parent, not a similarly named project class.
  3. Compile the shell, save it, then add current-phase variables/functions and component instances listed below. If a referenced project class does not exist yet, compile both shells before adding cross-references. Add later-phase features only when their phase arrives.

Interfaces and delegation

This Actor implements BPI_Damageable. See each contract for inputs/outputs and failure meaning. Persistent participation on EnemyBase/NPCBase is conditional as documented; Door may later implement AbilityTarget only for an actually needed authored receiver, not automatically.

The Actor adapter forwards damage acceptance to its Health component, persistent application to local collision/presentation, interaction to its specific coordinator/model operation, or ability application to a validated world transaction. Implementing an interface never transfers authoritative state into the interface asset.

Communication style

Use direct typed references for owned/injected relationships and read-only definitions; interface messages for unrelated world targets; completed-change dispatchers for observers; GI coordination for cross-model mutations and travel. The API caller column identifies the particular route. These dependencies describe types/configuration and known consumers, not an instruction that every asset must hold a reference to every other one.

Changing a value type can affect all direct consumers shown above and their consumers in turn. The dependency reference explains staged shells, cycles and change-impact tracing.

Lifecycle, initialization and teardown

Lifecycle stageExpected behavior
Construction / placed defaultsSet authored instance properties such as stable IDs/definitions; do not grant rewards or generate new persistent identities in Construction Script.
BeginPlay / registrationRegister or initialize only the responsibilities this asset needs. Persistent Actors remain unready until explicit model application; no assumed global BeginPlay order.

First working graph / data flow

Move input → cache intent → CanMove → Add Movement Input(world X)
Jump Started → pending request/timestamp → TryConsumeJumpRequest → consume budget → Launch Character
Release → pending cut → observe launch → shorten positive Z once
Confirmed Walking after landing → re-arm once → consume still-valid buffered press
Movement/action facts → PaperZD AnimInstance queries → state machine → Sprite

Read this as a division into small functions, queries, engine nodes and completed-change notifications—not as one giant Event Graph. Build only the current-phase path. Use function categories/comments and local staged values; log the first failed validation with the asset/ID, expected condition and actual value. No graph shown here has been compiled in Unreal as part of generating the manual.

Resolve AnimInstanceClass from the character definition and configure the inherited PaperZD Animation component. ABP_Player observes current action/movement state. Gameplay cancel/death/travel/EndPlay cleanup stays on the body/components even when no animation callback arrives.

Common mistakes

Do not keep the only inventory/XP copy here, implement a second movement integrator, fire native Jump alongside ExecuteJump, or let animation determine gameplay permission.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
