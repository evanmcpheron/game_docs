Purpose and boundaries

Its job: Uses native CharacterMovement and PaperZD integration over the inherited Paper2D Sprite.

Why this exists separately: A PaperZDCharacter combines native Character Movement and a Paper2D visual body. Your Blueprint decides player intent and the custom single-jump budget; native movement still integrates velocity and collision. The body is intentionally replaceable.

What it must NOT own or do

Do not keep the only inventory/XP copy here, implement a second movement integrator, fire native Jump alongside ExecuteJump, or let animation determine gameplay permission.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Player/. Save the asset with the exact name BP_PlayerCharacter. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click empty space → Blueprint Class → All Classes if necessary → search PaperZDCharacter. Select that native parent, not a similarly named project class.
  3. Compile the shell, save it, then add current-phase variables/functions and component instances listed below. If a referenced project class does not exist yet, compile both shells before adding cross-references. Add later-phase features only when their phase arrives.

When and where to connect this asset

Current replaceable player body. Keep inherited PaperZDCharacter composition. Add only phase-current owned components; the generated attachment/assignment tables name them. One explicit setup path grows from the lab into area bootstrap, with Stats before Health and old-body cleanup before replacement.

Phase 1
BPC_ActionState → BP_PlayerCharacter
ActionState

Open BP_PlayerCharacter → Components → Add BPC_ActionState, rename ActionState and Compile. Retain the native movement/animation components.

Initialize the body action policy before input is accepted. Movement queries CanMove/CanJump; Phase 2 Combat calls TryBeginAction/EndAction. OnActionChanged and OnInterrupted publish complete action/token facts. Only a matching token can end an action.

Required: missing/unready authority rejects affected gameplay requests; do not create a duplicate action flag in Controller or animation.

Expected verification: Phase 1 input/landing regression; Phase 2 interrupted attack and stale-token rejection.

Phase 2
BPC_Stats → BP_PlayerCharacter
Stats

Open BP_PlayerCharacter → Components → Add BPC_Stats, rename Stats and Compile.

Owned body setup passes CharacterDefinition.BaseStats, current supported cumulative growth and the complete modifier array into Recalculate. Initialize before Health; inject this exact Stats reference into Health and Combat where present. OnStatsChanged publishes a complete cache; later build changes rebuild once and clamp Health, never heal automatically. Recalculate the complete seven-stat cache; expose Success/Reason and IsStatsReady. Resources consumes final capacity/rates and owns current pools independently.

Required on this living target: fail readiness/health initialization when missing or when base capacity is invalid. Zero growth/empty modifiers are deliberate in Phase 2.

Expected verification: Compare the initialized capacity/attack/defense and one accepted hit. Repeat complete rebuilds without accumulating modifiers.

Phase 2
BPC_Health → BP_PlayerCharacter
Health

Open BP_PlayerCharacter → Components → Add BPC_Health, rename Health; implement the Actor BPI_Damageable adapter separately in Class Settings.

After Stats is ready, InitializeHealth receives that owned Stats reference and an explicit initial health value. ReceiveDamage forwards to TryReceiveDamage; mitigation/death detection stay here. OnDamageAccepted/OnDied feed the body adapter; OnHealthChanged and current queries feed views. Teardown clears transient acceptance timers; this component never loads a checkpoint or grants rewards.

Required: an unready/missing Health rejects damage and prevents body gameplay readiness. Do not retain a second CurrentHealth or bDead authority on the Actor.

Expected verification: Nonlethal/lethal hit, invulnerability rejection and one death notification; dummy has no rewards and enemy rewards require legitimate death.

Phase 2
BPC_Combat → BP_PlayerCharacter
Combat

Open BP_PlayerCharacter → Components → Add BPC_Combat and rename Combat. In explicit body initialization assign the owned Stats and ActionState references; Compile.

Player RequestAttack or enemy AI/body supplies a validated candidate definition to TryStartAttack. Combat acquires the shared action token and owns elapsed Windup/Active/Recovery, hit accounting and cleanup. AttackDefinition is transient current-execution state, not the default attack-selection slot. OnAttackStarted/OnAttackPhaseChanged/OnAttackEnded are observations; bind the existing matching-token interruption route. Stop timers/queries and cancel idempotently on body teardown.

Required for attacks: missing Stats, ActionState or candidate definition rejects before acceptance. Presentation absence does not prevent gameplay timing, damage or required cleanup.

Expected verification: One target attempt per swing, next-swing hit, active-window hitch, blocking wall, invalid definition and old-token cancellation.

Phase 3
BPC_Interaction → BP_PlayerCharacter
Interaction

Open BP_PlayerCharacter → Components → Add BPC_Interaction, rename Interaction and configure its bounded query/radius; a native body query shape is optional, not a new Blueprint class.

After area/body readiness, refresh nearby candidates with a bounded overlap/query and normalize to Actors implementing BPI_Interactable. RefreshTarget publishes OnTargetChanged; Controller IA_Interact Started calls TryInteract. Revalidate target/range/readiness at the press. ClearTarget and obsolete candidates on modal/death/travel/EndPlay.

Required for interaction input: unready/missing component or no supported candidate returns failure/empty prompt without changing world state.

Expected verification: Switch/checkpoint command, two candidates, target leaving range or disappearing between prompt and press.

Phase 7
BPC_EquipmentVisuals → BP_PlayerCharacter
EquipmentVisuals

Add BPC_EquipmentVisuals as EquipmentVisuals, add native EquipmentRoot with ShoesLayer, BeltLayer, HeadLayer, GlovesLayer, TopLayer, and PantsLayer; disable wearable collision/autoplay and independent component Tick. InitializeLayers receives inherited Sprite and the slot-to-layer references. Bind all six enum values to their matching distinct layer components; empty slots start hidden.

Body build refresh calls SetAppearance from Profile-derived equipment definitions. ABP_Player samples actual rendered sequence/body playback position at its documented presentation callback and calls SyncToBodyPose. Missing sequence mappings hide; ClearLayers clears references on teardown. This adapter never changes the body Sprite or decides equipment/stat rules. Every complete equipment refresh sets or clears all six appearances; clearing one slot leaves the other five unchanged.

Optional for gameplay correctness, required for supported visible-equipment acceptance. Missing/incompatible appearance deterministically hides its layer and reports the mapping issue; valid ownership/stats still work.

Expected verification: Two facings, immediate airborne equip, pause/restart and no one-frame lag at 30/60/120; unsupported Land/Attack/Hit/Death intentionally hide. With temporary matching fixtures, render all six slots together and replace/clear each without disturbing the others.

Phase 9
BPC_Abilities → BP_PlayerCharacter
Abilities

Add BPC_Abilities as Abilities in the existing player. Inject owned ActionState and the validated GameCatalog during explicit body setup, then RefreshUnlocks from current Profile.

Controller/body activation intent calls TryActivate; derived unlocks, charge/recharge ledgers and active executors live here. OnAbilityStateChanged feeds WBP_Abilities. RefreshUnlocks preserves still-valid cooldowns. Export normal-travel values before CancelAll/teardown; import on the new body and clear stale executor/timer references. Inject Resources from this same body and follow the resource/charge commit before publishing or starting the inert prepared executor.

Required for the Phase 9 ability path: unavailable definition/executor, invalid body/action/target, no unlock or no charge rejects before cost; never grant an unlock because the input is mapped.

Expected verification: Purchased TestActive → TestPulse, cooldown, accepted interruption/no refund, stale completion, equipment refresh and normal-travel remaining recharge.

Phase 9
BPC_StatusEffects → BP_PlayerCharacter
StatusEffects

Add BPC_StatusEffects as StatusEffects. Inject GameCatalog before accepting effects and bind OnEffectsChanged to the body’s existing complete build refresh, once.

GI consumable or accepted ability validates CanApplyEffect then applies through the coherent operation. GetStatModifiers returns complete active sources; controlled game-time expiry updates only while needed. Normal travel restores timed values before final Stats/Health; clean recovery clears them. No immediate heal is replayed during import.

Required only for timed-effect use: missing/unresolved effect or invalid target rejects before consuming an item. Immediate Phase 6 healing remains a Health operation.

Expected verification: One modifier source, same-ID duration refresh/no stacking, expiry, pause, normal travel and clean recovery without quantity rollback.

Phase 2
BPI_Damageable → BP_PlayerCharacter, BP_TrainingDummy
GetCombatSide / ReceiveDamage

Open each Actor → Class Settings → Implemented Interfaces → Add BPI_Damageable, Compile, then implement both interface functions. Merely adding Health does not implement an Actor interface.

GetCombatSide returns Player for the player and Enemy for the dummy. ReceiveDamage validates the live adapter, forwards S_DamageSpec unchanged to owned Health.TryReceiveDamage and returns S_DamageResult. Health queries Stats and publishes accepted damage/death facts; the Actor handles movement/action response.

Required on intended targets. Does Implement Interface filters an unsupported Actor; no fallback cast/direct health subtraction is added.

Expected verification: Attack a dummy and damage the player with a hazard; an ordinary native geometry Actor must not become a damageable target.

Phase 2
BPC_Resources → BP_PlayerCharacter
Resources

Open BP_PlayerCharacter → Components → Add BPC_Resources, rename Resources, Compile and Save. Configure after BPC_Stats. Runtime currents are private; no instance-editable balance defaults.

Initialize from ready final Stats while body unready; Resources binds Stats.OnStatsChanged once, fills clean initial pools, and resumes only after body readiness. Controller supplies this same instance to HUD. Death/travel suspend before capture; EndPlay shuts down and unbinds. Later Abilities requests atomic costs.

Missing/unready Stats or Resources fails body initialization closed. No HUD/Controller/Profile fallback owner or zero-default substitute.

Expected verification: Phase 2 real-player lab spending, regeneration, dual rejection, zero capacity and repeat init/teardown; Phase 3 handoff; Phase 9 resource/charge commit.

Resource component attachment and body readiness

Phase 2: open BP_PlayerCharacter → Components → Add BPC_Resources, rename the component Resources, Compile and Save. Use this owned instance throughout; the Components panel creates its Resources reference, so do not create a second manual variable with the same name. Do not add it to the Controller, Profile or GameInstance. Preserve the existing Stats, Health, Combat, ActionState and inherited PaperZD components. Resource state is per current player body.

  1. Extend the existing InitializeCombatBody() → Success: Boolean, Reason: Text lab function. If bBodyReady is already true with the same dependencies, return success without repeating Health/Resources initialization. Initially keep bBodyReady=false and movement/combat requests gated while setup runs.
  2. Read the assigned CharacterDefinition (DA_PlayerBaseStats) and grounded/air attack definitions; validate required components and definitions. Call Stats.Recalculate with its seven-field BaseStats, an all-zero seven-field growth block and an empty modifier array. Branch on Success; failure leaves the body unready and reports the specific missing/invalid input.
  3. Pass the same ready Stats component to Resources.InitializeResources. It fills mana/stamina from final maximums but remains suspended. Initialize Health through its existing InitializeHealth contract, passing that ready Stats reference and final MaxHealth. Inject Stats and the existing ActionState into Combat, preserving attack-definition assignments and interruption wiring. Do not substitute a resource component for Health or ActionState.
  4. Bind Health.OnDied to the existing death adapter and immediately suspend Resources when death begins. Resources binds its own exact Stats.OnStatsChanged handler; do not bind an additional duplicate clamp from the Character or HUD. Finish the existing Health, Combat and animation setup, then set bBodyReady=true. Call Resources.ResumeResources only after the body is alive and ready; treat failure as setup failure and close the readiness gate.
  5. Notify the owning BP_PlayerController through the existing ready-body path. Possession and component readiness may arrive in either order; Controller must require both before binding HUD and accepting input. Opening UI is not a prerequisite for regeneration or combat correctness.

Phase 3 onward: InitializeFromProfile uses the same final-Stats → Resources/Health/Combat setup under an unready gate, not a second unconditional BeginPlay initialization. RefreshBuildFromProfile assembles complete seven-stat base/growth/equipment/passive/effect inputs and checks Recalculate.Success. It never directly modifies CurrentMana/CurrentStamina and never calls InitializeResources merely to refresh a build. Normal travel imports effects in Phase 9 before final current-pool clamping; see the travel contract below. Clean new-game/death/disk-load bodies start full at their final capacities.

PrepareForRecovery() → None closes bBodyReady first, calls Resources.SuspendResources, clears movement requests, cancels active attacks/abilities using existing tokens and continues the original recovery orchestration. For ordinary travel, close the gate and suspend Resources before CaptureTravelHandoff. During EndPlay call Resources.ShutdownResources; Controller/HUD remove their exact subscriptions. Aborted travel may resume the same still-alive body explicitly; destruction never reactivates it.

Do not edit horizontal acceleration/deceleration, facing, collision, jump/coyote/buffer logic or PaperZD state ownership. Verify that zero mana/stamina still permits the existing grounded and airborne basic attacks and all committed movement.

Current-resource handoff after suspension

Phase 3 runtime travel, not disk persistence: extend S_RuntimeTravelState with CurrentMana: Float and CurrentStamina: Float, beside CurrentHealth. Both are finite nonnegative absolute values copied from Resources.GetResourceSnapshot after suspension. Do not add Profile, Actor, component, widget, timer, dispatcher or executor references. Phase 9 ActiveEffects/AbilityStates members stay absent until their types exist.

  1. In BP_GameInstance.PrepareTravelHandoff close source-body readiness/input, stop active movement/attacks/abilities and call Resources.SuspendResources before capturing any current pools. Preserve the current Profile and WorldState objects/values. The suspension barrier discards an unfinished regeneration interval; no regeneration or spending may occur after capture.
  2. Capture CurrentHealth and the coherent mana/stamina snapshot into a local S_RuntimeTravelState. Reject invalid/nonfinite captured values or missing required initialized components; do not substitute a fresh refill for a failed normal-travel capture. Retain only supported value data in GameInstance's existing handoff, then unbind views and tear down the source body. If travel aborts before destruction, explicitly resume only the same valid living body with a new regeneration clock origin.
  3. Use the existing registered-area/bootstrap path to create exactly one destination body under bBodyReady=false. Reconstruct Stats from the current authored base, cumulative growth, equipment and purchased passives. From Phase 9 import supported effects without replaying immediate effects, then complete the final Stats rebuild before restoring/clamping health and resources. Initialize Resources while suspended using ready Stats.
  4. For NormalTravel only, call Resources.RestoreTravelResources(CurrentMana,CurrentStamina): require a newly initialized, suspended destination; reject negative/nonfinite values; assign the absolute captured amounts clamped to final maximums in one update, never add them to the initial full pools. Restore health through its existing travel path and Phase 9 charge/remaining-duration state through its existing component. Loading time grants no regeneration or recharge catch-up.
  5. Finish dependencies, establish body readiness, bind the new HUD/component observers and immediately pull snapshots, then resume Resources and allow gameplay. No late unconditional Health/Resources initialization may overwrite the restored values. Clean teardown prevents callbacks to the old body.

New game, ordinary death and disk load: create a clean body, rebuild all final stats from retained/imported progression and initialize health, mana and stamina to their final maximums. Death retains current Profile/world progress and checkpoint selection; it must not load an older disk save. Disk S_CharacterSave stores neither current pools nor calculated final stats. This change adds runtime handoff members, not new disk-resource fields. Review versioned definition interpretation and retained fixture-save compatibility before a released schema/content change; do not invent migrations for a release that does not exist.

Common mistakes

Do not keep the only inventory/XP copy here, implement a second movement integrator, fire native Jump alongside ExecuteJump, or let animation determine gameplay permission.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
