Purpose and boundaries

Its job: Receives player intent, possesses the current body, and owns local screens.

Why this exists separately: This is the local player’s input and screen owner. A separate controller can replace the body while consistently rebuilding UI bindings and modal focus.

What it must NOT own or do

Do not own inventory copies, purchase rules, current health or permanent dialogue state. Do not leave old pawn delegates bound after travel.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Player/. Save the asset with the exact name BP_PlayerController. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click empty space → Blueprint Class → All Classes if necessary → search PlayerController. Select that native parent, not a similarly named project class.
  3. Compile the shell, save it, then add current-phase variables/functions and component instances listed below. If a referenced project class does not exist yet, compile both shells before adding cross-references. Add later-phase features only when their phase arrives.

Components and composition

No additional manually added gameplay component is required for this framework/Object/snapshot asset. Native inherited framework behavior remains; plain Object/GameInstance/SaveGame models are not Actors to which you attach Actor Components.

When and where to connect this asset

Current input/view owner. Install current-phase mapping contexts once, retain current ready body, and route intent to owners. Create current-phase widgets, bind then pull, and unbind old body sources before replacement. Phase 10 frontend can have no pawn; permanent progress never resides in this Controller.

Common mistakes

Do not own inventory copies, purchase rules, current health or permanent dialogue state. Do not leave old pawn delegates bound after travel.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
