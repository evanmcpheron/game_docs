Purpose and boundaries

Its job: A shallow specialization selects ranged behavior/data.

Why this exists separately: This shallow child selects the ranged attack policy while inheriting the shared body, health and death contract. It exists for a real behavioral variation, not simply a different health number.

What it must NOT own or do

Do not copy the parent’s health/death/initialization graphs or bypass parent cleanup.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Enemies/. Save the asset with the exact name BP_Enemy_RangedBasic. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click BP_EnemyBase → Create Child Blueprint Class. Save the child in its assigned folder, even when the parent is elsewhere. Verify the parent in Class Settings; duplicating the parent is not inheritance.
  3. Compile the shell, save it, then add current-phase variables/functions and component instances listed below. If a referenced project class does not exist yet, compile both shells before adding cross-references. Add later-phase features only when their phase arrives.

When and where to connect this asset

Concrete placed enemy fixture. Use inherited body initialization/components and assign the appropriate EnemyDefinition on the child defaults or validated instance. Configure AI possession/readiness and floor/wall probes; only the ranged active-entry route spawns a projectile. Keep ordinary placement IDs transient unless explicitly configured unique.

Events, dispatchers and observers

No additional custom dispatcher is required for this asset’s first version. Use the referenced model/component events or native lifecycle/input/collision events when relevant. Do not invent a global event bus merely to broadcast every local call.

On reinitialization, remove the old subscription before binding the new source, then pull current values. On EndPlay or widget teardown, remove the exact subscription and clear old world references. The command must remain correct with no presentation listener.

Interfaces and delegation

No required implemented Blueprint Interface beyond an explicitly inherited contract or a future conditional use described in the source. Owned component/model relationships normally use direct typed references, not a new interface for every call.

Common mistakes

Do not copy the parent’s health/death/initialization graphs or bypass parent cleanup.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
