Purpose and boundaries

Its job: Describes enemy base stats, attacks, simple AI tuning and guaranteed reward values.

Why this exists separately: Describes enemy base stats, attacks, simple AI tuning and guaranteed reward values. A schema exists separately so many authored instances can be edited without duplicating runtime gameplay graphs.

What it must NOT own or do

Do not store mutable player ownership, current timers, Actor references or save truth in shared definitions. Definition validation does not execute the described gameplay.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Enemies/. Save the asset with the exact name BPDA_EnemyDefinition. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click → Blueprint Class → All Classes → PrimaryDataAsset. Add phase-appropriate schema variables, exposing authored editable fields, then compile/save.
  3. To create content, right-click the assigned DA_ destination → Miscellaneous → Data Asset → choose this compiled schema. Populate the instance fields rather than a spawned Actor. This guide retains the source’s flat schema/instance workflow, not a replacement child-Blueprint hierarchy.

When and where to connect this asset

Read-only enemy schema. Compile before the melee/ranged instances. EnemyDefinition on the concrete child points to the instance; BaseStats/Attacks/animation/rewards flow through explicit EnemyBase initialization and legitimate-death coordination.

Creation phase: Phase 5. World setup · Run-now proof · Which test map to use.

Only the current phase’s connections are active. The full reference/dependency list can include later schema extensions; it is not an instruction to add them early. Suggested properties/graph calls are implementation guidance, not verified existing game fields. Compile/configure the real consumer, save its world fixture, and record the linked scenario’s observed result before marking this asset done.

Common mistakes

Do not store mutable player ownership, current timers, Actor references or save truth in shared definitions. Definition validation does not execute the described gameplay.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.

Definition of done

Continue with the Phase 5 checklist and Enemy bodies, decisions and rewards. Canonical identity comes from the original placement index and phase register; detailed contracts/fields labeled suggested are the expansion, not a claim of engine execution.

PaperZD class selection

AnimInstanceClass is a class reference derived from UPaperZDAnimInstance, selecting ABP_EnemyTest. It is not a wearable appearance instance or an engine skeletal UAnimInstance. The body initializes its inherited PaperZD Animation component with that class after definitions/components are ready. Definitions remain read-only; action state and animation runtime state are never stored here.
