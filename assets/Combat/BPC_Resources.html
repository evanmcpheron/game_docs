Purpose and ownership boundaries

Resources alone writes CurrentMana and CurrentStamina. It initializes, queries, validates costs, spends both pools atomically, restores, regenerates, clamps to changed maximums, publishes coherent snapshots and suspends safely. BPC_Stats remains the sole calculator of capacities and rates; this component never rebuilds a character build. BPC_Health keeps health, mitigation and death. Profile owns earned progression, purchased skill IDs, inventory and equipment assignments.

Combat and Abilities own accepted actions, tokens, executors and charge/cooldown policy. A resource command grants no action permission. HUD observes; it is never required for gameplay. Do not add separate Mana/Stamina components, a GameInstance resource manager, a persistent resource database, GAS, generic attributes or a new class/skill system. Do not attach Resources to training dummies or enemies merely to make their existing health work.

0 <= CurrentMana <= ObservedStats.MaxMana
0 <= CurrentStamina <= ObservedStats.MaxStamina

Both current values and their maximums are finite. ObservedStats is a read-only value copy of the last final Stats snapshot applied by this component, not a second calculator or editable capacity authority. Applying a new snapshot and clamping happens together before resource observers are notified.

Create and attach in Unreal Editor

  1. Finish and save E_StatId, S_StatBlock, S_StatModifier, BFL_GameRules and BPC_Stats. Create the Resources shell only after the Stats shell compiles; configure it only after Stats can produce a validated seven-field final snapshot.
  2. In Content/Game/Combat/, right-click → Blueprint Class → All Classes → ActorComponent (or the installed Editor's Blueprint Actor Component entry). Name it BPC_Resources. Do not choose SceneComponent or Actor.
  3. In Class Defaults → Component Tick, use Tick Interval 0, Start with Tick Enabled false and Tick Even When Paused false. Keep the component tick available; add Event Tick in its Event Graph. The chosen path is one gated component tick, not Tick plus a timer. Use Set Component Tick Enabled on self to activate/deactivate it after registration.
  4. Add the fields, dispatcher and custom functions below, compile and save. No resource numeric balance belongs in Class Defaults. Zeroed current fields are an uninitialized sentinel, not a substitute player build.
  5. Open BP_PlayerCharacter → Components → Add BPC_Resources → rename the instance Resources. Keep the existing Stats, Health, Combat and ActionState instances and the inherited CharacterMovement/PaperZD composition. Compile.
  6. Open the existing InitializeCombatBody setup and follow the exact sequence below. Compile all touched graphs; a compiled unattached component is not completion. No Phase 3 enum or travel/effect type belongs in the Phase 2 API.

Common validation and notification rules

Every command executes synchronously on the game thread. Validate before any mutation: reference/initialization/lifecycle, numeric validity, then operation-specific conditions. Empty Reason means success; failure returns a stable readable Text such as Resource runtime unavailable, Invalid resource amount, Insufficient mana or Insufficient stamina. Check both costs first; do not turn a negative cost into free restoration or accept NaN through a less-than comparison.

Use the shared IsFiniteNumber predicate in BFL_GameRules before comparisons or Clamp. Public gameplay spending/restoration requires initialized, nonsuspended, nontearing-down state and no active notification/ability-cost commit. Queries require only a valid initialized snapshot, so a suspended body can be captured. Resume and lifecycle shutdown have their separate guards below.

Store proposed new values in local variables, validate the complete result, assign both current values, update tick eligibility, then notify once if any of the four snapshot numbers changed. Zero cost, zero restoration and saturated restoration produce no event. A changed maximum must notify even when the current absolute value is unchanged. Set bPublishing during Broadcast and clear it afterward; observer commands cannot recursively change the values being reported. Lifecycle suspension is permitted immediately during a callback; shutdown unbinds safely and must not be undone by a pending publication return.

Regeneration: one gated component tick

Chosen implementation recommendation: Event Tick calls the private synchronous function AdvanceRegeneration(Now: Real). Now comes from Get Game Time in Seconds, not wall time. The engine documents that this clock stops while paused and follows time dilation. Keep Tick Even When Paused=false. Do not create a TimerManager loop, UI update authority or a second tick on the Character for these same pools.

  1. Private RefreshRegenerationActivity() has no inputs/outputs. Enable tick exactly when initialized, nonsuspended, not tearing down, and at least one pool is below its observed maximum with an observed rate greater than zero. If changing from disabled to enabled, set LastRegenGameTime=Now before Set Component Tick Enabled(true). Do not reset the timestamp on every successful spend while tick is already running. Otherwise disable tick; no work remains when both are full or neither deficit has a positive rate.
  2. AdvanceRegeneration first checks the same guards. Compute Elapsed=Max(0, Now-LastRegenGameTime). Validate both times and Elapsed, then set LastRegenGameTime=Now once for this interval. A bad/nonfinite clock or result suspends the component and logs a diagnostic; never publish invalid numbers.
  3. For each pool with rate>0 and missing capacity>0: if Elapsed >= Missing / Rate, use NewCurrent=Maximum directly. Otherwise use NewCurrent=Current + Rate*Elapsed and clamp to [0,Maximum]. This avoids unbounded multiplication for a large hitch. Validate the staged results. A zero rate or zero maximum adds zero and never divides by zero. No capacity/rate is recalculated here.
  4. Assign both results before any callback. Refresh tick eligibility and emit at most one OnResourcesChanged if current values changed. A delayed frame integrates its measured game-time interval once; do not assume a fixed 1/60 second or a nominal timer period.
  5. When Stats changes during an active interval, HandleStatsChanged(FinalStats: S_StatBlock) calls ClampToMaximums. That function uses the same private integrator with notifications suppressed for the old-rate interval, then adopts the new snapshot and publishes the single final result. New rates apply from that event time onward. Suspension discards the unfinished interval by policy; there is no offline/travel/death catch-up.

InitializeResources remains suspended and full. Spending wakes regeneration; restoration may stop it. A maximum increase can wake regeneration at the new finalized rate, but it is not an immediate refill. Rates changed from zero to positive wake work through HandleStatsChanged. EndPlay stops the one tick and unbinds the one Stats observer. Never use Stats.Recalculate inside Event Tick.

OnResourcesChanged and observers

Create Event Dispatcher OnResourcesChanged(CurrentMana: Float, MaxMana: Float, CurrentStamina: Float, MaxStamina: Float). Parameters are one coherent completed snapshot. WBP_HUD and, in Phase 9, WBP_Abilities bind exact custom events. There is no new resource snapshot Blueprint Structure. Initialization may publish the first valid state before UI exists; every new observer therefore binds once and immediately calls GetResourceSnapshot.

HandleStatsChanged is an exact bound handler with the existing Stats.OnStatsChanged signature, not a second stat calculation. All mutation paths compare before/after values and maximums; do not broadcast from CanAfford/GetResourceSnapshot. Removing a widget or all listeners changes no gameplay result.

Player initialization, recovery and teardown

  1. Phase 2: InitializeCombatBody keeps its readiness gate false. Validate the authored CharacterDefinition and required owned components. Obtain base values only from DA_PlayerBaseStats; call Stats.Recalculate(Base, all-zero seven-field Growth, empty Modifiers). Stop if Success=false.
  2. Call Resources.InitializeResources(Stats). Require Success. Resources is now full but suspended. Call the existing Health.InitializeHealth with this same ready Stats and final MaxHealth, then initialize Combat with this same Stats and the existing ActionState. Keep existing damage/interface/animation adapters.
  3. Bind Health death to the body adapter. When Health establishes death, immediately Resources.SuspendResources, clear body readiness/input and cancel the matching existing action. Do not let Resources determine death or load a checkpoint.
  4. After every current-phase dependency succeeds, mark the body ready, call Resources.ResumeResources, and only then tell the Controller's guarded possession/readiness check to BindSources(Health, Stats, Resources). If resume fails, restore the unready gate and stop. This is explicit composition, not component BeginPlay ordering.
  5. Phase 3 replaces the automatic lab initializer with InitializeFromProfile; it reuses this same order, not a second initializer. For normal travel, freeze the source body before CaptureTravelHandoff, capture health/mana/stamina values, then destroy the old body. Rebuild the destination's final Stats, initialize Resources while suspended, restore captured absolute resource values, bind the new views and resume only after readiness.
  6. Phase 9 extends destination setup: reconstruct supported temporary effects before the final Stats/resource maximum clamp and absolute handoff restoration. Active executors never travel. No paused/loading interval restores extra mana or stamina.
  7. New game, death recovery and disk load construct a clean body and fill health/mana/stamina from final capacities. Retain purchased skill/equipment/progression inputs; do not save current pools or FinalStats in S_CharacterSave. Checkpoint activation selects recovery without refilling the current body. A repeated initialization of a living body is not a recovery.
  8. Controller UnbindSources precedes old-body destruction/replacement. The body and component EndPlay both use idempotent ShutdownResources; remove only owned subscriptions, not another listener's binding. Phase 2 death resets by Stop/Play; do not implement a Phase 3 recovery system early.

Phase 9 deferred resource/charge commit

Future Phase 9 extension, not Phase 2 work. The synchronous resource dispatcher must not run between resource deduction and charge mutation. Keep the public TrySpend signature/behavior above. Add two restricted orchestration functions on this same component, callable only by the owning BPC_Abilities, and reuse the same private cost validation/staged subtraction implementation as TrySpend:

BeginDeferredSpend(ManaCost: Float, StaminaCost: Float) → Success: Boolean, Reason: Text revalidates, commits both deductions without broadcasting, and opens bCostCommitOpen on success (including zero cost). It records whether a resource event is pending. Failure changes no pools, flags or charge state. EndDeferredSpend() → None is called by that Abilities transaction only after charge/deadline/executor acceptance fields are final; it emits the pending resource snapshot once under the guards and then clears its pending/open flags. Calling it without an open commit is a no-op diagnostic. Ordinary callers cannot open/close this bracket; only the injected same-body Abilities acceptance graph uses it.

During the open interval all ordinary resource writes, further deferred spends and ability reentry fail; queries may read the already committed values. The same synchronous Abilities graph assigns the prevalidated charge/recharge state without latent nodes, target calls or dispatch, publishes its completed OnAbilityStateChanged while both owners are guarded, then calls EndDeferredSpend. Clear the Abilities commit guard after both publications. Resource/ability observers are read-only presentation/query consumers; do not synchronously mutate Profile, Stats or effects inside these notifications. Schedule a new independent gameplay request after the acceptance call returns instead. Every success path closes the interval; the charge assignment after BeginDeferredSpend is a prepared nonfailing value commit, not a second fallible command.

Only after the complete accepted operation is published does the owning ability start the prepared executor if its body/token is still valid. A callback-triggered death/interruption can cancel that already accepted action; it never refunds the accepted cost. Missing executor/failed preparation/failed spending BEFORE acceptance releases only the reserved action token, destroys the inert object and leaves both resources and charges unchanged. See the complete activation sequence.

Dependencies and communication

Direct dependencies: BPC_Stats, S_StatBlock and the existing BFL_GameRules numeric validation. No Profile, WorldState, GameInstance, E_EntryReason or future effect/ability state type is needed in this Phase 2 component. Body/controller adapters supply owned references; views receive the current body component, not a global lookup.

Failure conditions and definition of done

Stop when any current pool exceeds its applied maximum, any invalid value reaches a snapshot, one cost is spent on dual-cost failure, a stat rebuild refills resources, an old body changes after capture, duplicate update work exists, or HUD absence changes the result. Debug the owner/API boundary rather than adding a second mutable store.

Completion requires the exact component/type/folder, real player attachment, validated Stats-before-Resources setup, idempotent lifetime wiring, three working HUD readouts, atomic acceptance/rejection, elapsed game-time regeneration, pause/full/death/teardown gates and recorded results from the linked map tests. Static documentation checks cannot establish Blueprint compilation or runtime correctness. Level growth, equipment, purchased passives, active ability costs and travel/effect reconstruction remain activated only in their documented phases.
