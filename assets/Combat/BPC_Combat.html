Purpose and boundaries

Its job: Reusable attack execution and hit accounting, not animation ownership.

Why this exists separately: Attacks need a clock, action token and hit accounting that work even with placeholder art. This component can run on player and enemy without knowing equipment UI or enemy reward policy.

What it must NOT own or do

Do not award XP, own skills, use flipbook completion to cause damage, or maintain a second authoritative health value.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Combat/. Save the asset with the exact name BPC_Combat. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click → Blueprint Actor Component (ActorComponent), or the equivalent Actor Component class option in your installed Editor. This component has no independent transform.
  3. Compile/save the class. Open each intended owning Actor and add one component instance in its Components panel at the appropriate phase. Initialize required typed references explicitly; do not attach Actor Components to GameInstance.

Components and composition

This is itself a non-spatial ActorComponent. Do not give it a second independent transform or attach gameplay geometry “inside” it. The owning Actor provides native collision/visual components and injects typed references. Its state is replaced with that Actor, except explicitly exported handoff values.

TryStartAttack Custom function

Inputs
Definition: BPDA_AttackDefinition reference
Outputs
Started: Boolean; Reason: Text
Called by
Player request or EnemyBase attack selection
Allowed changes
This execution's timing, token and hit data

Validate body/definition/movement eligibility, acquire token, snapshot damage, clear hit set and begin Windup. Reject repeated requests without changing active state.

Execution: Synchronous function/query. Latent nodes are forbidden inside this function; start separate event-driven orchestration when needed. A returned “accepted” is not asynchronous completion.

Communication style

Use direct typed references for owned/injected relationships and read-only definitions; interface messages for unrelated world targets; completed-change dispatchers for observers; GI coordination for cross-model mutations and travel. The API caller column identifies the particular route. These dependencies describe types/configuration and known consumers, not an instruction that every asset must hold a reference to every other one.

Changing a value type can affect all direct consumers shown above and their consumers in turn. The dependency reference explains staged shells, cycles and change-impact tracing.

Lifecycle, initialization and teardown

Lifecycle stageExpected behavior
AttachmentAdd one instance to the intended Actor at the assigned phase; no independent transform.
InitializationInject required owner/component/model/definition references before accepting commands. Validate once, not repeated global Actor scans.
Gameplay / updatesEnable controlled update only while an attack is executing; stop on cancel/finish.
Travel / deathRuntime component is replaceable. Export permitted value handoff before teardown for abilities/effects/health; persistent purchases/world facts stay in models.
EndPlay / reinitializeClear own timers/active queries, cancel executors if owned, unbind long-lived model events and clear obsolete refs. Cleanup and cancellation are idempotent.

Common mistakes

Do not award XP, own skills, use flipbook completion to cause damage, or maintain a second authoritative health value.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
