Purpose and boundaries

Its job: Reusable health and damage acceptance independent of enemy/player type.

Why this exists separately: Current health and acceptance of a hit are reusable live-body behavior. Keeping them separate from Stats distinguishes “how much capacity this build has” from “how much damage this body has taken.”

What it must NOT own or do

Do not choose checkpoints, open maps, save inventory, grant enemy rewards or time attacks from animation.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Combat/. Save the asset with the exact name BPC_Health. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click → Blueprint Actor Component (ActorComponent), or the equivalent Actor Component class option in your installed Editor. This component has no independent transform.
  3. Compile/save the class. Open each intended owning Actor and add one component instance in its Components panel at the appropriate phase. Initialize required typed references explicitly; do not attach Actor Components to GameInstance.

Components and composition

This is itself a non-spatial ActorComponent. Do not give it a second independent transform or attach gameplay geometry “inside” it. The owning Actor provides native collision/visual components and injects typed references. Its state is replaced with that Actor, except explicitly exported handoff values.

Interfaces and delegation

No required implemented Blueprint Interface beyond an explicitly inherited contract or a future conditional use described in the source. Owned component/model relationships normally use direct typed references, not a new interface for every call.

Communication style

Use direct typed references for owned/injected relationships and read-only definitions; interface messages for unrelated world targets; completed-change dispatchers for observers; GI coordination for cross-model mutations and travel. The API caller column identifies the particular route. These dependencies describe types/configuration and known consumers, not an instruction that every asset must hold a reference to every other one.

Changing a value type can affect all direct consumers shown above and their consumers in turn. The dependency reference explains staged shells, cycles and change-impact tracing.

Common mistakes

Do not choose checkpoints, open maps, save inventory, grant enemy rewards or time attacks from animation.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
