Purpose and boundaries

Its job: Provides stable-ID lookups to authored definitions and the progression table without guessing paths.

Why this exists separately: Provides stable-ID lookups to authored definitions and the progression table without guessing paths. A schema exists separately so many authored instances can be edited without duplicating runtime gameplay graphs.

What it must NOT own or do

Do not store mutable player ownership, current timers, Actor references or save truth in shared definitions. Definition validation does not execute the described gameplay.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Core/. Save the asset with the exact name BPDA_GameCatalog. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click → Blueprint Class → All Classes → PrimaryDataAsset. Add phase-appropriate schema variables, exposing authored editable fields, then compile/save.
  3. To create content, right-click the assigned DA_ destination → Miscellaneous → Data Asset → choose this compiled schema. Populate the instance fields rather than a spawned Actor. This guide retains the source’s flat schema/instance workflow, not a replacement child-Blueprint hierarchy.

Functions and request contracts

No executable gameplay API belongs on this authored content/value asset. Use its field/value editor and the linked consuming system. Schema classes need editable fields, not player-state mutation or world timers.

Events, dispatchers and observers

No additional custom dispatcher is required for this asset’s first version. Use the referenced model/component events or native lifecycle/input/collision events when relevant. Do not invent a global event bus merely to broadcast every local call.

Interfaces and delegation

No required implemented Blueprint Interface beyond an explicitly inherited contract or a future conditional use described in the source. Owned component/model relationships normally use direct typed references, not a new interface for every call.

Communication style

Use direct typed references for owned/injected relationships and read-only definitions; interface messages for unrelated world targets; completed-change dispatchers for observers; GI coordination for cross-model mutations and travel. The API caller column identifies the particular route. These dependencies describe types/configuration and known consumers, not an instruction that every asset must hold a reference to every other one.

Changing a value type can affect all direct consumers shown above and their consumers in turn. The dependency reference explains staged shells, cycles and change-impact tracing.

Common mistakes

Do not store mutable player ownership, current timers, Actor references or save truth in shared definitions. Definition validation does not execute the described gameplay.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.

Definition of done

Continue with the Phase 3 checklist and Persistent models and stable world identity. Canonical identity comes from the original placement index and phase register; detailed contracts/fields labeled suggested are the expansion, not a claim of engine execution.
