Purpose and boundaries

Its job: Survives ordinary map travel; coordinates the session and save I/O.

Why this exists separately: The player body, controller and map can be replaced. This session object keeps the two long-lived models reachable and gives cross-model operations one coordination point. Keeping that coordination separate from either model prevents Profile and WorldState from calling one another.

What it must NOT own or do

Do not execute movement, AI, attack hits, skill-tree layout or every gameplay rule here. Do not retain old door/pawn/controller references through travel.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Core/. Save the asset with the exact name BP_GameInstance. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click empty space → Blueprint Class → All Classes if necessary → search GameInstance. Select that native parent, not a similarly named project class.
  3. Compile the shell, save it, then add current-phase variables/functions and component instances listed below. If a referenced project class does not exist yet, compile both shells before adding cross-references. Add later-phase features only when their phase arrives.

Components and composition

No additional manually added gameplay component is required for this framework/Object/snapshot asset. Native inherited framework behavior remains; plain Object/GameInstance/SaveGame models are not Actors to which you attach Actor Components.

Communication style

Use direct typed references for owned/injected relationships and read-only definitions; interface messages for unrelated world targets; completed-change dispatchers for observers; GI coordination for cross-model mutations and travel. The API caller column identifies the particular route. These dependencies describe types/configuration and known consumers, not an instruction that every asset must hold a reference to every other one.

Changing a value type can affect all direct consumers shown above and their consumers in turn. The dependency reference explains staged shells, cycles and change-impact tracing.

Lifecycle, initialization and teardown

Lifecycle stageExpected behavior
Session startConfigured class created for the session; add actual model logic in Phase 3, save queue in Phase 4.
GameplayCoordinate model transactions and serialization, not continuous character/enemy simulation.
Normal area travelSettle I/O, suspend body requests, retain models and value handoff; release obsolete Actor references.
DeathRetain current progress, choose checkpoint recovery and create a clean runtime body after map reload.
Disk load/new sessionSerialize I/O, stage/validate candidates, then replace/import model values deliberately.
ExitComplete or explicitly acknowledge failed/pending save policy before quit. A queue request alone is not a completed save.

First working graph / data flow

Session Init → validate definitions → Construct Object from Class twice → retain typed refs → initialize models → ready
Persistent request → validate whole operation → guarded value commit → increment revision once → publish → request save
RequestSave → immutable snapshot → custom Event Graph I/O → completion result → captured revision saved / failure retained

Read this as a division into small functions, queries, engine nodes and completed-change notifications—not as one giant Event Graph. Build only the current-phase path. Use function categories/comments and local staged values; log the first failed validation with the asset/ID, expected condition and actual value. No graph shown here has been compiled in Unreal as part of generating the manual.

Concrete tests

Debug output pattern: [BP_GameInstance] Case=<name> Id=<stable ID or token> Expected=<value> Actual=<value> Result=PASS/FAIL. Include revision/area where relevant; output is a diagnostic, not a substitute for comparing typed values.

Common mistakes

Do not execute movement, AI, attack hits, skill-tree layout or every gameplay rule here. Do not retain old door/pawn/controller references through travel.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
