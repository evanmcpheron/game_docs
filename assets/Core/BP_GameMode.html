Purpose and boundaries

Its job: Owns area bootstrap and controlled pawn spawning, not permanent progression.

Why this exists separately: Each loaded gameplay map needs a coordinator that knows its current Actors and can wait until they are ready. That short-lived job belongs here, not in persistent records.

What it must NOT own or do

Do not own XP/inventory/checkpoint truth. Do not combine automatic and manual pawn spawning. Do not use arbitrary Delay as a substitute for readiness.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Core/. Save the asset with the exact name BP_GameMode. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click empty space → Blueprint Class → All Classes if necessary → search GameModeBase. Select that native parent, not a similarly named project class.
  3. Compile the shell, save it, then add current-phase variables/functions and component instances listed below. If a referenced project class does not exist yet, compile both shells before adding cross-references. Add later-phase features only when their phase arrives.

Components and composition

No additional manually added gameplay component is required for this framework/Object/snapshot asset. Native inherited framework behavior remains; plain Object/GameInstance/SaveGame models are not Actors to which you attach Actor Components.

Events, dispatchers and observers

No additional custom dispatcher is required for this asset’s first version. Use the referenced model/component events or native lifecycle/input/collision events when relevant. Do not invent a global event bus merely to broadcast every local call.

On reinitialization, remove the old subscription before binding the new source, then pull current values. On EndPlay or widget teardown, remove the exact subscription and clear old world references. The command must remain correct with no presentation listener.

Interfaces and delegation

No required implemented Blueprint Interface beyond an explicitly inherited contract or a future conditional use described in the source. Owned component/model relationships normally use direct typed references, not a new interface for every call.

Communication style

Use direct typed references for owned/injected relationships and read-only definitions; interface messages for unrelated world targets; completed-change dispatchers for observers; GI coordination for cross-model mutations and travel. The API caller column identifies the particular route. These dependencies describe types/configuration and known consumers, not an instruction that every asset must hold a reference to every other one.

Changing a value type can affect all direct consumers shown above and their consumers in turn. The dependency reference explains staged shells, cycles and change-impact tracing.

Lifecycle, initialization and teardown

Lifecycle stageExpected behavior
Construction / placed defaultsSet authored instance properties such as stable IDs/definitions; do not grant rewards or generate new persistent identities in Construction Script.
BeginPlay / registrationRegister or initialize only the responsibilities this asset needs. Persistent Actors remain unready until explicit model application; no assumed global BeginPlay order.
GameplayExecute public requests and owned runtime behavior; projection-only assets read models. Use event-driven work unless a listed update/timer is necessary.

First working graph / data flow

Participant registers → query all prerequisites → guard initializing → validate current map spawns → initialize persistent Actors → resolve destination → Spawn Actor from Class → initialize body → Possess → bind HUD → ready

Read this as a division into small functions, queries, engine nodes and completed-change notifications—not as one giant Event Graph. Build only the current-phase path. Use function categories/comments and local staged values; log the first failed validation with the asset/ID, expected condition and actual value. Common mistakes

Do not own XP/inventory/checkpoint truth. Do not combine automatic and manual pawn spawning. Do not use arbitrary Delay as a substitute for readiness.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.

Definition of done

Continue with the Phase 0 checklist and Persistent models and stable world identity. Canonical identity comes from the original placement index and phase register; detailed contracts/fields labeled suggested are the expansion, not a claim of engine execution.
