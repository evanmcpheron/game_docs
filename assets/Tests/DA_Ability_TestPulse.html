Purpose and boundaries

Its job: Select the compiled schema class in Miscellaneous → Data Asset; edit this instance.

Why this exists separately: This is one authored content object using BPDA_AbilityDefinition. Its identity and field values describe content, while the consuming runtime/model class owns mutable results. It is a development fixture, not a final content commitment.

What it must NOT own or do

Do not Spawn Actor from this data instance, use it as an owned inventory entry or change it to record a purchase/current recharge. Do not relocate it from the canonical folder.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Tests/. Save the asset with the exact name DA_Ability_TestPulse. The folder already exists; do not move the asset into a different generic folder.
  2. First compile BPDA_AbilityDefinition. Right-click → Miscellaneous → Data Asset → select BPDA_AbilityDefinition in the class picker. Create an instance, not a child Actor Blueprint.
  3. Populate the field table with this instance’s explicitly labeled fixture values. Register its stable ID in the appropriate existing catalog map when the consuming phase needs it. Leave future fields unused until their systems exist; never mutate the instance to record player progress.

Instance versus schema versus owned state

This asset uses BPDA_AbilityDefinition. The schema page defines field meanings; this page supplies its concrete proposed content/fixture configuration. Neither this object nor its schema stores the player’s acquired quantity, selected equipment EntryId or current ability cooldown.

Functions and request contracts

No executable gameplay API belongs on this authored content/value asset. Use its field/value editor and the linked consuming system. Schema classes need editable fields, not player-state mutation or world timers.

Events, dispatchers and observers

No additional custom dispatcher is required for this asset’s first version. Use the referenced model/component events or native lifecycle/input/collision events when relevant. Do not invent a global event bus merely to broadcast every local call.

Interfaces and delegation

No required implemented Blueprint Interface beyond an explicitly inherited contract or a future conditional use described in the source. Owned component/model relationships normally use direct typed references, not a new interface for every call.

Phase 9 resource costs

The schema defaults ManaCost=0 and StaminaCost=0. Costs complement, rather than replace, MaxCharges and RechargeDuration. Validate both finite/nonnegative values during catalog/definition validation and again at activation. An invalid definition fails before action acceptance or deduction; do not silently clamp a negative cost into a free ability.

DA_Ability_TestPulse uses the development values ManaCost=10 and StaminaCost=0 while retaining its existing executor, damage/range/capability, one-charge/recharge fixture and nonexclusive DA_Skill_TestActive grant. Test an additional stamina-only case by temporarily setting this same instance to ManaCost=0, StaminaCost=20 in the Editor before PIE. Test dual-resource atomicity with 10/20, then restore 10/0 and save. These variants are test configurations, not final warrior abilities or new assets.

Common mistakes

Do not Spawn Actor from this data instance, use it as an owned inventory entry or change it to record a purchase/current recharge. Do not relocate it from the canonical folder.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
