Purpose and boundaries

Its job: A map asset, not a Blueprint subclass.

Why this exists separately: This World asset holds the placed fixture/context described in its recipe. A map is content, not a Blueprint with an Actor parent. A map asset, not a Blueprint subclass.

What it must NOT own or do

Do not add a second session-model owner to Level Blueprint or assume every room needs another map. Do not manually make an empty .umap file.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Tests/. Save the asset with the exact name L_SystemTests. The folder already exists; do not move the asset into a different generic folder.
  2. Use File → New Level and select an ordinary empty/basic level suitable for the test, not an Open World/World Partition template. Save the World asset in the exact folder.
  3. Use the recipe below to place/configure existing Blueprint instances and native geometry. A placed instance does not require a new registered asset name. Verify World Settings GameMode override, spawn policy and packaged map inclusion.

Map recipe and placed-instance checklist

Suggested harness-only setup (the source does not specify a separate area definition): use native GameModeBase for this isolated map and run stateless/value/definition assertion scenarios from BP_ArchitectureTestHarness without assuming a BP_PlayerCharacter exists. Native default framework participants are not new custom assets. Run full player, travel, checkpoint and recovery scenarios in the already registered L_Slice_A/B, and continue tests from explicit readiness/completion. Do not pretend L_SystemTests already has an AreaId or secretly add another DA_Area asset.

Instance IDs are not extra asset names

Start, FromA, FromB, room IDs and PersistentIds are values on placed instances. They do not add new Blueprint files or change the 149-asset register. Validate safe transforms, collision clearance and no duplicate current-map SpawnId.

Functions and request contracts

No executable gameplay API belongs on this authored content/value asset. Use its field/value editor and the linked consuming system. Schema classes need editable fields, not player-state mutation or world timers.

Events, dispatchers and observers

No additional custom dispatcher is required for this asset’s first version. Use the referenced model/component events or native lifecycle/input/collision events when relevant. Do not invent a global event bus merely to broadcast every local call.

Interfaces and delegation

No required implemented Blueprint Interface beyond an explicitly inherited contract or a future conditional use described in the source. Owned component/model relationships normally use direct typed references, not a new interface for every call.

Common mistakes

Do not add a second session-model owner to Level Blueprint or assume every room needs another map. Do not manually make an empty .umap file.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.

Definition of done

Continue with the Phase 11 checklist and Validation and packaged proof. Canonical identity comes from the original placement index and phase register; detailed contracts/fields labeled suggested are the expansion, not a claim of engine execution.
