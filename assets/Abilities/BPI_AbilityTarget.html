Purpose and boundaries

Its job: An environmental ability contract separate from ordinary interaction and damage.

Why this exists separately: An environmental ability contract separate from ordinary interaction and damage. This contract lets unrelated Actor types receive the same request without a shared gameplay mega-parent or caller casts to every subtype.

What it must NOT own or do

Do not store fields/components in the interface or use it as an event broadcast. An unsupported target is not success; adding a component does not automatically implement its owner interface.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Abilities/. Save the asset with the exact name BPI_AbilityTarget. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click → Blueprints → Blueprint Interface. There is no selectable Actor parent. Add each exact function name and its agreed inputs/outputs, then compile/save.
  3. On each implementing Actor, open Class Settings → Implemented Interfaces and add this interface. Implement the functions there and delegate to the correct owned component/model. An interface asset contains no variables or component instances.

Data fields, variables and property guidance

No mutable variable store is required. An interface declares signatures; a Function Library operates on explicit inputs. Do not add a second gameplay owner here.

Events, dispatchers and observers

No additional custom dispatcher is required for this asset’s first version. Use the referenced model/component events or native lifecycle/input/collision events when relevant. Do not invent a global event bus merely to broadcast every local call.

Interfaces and delegation

Implementers: BP_AbilityTestReceiver.

Filter with engine Does Implement Interface and a valid Actor reference. Implement the declared function on the receiving Actor and delegate to its owner/component; the interface itself contains no storage. For command outputs, false means no completed operation. Persistence apply is a no-reward reconstruction contract, not a notification broadcast.

Communication style

Use direct typed references for owned/injected relationships and read-only definitions; interface messages for unrelated world targets; completed-change dispatchers for observers; GI coordination for cross-model mutations and travel. The API caller column identifies the particular route. These dependencies describe types/configuration and known consumers, not an instruction that every asset must hold a reference to every other one.

Changing a value type can affect all direct consumers shown above and their consumers in turn. The dependency reference explains staged shells, cycles and change-impact tracing.

Common mistakes

Do not store fields/components in the interface or use it as an event broadcast. An unsupported target is not success; adding a component does not automatically implement its owner interface.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.

Definition of done

Continue with the Phase 9 checklist and Active abilities and capability gates. Canonical identity comes from the original placement index and phase register; detailed contracts/fields labeled suggested are the expansion, not a claim of engine execution.
