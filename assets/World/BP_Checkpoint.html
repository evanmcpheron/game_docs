Purpose and boundaries

Its job: Specializes an interactable with a persistent recovery destination.

Why this exists separately: A checkpoint is an interactable with a safe authored recovery identity. Its local visuals can be rebuilt while WorldState keeps the actual last-activated destination.

What it must NOT own or do

Do not load an old save on death, assume activation must heal, or save a live PlayerStart reference.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/World/. Save the asset with the exact name BP_Checkpoint. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click BP_InteractableBase → Create Child Blueprint Class. Save the child in its assigned folder, even when the parent is elsewhere. Verify the parent in Class Settings; duplicating the parent is not inheritance.
  3. Compile the shell, save it, then add current-phase variables/functions and component instances listed below. If a referenced project class does not exist yet, compile both shells before adding cross-references. Add later-phase features only when their phase arrives.

Events, dispatchers and observers

No additional custom dispatcher is required for this asset’s first version. Use the referenced model/component events or native lifecycle/input/collision events when relevant. Do not invent a global event bus merely to broadcast every local call.

On reinitialization, remove the old subscription before binding the new source, then pull current values. On EndPlay or widget teardown, remove the exact subscription and clear old world references. The command must remain correct with no presentation listener.

Interfaces and delegation

This Actor implements BPI_Interactable, BPI_PersistentActor. See each contract for inputs/outputs and failure meaning. Persistent participation on EnemyBase/NPCBase is conditional as documented; Door may later implement AbilityTarget only for an actually needed authored receiver, not automatically.

The Actor adapter forwards damage acceptance to its Health component, persistent application to local collision/presentation, interaction to its specific coordinator/model operation, or ability application to a validated world transaction. Implementing an interface never transfers authoritative state into the interface asset.

Use direct typed references for owned/injected relationships and read-only definitions; interface messages for unrelated world targets; completed-change dispatchers for observers; GI coordination for cross-model mutations and travel. Common mistakes

Do not load an old save on death, assume activation must heal, or save a live PlayerStart reference.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.

Definition of done

Continue with the Phase 3 checklist and Disk saving, loading and death recovery. Canonical identity comes from the original placement index and phase register; detailed contracts/fields labeled suggested are the expansion, not a claim of engine execution.
