Purpose and boundaries

Its job: A non-spatial owner of persistent world records, independent of loaded Actors.

Why this exists separately: World facts must remain queryable even when the corresponding map and Actor are absent. A non-spatial Object keyed by authored IDs holds those facts without turning a door or NPC into a global manager.

What it must NOT own or do

Do not hold loaded Actor references, grant items/XP, run timers or save to disk independently. Do not let a local door Boolean overwrite an already-open model record.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/World/. Save the asset with the exact name BP_WorldState. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click empty space → Blueprint Class → All Classes if necessary → search Object. Select that native parent, not a similarly named project class.
  3. Compile the shell, save it, then add current-phase variables/functions and component instances listed below. If a referenced project class does not exist yet, compile both shells before adding cross-references. Add later-phase features only when their phase arrives. Construct instances through GameInstance, not Spawn Actor. Call explicit initialization; there is no Actor BeginPlay for these models.

Components and composition

No additional manually added gameplay component is required for this framework/Object/snapshot asset. Native inherited framework behavior remains; plain Object/GameInstance/SaveGame models are not Actors to which you attach Actor Components.

When and where to connect this asset

Session-owned Object. GI uses Construct Object from Class with Outer=self, retains a typed strong reference and explicitly initializes once. Never Spawn Actor, wait for Actor BeginPlay or reconstruct a new model on ordinary map travel/death. Inject these existing references into current consumers.

Communication style

Use direct typed references for owned/injected relationships and read-only definitions; interface messages for unrelated world targets; completed-change dispatchers for observers; GI coordination for cross-model mutations and travel. The API caller column identifies the particular route. These dependencies describe types/configuration and known consumers, not an instruction that every asset must hold a reference to every other one.

Changing a value type can affect all direct consumers shown above and their consumers in turn. The dependency reference explains staged shells, cycles and change-impact tracing.

Lifecycle, initialization and teardown

Lifecycle stageExpected behavior
ConstructionGameInstance uses Construct Object from Class, Outer self and a stored typed reference. No Actor BeginPlay.
InitializationCall explicit synchronous new/import initializer; validate values before marking session ready.
GameplayQueries are read-only; mutations obey owner/transaction rules. No world Tick or timers.
Area travel / deathKeep the same current model objects and values. Never recreate from an older save on death.
Disk loadImport a completely validated supported value snapshot without replaying rewards; reconstruct dependent bodies/views afterward.
TeardownAt session replacement/exit, consumers unbind and release old references. No rewards or world operations run from object teardown.

Common mistakes

Do not hold loaded Actor references, grant items/XP, run timers or save to disk independently. Do not let a local door Boolean overwrite an already-open model record.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.
