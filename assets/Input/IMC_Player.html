Purpose and boundaries

Its job: Groups key/button bindings for an input context.

Why this exists separately: Groups key/button bindings for an input context. Input assets describe intent/mappings; the local Controller routes it and gameplay owners still decide permission.

What it must NOT own or do

Do not implement damage, inventory ownership or action permission in mapping assets. Do not add unapproved traversal mappings.

Create the asset in the Editor

  1. In the Content Browser, navigate to Content/Game/Input/. Save the asset with the exact name IMC_Player. The folder already exists; do not move the asset into a different generic folder.
  2. Right-click → Input → Input Mapping Context. Open the mapping editor and add the phase-appropriate Input Actions and keys/buttons.
  3. PlayerController installs it through the existing Enhanced Input Local Player Subsystem with deliberate priority. Higher-priority UI routing still does not own gameplay permission. Verify close/cancel while paused.

When and where to connect this asset

Incremental gameplay mapping. Install once on the local player through Controller. Add Move/Jump at Phase 0, Attack at 2, Interact at 3, Inventory at 6, Skills at 8, AbilityPrimary at 9 and Pause at 10. Do not map unavailable or unapproved actions early. Clear cached intent when removing/blocking the context.

Mappings and installation

Mapping actions: IA_Move, IA_Jump, IA_Attack, IA_Interact, IA_Inventory, IA_Skills, IA_AbilityPrimary, IA_Pause. Add each only at its source phase.

Value Type and Started/Triggered/Completed/Canceled belong to each Input Action, not to the context itself. Controller adds/removes the context through the native Enhanced Input Local Player Subsystem. Suggested priorities are gameplay 0 and modal UI 100; these are implementation examples, not gameplay permission. Prove the selected paused/focus route. Never expect an action in a removed context to close the screen unless another deliberate route handles it.

Functions and request contracts

No executable gameplay API belongs on this authored content/value asset. Use its field/value editor and the linked consuming system. Schema classes need editable fields, not player-state mutation or world timers.

Events, dispatchers and observers

No additional custom dispatcher is required for this asset’s first version. Use the referenced model/component events or native lifecycle/input/collision events when relevant. Do not invent a global event bus merely to broadcast every local call.

Interfaces and delegation

No required implemented Blueprint Interface beyond an explicitly inherited contract or a future conditional use described in the source. Owned component/model relationships normally use direct typed references, not a new interface for every call.

Dependencies and communication

No earlier custom asset type is required beyond native engine/plugin facilities. See the current phase for consumer wiring.

Common mistakes

Do not implement damage, inventory ownership or action permission in mapping assets. Do not add unapproved traversal mappings.

A source-named function is not automatically an engine node. A later-phase typed field does not require moving its schema earlier. If an implementation seems to require a second authoritative store, stop and check ownership and source naming notes before adding another variable or class.

Continue with the Phase 0 checklist and Input intent and routing. Canonical identity comes from the original placement index and phase register; detailed contracts/fields labeled suggested are the expansion, not a claim of engine execution.
