Purpose and boundaries

Player presentation graph: observes movement and gameplay actions, orchestrates body animation.

Paper2D supplies visual assets. PaperZD owns character playback. Gameplay owners retain all permission, timing, damage, inventory, progression and recovery rules. This asset never supplies required gameplay authority.

Create the asset in the Editor

In Content/Game/Animation/, create a PaperZD Animation Blueprint named ABP_Player, selecting AS_Player as Animation Source. The generated runtime parent is UPaperZDAnimInstance, not the engine skeletal UAnimInstance. Add a State Machine and wire its result to Output Animation. Assign this class to the character’s inherited PaperZD Animation component AnimInstanceClass. The character base already supplies that component; do not add a duplicate.

Components and composition

The authored AnimBP generates a UPaperZDAnimInstance runtime class. The character’s inherited native PaperZD Animation component owns the live instance and uses its inherited Sprite as render target; this Blueprint adds no Actor components.

When and where to connect this asset

Authored presentation. Create with its matching Animation Source, compile and assign the inherited PaperZD Animation component AnimInstanceClass on BP_PlayerCharacter (also DA_PlayerBaseStats.AnimInstanceClass). Observe ready gameplay facts/body identity, not damage or action authority. Reopen for only phase-current states; required cleanup works with missing notifies.

Functions and request contracts

OnInit resolves the owning Actor and binds optional completed-change events, then pulls facts. The animation update samples current facts and the graph evaluates transitions. Phase 1 requires only movement/ActionState; add Health/Combat and Attack/Hit/Death at Phase 2, then optional Ability observations at Phase 9. Missing later-phase components remain safe and do not become early build prerequisites. Use PaperZD Jump Nodes for urgent Hit/Death presentation only if they simplify the graph; they do not jump the character or acquire a gameplay token. Sequence completion/time-remaining rules may end Land cosmetics, while accepted gameplay interrupts it immediately. Attack/Hit presentation follows the owner’s lifecycle even if the sequence finishes early.

Phase 7: OnTick, after PaperZD processes animation, calls BPC_EquipmentVisuals.SyncToBodyPose with the current rendered sequence and body time. This is an optional cosmetic adapter call, never a required gameplay listener.

Events and observers

PaperZD notifies and sequence completion are cosmetic observations. They cannot release ActionState, determine damage, grant rewards or be the only cleanup path. Validate live owner/body and execution identity for any timed request; editor preview may have no owning instance.

Interfaces and delegation

No new gameplay interface is required. Observe existing movement, Health, ActionState and Combat queries/events. Equipment ownership is queried from Profile through the player adapter.

Dependencies and communication

AS_Player, BPC_ActionState, BPC_Combat, BPC_Health, BPC_Abilities, ASQ_Player_IdleTest, ASQ_Player_MoveTest, ASQ_Player_RiseTest, ASQ_Player_FallTest, ASQ_Player_LandTest, ASQ_Player_AttackTest, ASQ_Player_HitTest, ASQ_Player_DeathTest

Queries flow from presentation to gameplay owners; completed facts flow back to presentation. Equipment mapping is read-only. There is no presentation dependency required for gameplay correctness.

Lifecycle and teardown

Save/compile the AnimBP with its source and current-phase sequences. OnInit resolves ready gameplay owners; ownerless preview and missing later-phase components use safe defaults. Unbind optional observers on body/AnimInstance replacement and teardown; never retain an old body/session callback. Travel/load creates a fresh AnimInstance from current gameplay facts. Phase 7 player presentation may call the separately initialized equipment adapter; gameplay never waits for that call.

First working data flow

CharacterMovement / Health / ActionState / Combat → PaperZD AnimInstance → state machine → body Sprite

Concrete tests

  • Exercise every current-phase state and immediate Land→new jump/attack interruption.
  • Cancel attack into Hit, then Death; deliver an old cosmetic callback and verify no newer action is released.
  • Disable the Animation component or remove notifies; damage, rewards, cooldowns and movement remain correct.
  • Compile in the installed plugin and run the packaged slice; neither is claimed here.

Common mistakes

  • Using the engine skeletal Animation Blueprint creation action.
  • Setting Sprite flipbooks from Character Tick while this graph also controls them.
  • Adding dash, roll, double-jump or wall states without approved gameplay.
  • Letting notifies begin/end exclusive gameplay action ownership.

Definition of done

One PaperZD graph controls body playback; committed states and robust interruption are validated without gameplay authority in animation.

These are required project tests, not executed results. No Unreal Editor compile, engine build or runtime test was performed for this documentation change.
