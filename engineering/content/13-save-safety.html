Rule: persist domain identity and values, not runtime object graphs. Why: Actors, components and world contexts are replaced. Applies: progression, inventory, slot references, purchases, world records, discovery, checkpoint and remembered NPC facts. Exception: a deliberate catalog asset locator may be serialized when the format explicitly supports it; it still requires loading/cook and content migration. It is not live Actor identity.

Snapshot boundary

The planned SaveGame fields remain Header, Character, World and Recovery. Snapshot capture reads complete committed Profile/WorldState values and derives Recovery. Keep runtime Actor/component/widget/executor pointers, timers, delegate handles, absolute old-world deadlines, final-stat caches and current dialogue cursors out of disk data.

Keep snapshots immutable once I/O starts. Retain the in-flight SaveGame with a reflected strong reference until completion. Live gameplay mutates live models and a future snapshot. Use the existing schema/content versions, save sequence and revision bookkeeping rather than inventing a second save owner.

UPROPERTY(SaveGame) is not a complete save architecture. Its filtering effect depends on the archive used. Epic’s standard SaveGameToSlot documents saving non-transient properties without checking that flag; never assume a SaveGame annotation serializes only selected state. Keep USaveGame itself value-only and test the actual codec. See SaveGameToSlot API.

Completion-driven save queue

  1. After a meaningful persistent commit, increment one PersistentRevision and request save. No save per Tick or per health change.
  2. If I/O is active, coalesce a pending request. Capture a fresh immutable snapshot and InFlightRevision when allowed.
  3. Permit one save/load operation at a time for the logical slot; keep the snapshot reachable.
  4. On successful completion, acknowledge only the captured revision/sequence. Newer live revisions remain dirty and require another capture.
  5. On failure, retain dirty state and the last valid generation, report failure and offer the existing retry/acknowledged unsaved-progress path.

Keep the established A/B generation fallback: write the older/invalid generation, preserve the other, then load candidates sequentially and choose the highest valid sequence. This reduces some interrupted-write risks; it is not a guarantee of atomic storage or immunity to every platform failure. Do not overwrite a corrupt/unsupported existing slot as New Game silently.

C++ uses the appropriate GameplayStatics callback API rather than assuming the Blueprint async wrapper’s signature. AsyncSaveGameToSlot serializes on the game thread, writes via a worker and completes on the game thread; payload copies must be thread-safe. See C++ async save API. The project queue, revision and immutability rules remain necessary.

Establish the in-flight state and retain the snapshot before invoking the async API. The inspected 5.8.3 implementation can invoke its failure callback immediately when preparation fails, before the call returns; do not assume every completion is delayed. Keep completion handling safe for both immediate and later delivery.

Callbacks validate the logical slot, in-flight operation and session generation. Settle outstanding work before load/profile replacement/travel/final quit according to existing orchestration. Mandatory flush failure needs a visible decision; do not hang indefinitely or depend on a paused gameplay timer for retry. Queue acceptance is not proof of disk success.

Validate before replacing truth

Load into temporary values. Validate class/format/version, unique EntryIds, positive bounded quantities, catalog IDs, equipment ownership/slot compatibility, purchased skills, XP/points consistency, world identity and recovery destination. Apply the project’s declared reject/quarantine/prune policy with diagnostics. Never silently reinterpret an unknown item as another item or a serialized enum as a harmless default.

Only after validation/migration succeeds, replace session values under the mutation guard. Recompute level/build caches without awarding XP or points again. Apply world records before Actors/AI activate; rebuild the body and unlock cache before enabling requests. Disk import does not replay reward, immediate heal or legitimate-death events.

Changing serialized contracts

  1. Inventory affected enums, structures, properties, IDs, asset references, Blueprint pins and existing fixture saves.
  2. Define the supported old representations, explicit conversion, unknown/removed-content policy and version change.
  3. Ensure the old representation can deserialize before relying on an in-object version field. A broken reflected structure may fail before migration runs.
  4. Preserve deprecated fields/types or add a real compatibility reader when required. Core redirects may address certain reflected renames, but not arbitrary schema/value conversion.
  5. Test retained saves in a fresh packaged process, including previous supported versions, missing content, corrupt newest generation and fallback.

Renumbering native enum values, Blueprint-to-native struct conversion, property renames and content-ID changes are compatibility work, even if the values look identical. See Epic Core Redirects. Do not implement speculative legacy readers before a real format exists.

No save files or schema implementation are present in the current game checkout. These requirements govern future persistence work; they are not a claim that existing game saves were tested.
