Choose references by purpose

The following pointer mechanics are grounded in Epic object pointers. The owner and teardown decisions are project policy.

ReferenceDefault useConstraint
UPROPERTY TObjectPtr<T>Strong UObject member reference: session models, owned components, in-flight snapshot.Participates in GC when reflected/reachable; a bare TObjectPtr is not a retention guarantee.
TWeakObjectPtr<T>Non-owning live candidates/targets, old-world-sensitive callbacks.Does not retain; resolve and validate when used.
TSoftObjectPtr / TSoftClassPtrAuthored asset/class location with deferred loading.Not proof of loading or cooking; prepare before activation.
TSubclassOf<T>Already-required configured spawn class.Class selection is not a spawned instance.
Raw T*Short-lived parameter/local borrowed reference, engine signature.Does not retain; do not store across callbacks without a deliberate lifetime strategy.
TStrongObjectPtr<T>Exceptional non-UObject holder needing explicit retention.Do not use by default inside UObject owners.

Creation and GC reachability

Create runtime UObjects with NewObject, Actors through UWorld spawning, and native constructor subobjects with CreateDefaultSubobject. Never use new/delete for a UObject or spawn an Actor with NewObject. Choose a meaningful Outer for containment, naming and lifetime context; do not rely on Outer alone as the strong reference keeping a child alive. A long-lived UObject owner stores its child in a reflected property.

// GameInstance.h fragment
private:
    UPROPERTY(Transient)
    TObjectPtr<UPlayerProfile> PlayerProfile;

// GameInstance.cpp initialization fragment
PlayerProfile = NewObject<UPlayerProfile>(this);

The session creates and retains Profile/WorldState. Their gameplay initialization/import is explicit after required definitions are ready; UObject construction is not actor BeginPlay. Nested structs/containers holding UObjects need reflected traversal all the way from a reachable owner, or a justified explicit GC reference strategy. Do not hide UObject references in unreflected plain collections and expect GC to find them.

Actor and component ownership

A world controls Actor lifetime; Actor Owner and Instigator serve gameplay/engine relationships, not an exclusive C++ memory owner. Strong references do not stop explicit Destroy or EndPlay. An Actor may exist in memory yet be unusable for gameplay. Default subobjects are created once per native construction; runtime-added components need the proper owning Actor, instance registration and teardown path for their use.

Preserve the existing world/body boundary: GameInstance must release old pawn, component, controller-view and executor references across ordinary travel. Retain value handoffs, not old bodies. Do not cache GetWorld once in a session object and reuse it across maps. EndPlay cancels active work and subscriptions regardless of whether destruction came from combat, travel or PIE shutdown.

Use Actor Destroy for an intentionally finished live Actor and DestroyComponent for an intentionally removed runtime component, with owned work canceled through teardown. Destroy is not immediate memory deallocation. Plain UObjects normally become collectible after reachable references are released; do not force deletion or AddToRoot as an ordinary ownership workaround.

Validity at real boundaries

AActor* CurrentTarget = TargetActor.Get();
if (!IsValid(CurrentTarget))
{
    return;
}

if (!CurrentTarget->GetClass()->ImplementsInterface(UAbilityTarget::StaticClass()))
{
    return;
}

This is a runtime target-check fragment. Also validate source readiness, range/permission and token before effect application. Recheck a UObject after an external callback if it will be used again. Do not turn impossible local assumptions into silent no-ops everywhere; use the validation policy to distinguish configuration failures and programmer errors.

Soft loading and worker safety

Resolve required soft definitions/classes before acquiring irreversible gameplay state or tearing down the source map. Keep loaded objects strongly reachable for the period they are required. Hold/cancel request handles according to the actual loader API and validate the current session/body on completion. A failed load rejects activation with a useful diagnostic.

Soft references need a proven packaging/cook route through the existing catalog or a deliberately configured asset-loading policy. Do not add AssetManager infrastructure without a concrete need. A hard reference is reasonable for a small always-needed dependency; a soft reference is reasonable for optional/area content. Verify both in a packaged build.

Gameplay UObject access and mutation remain on the game thread unless the engine API explicitly allows otherwise. Worker tasks operate on copied, thread-safe value inputs and return results to the correct context. A pointer wrapper alone does not make an Actor, Blueprint call, UObject mutation or shared container thread-safe.
