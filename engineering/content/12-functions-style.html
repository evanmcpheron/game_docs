One understandable operation

Rule: functions have one purpose, consistent conceptual level and explicit side effects. Why: a reader should understand a request without tracing hidden saving/UI/reward work. Applies: commands, queries and orchestration. Exception: the existing coordinator can deliberately orchestrate coherent cross-owner operations, but cannot absorb each owner’s implementation.

Use small value/enum inputs for simple operations; a cohesive request struct is appropriate for related contextual data, not for hiding excessive unrelated parameters. Mark queries const, use const references for appropriate nontrivial input values and initialize output parameters on every path. Document whether a returned bool means accepted, changed, released or queued. Expected multi-cause failures can use a typed result enum; do not add a generic Result framework.

Validate at domain boundaries. Guard clauses reduce nesting; named predicates help when a repeated meaningful condition needs a name. Do not extract every trivial expression to reach a line-count target. Shared numeric calculations need one authoritative implementation, but presentation wrappers may remain local.

Guard clauses

if (IsValid(Target))
{
    if (bInitialized)
    {
        if (CanAttack())
        {
            TryStartAttack(Target);
        }
    }
}

Prefer the same visible prerequisites without nested indentation:

if (!IsValid(Target))
{
    return;
}

if (!bInitialized)
{
    return;
}

if (!CanAttack())
{
    return;
}

TryStartAttack(Target);

This caller fragment does not replace TryStartAttack’s authoritative revalidation. If uninitialized state is an unexpected configuration error, report it once at initialization rather than silently swallowing it in every frame.

No nested ternaries

Never use a ternary inside either branch or condition of another ternary. The following is prohibited:

const int32 SelectedValue = ConditionA ? ValueA : (ConditionB ? ValueB : ValueC);

Write the choices explicitly:

int32 SelectedValue = ValueC;

if (ConditionA)
{
    SelectedValue = ValueA;
}
else if (ConditionB)
{
    SelectedValue = ValueB;
}

A single simple ternary may improve a binary choice such as a facing sign. If the reader must parse side effects or several clauses, use if/else. This is a hard project rule with no project-code exception; generated or external engine code is outside the rule’s scope.

Formatting and ordinary C++ choices

Use Unreal-style PascalCase identifiers, braces on separate lines, braces around conditional/loop bodies, one declaration per line and consistent indentation with the surrounding source. For new native files, use tabs for indentation as in Epic’s convention. Separate logical phases with a blank line; do not align long blocks with decorative spacing. Keep conditions readable without an arbitrary maximum function length.

Use nullptr, explicit initialization, override for overrides and const wherever it expresses a real contract. Use auto when the type is evident locally, not when it hides a domain result. Use named constants/configuration instead of repeated unexplained numbers; units belong in names/metadata or a brief contract. Do not introduce exceptions, RTTI or custom build flags to emulate ordinary UE error handling. RAII is appropriate for scoped native resources and guards.

Domain naming

Use A for Actor-derived types, U for other UObject types, F for structs/plain project types, E for enums, I/U for native Unreal interfaces, b for Boolean fields, and Out for output parameters where useful. Name headers after their principal native type without the prefix, such as HealthComponent.h. Existing BP_, BPC_, BPDA_, BPI_, S_, E_, DA_ and WBP_ asset identities stay intact until an intentional migration.

Prefer CurrentHealth, MaximumHealth, EquippedEntryIdsBySlot, CharacterStats, TryReceiveDamage and CanPerformAction. Avoid Val, Mgr, Info, Thing, Process or DoStuff. Do not ban every word such as Handler or System mechanically: a narrowly named callback like OnSaveCompleted describes a real role; GameManager collecting unrelated work does not.

Maintain canonical source aliases from architecture notes: Recalculate/RebuildStats, AwardXP/GrantXP, MoveAxis/MoveIntent and equivalent save/equipment spellings have one underlying implementation/store. A necessary compatibility wrapper delegates rather than repeating rules.

Comments reduce cognitive load

A comment should exist only when reading the code with the comment requires less mental effort than reading the code without it. Prefer self-explanatory code. Comments explain non-obvious intent, lifetime constraints, pending movement behavior, serialization/migration or deliberately unusual policy; they do not narrate assignments or repeat a function name.

// An old attack must not release an action acquired after interruption.
if (ExpectedToken != ActionToken)
{
    return false;
}

The comment explains identity, not the equality syntax. Keep it proportional and preserve useful existing comments. If a simple implementation needs a paragraph to be understood, simplify the code first. Do not add comments to every changed line or require documentation density. Public APIs need concise contract documentation only for unclear units, ownership, failure or side effects.

Record architecture decisions outside code when they span systems. A short decision record states the concrete problem, owner/dependency choice, alternatives, compatibility effects and proof. Comments and docs must be updated with the behavior they describe.
