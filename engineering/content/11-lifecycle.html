Use the correct stage

Engine lifecycle facts follow Epic Actor lifecycle. The responsibilities below are this project’s conventions.

Use Super calls according to the engine lifecycle contract and deliberate ordering. If overriding UActorComponent::InitializeComponent, enable bWantsInitializeComponent when required and ensure registration; it is before BeginPlay, not a global gameplay-ready signal. See InitializeComponent API.

Readiness is an explicit domain contract

Rule: commands that need a built body require its initialized state. Why: components, controller, area and definitions may arrive in different orders. Applies: damage, interaction, attack/ability acceptance and travel restore. Exception: pure value calculations require no world and can run before gameplay; configured constructor defaults also remain simple.

Choose an initialization entry point with required inputs and success/failure meaning. Repeated setup must be intentionally idempotent or reject duplicates with a diagnostic. Do not implement several competing initialization paths in constructor, BeginPlay and Tick. Do not use fixed delays to make ordering seem correct.

  1. Create/validate session models and required definitions.
  2. Register AreaRoot, controller and the current map’s unique spawn/persistent identity participants.
  3. When prerequisites are ready, enter one guarded GameMode bootstrap.
  4. Apply persistent records while affected Actors are inert.
  5. Spawn one body; validate collision/spawn success; initialize components and reconstruct the build.
  6. Apply EEntryReason’s normal-travel handoff or clean recovery policy.
  7. Possess, bind then pull UI, clear consumed handoff and enable gameplay.

Registration events retry bootstrap; a late listener also queries current readiness. Failure keeps gameplay blocked with the missing prerequisite identified. Resolve a safe authored fallback; never silently spawn at an uninitialized transform. Phase 0’s automatic lab pawn and Phase 3’s explicit spawn route are alternatives, not two paths to run simultaneously.

Spawn inert, initialize, activate

Projectiles and ability executors must not cause gameplay effects in BeginPlay before their damage/context/owner/instigator are supplied. Deferred spawning is appropriate when data is required before construction/BeginPlay; set needed values and call FinishSpawning exactly once. It does not replace the project’s activation/readiness gate. Check spawn and finish results before possession or charge consumption.

Abilities acquire the permitted action token, spawn a prepared inert executor, release that same token if spawn fails, and only then consume the accepted charge and start execution. Projectile overlap paths share one consumed guard established before target callbacks. Do not leave half-initialized executors active when setup fails.

Restoration has its own order

Normal travel restores timed effects without replaying immediate healing, then rebuilds Stats/capacity, restores recharge and clamps/restores current health. Death/disk load reconstruct a clean runtime body. Profile/WorldState import and record application happen while gameplay is blocked; presentation follows committed state. BeginPlay must not overwrite state the bootstrap already restored.

Teardown must be safe after partial initialization and repeated cancellation. Remove exactly the resources this instance established. C++ destructors and GC cleanup are not the place to issue gameplay commands, write saves or depend on a valid world.
