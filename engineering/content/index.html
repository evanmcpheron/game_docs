It governs stable gameplay architecture, state, contracts, implementation, Blueprint exposure and maintenance. It preserves the game’s documented 2D exploration action-platforming RPG design.

Default boundary: C++ owns stable gameplay architecture, rules, state, reusable systems, invariants, contracts and core behavior. Blueprints own composition, asset assignment, tuning, presentation, designer configuration and deliberate extension points. There must still be one authority for each fact and rule.

The historical Blueprint manual remains the source of committed domain ownership and gameplay policy. This standard governs new/modified C++ and supersedes language-specific recipes where they conflict; it does not require an immediate full port. Existing architecture and serialized APIs are preserved through scoped migration.

Hard rules at a glance

  • No nested ternaries. Ordinary implementation lives in .cpp, including getters.
  • Use narrow strongly typed enums for finite choices; make invalid states difficult to represent.
  • Keep invariants with the owner and expose controlled operations rather than mutable internal values.
  • Prefer reusable composition; keep inheritance shallow and meaningful.
  • Expose Blueprint configuration, observation, commands and hooks deliberately.
  • Use events, timers and Tick according to actual scheduling needs and lifetime.
  • Preserve serialized contracts, identity and the distinct travel/death/load policies.
  • No speculative systems, giant managers, circular dependencies, unrelated refactors or unsupported optimizations.

When rules compete: correctness → safety → ownership → maintainability → readability → consistency → testability → reuse → measured performance → brevity. Major rules, rationale, application and justified exceptions are in the chapters; this summary does not replace them.

Maintain this standard

Authoritative chapter bodies are the HTML fragments in engineering/content/. Titles and reading order live in engineering/pages.json. The assembled engineering/*.html pages and engineering entries in site/search-data.js are generated. Edit a fragment, run python3 tools/build_cpp_standard.py, then python3 tools/build_cpp_standard.py --check and python3 tools/check_cpp_standard.py from the repository root. No Python packages or web server are required to build/read the guide.

Update architecture evidence when real Source/Config/assets become available, and update the rule chapter when an accepted technical deviation changes project policy. Keep gameplay design changes separate. Preserve original-roadmap.html and sources/asset-manifest.json; do not rewrite historical audits to claim new runtime results. The engineering evidence record and documentation verification record state the proof boundary. Browser checks record direct-file navigation, offline search and representative desktop/mobile rendering.

Examples are small illustrative Unreal C++ fragments; surrounding declarations, staging and initialization are omitted when irrelevant to the rule. Native example names are proposed counterparts unless confirmed by actual source. Bad-pattern examples are explicitly labeled and must not be copied as project code.
