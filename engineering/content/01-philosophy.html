Scope and authority

This standard governs new and modified project C++ targeting Unreal Engine 5.8.3. It covers gameplay architecture, Blueprint contracts, lifetime, persistence, implementation and review. It does not approve new mechanics or require every documented Blueprint to be converted.

C++ owns stable gameplay architecture, rules, state, reusable systems, invariants, contracts and core behavior. Blueprints own composition, asset assignment, tuning, presentation, designer configuration and deliberate extension points. An owner remains authoritative regardless of implementation language.

The project architecture and evidence inventory distinguishes repository observations from planned assets. The older Blueprint manual supplies domain ownership and gameplay policy. This standard supersedes its language-specific implementation recipes for new C++ work; it preserves its gameplay design, asset identities and phase intent. A conflict must be recorded, not silently resolved by adding a second owner.

When principles compete

  1. Correctness
  2. Safety
  3. Clear ownership
  4. Maintainability
  5. Readability
  6. Architectural consistency
  7. Testability
  8. Reuse
  9. Performance supported by evidence
  10. Brevity

For example, duplicate a small guard rather than hide control flow behind a generic helper. Keep a stat calculation authoritative rather than copy it into widgets. A measured hot path can justify a local implementation choice; it cannot justify silently breaking save identity.

Practical Clean Code, SOLID and DRY

Cohesion before class count

A class should own one meaningful game responsibility and its invariants. Apply Single Responsibility to reasons for change: Health accepts damage; Stats computes capacity; the body reacts. Do not fragment each validation into a new object. A composition root may wire several capabilities because wiring is its coherent job.

Abstraction follows a real contract

Use composition and narrow contracts to control dependencies. A subtype must honor its parent’s valid inputs, results and side effects; do not make an enemy child bypass shared damage acceptance. Extend through data or an intentional hook before editing a giant type switch. Introduce an interface only for actual unrelated implementers, not to satisfy Dependency Inversion mechanically. Ordinary typed references are appropriate for owned components.

DRY means one authority for domain knowledge

Centralize each shared gameplay rule, algorithm, invariant, state definition, calculation or meaningful constant when practical. Similar syntax alone is insufficient. Two IsValid guards need no abstraction; two damage formulas for the same rule do. A copied snapshot or derived cache is permitted if its source, invalidation and reconstruction are explicit.

Keep architecture proportional

Do not add generic factories, repositories, service layers, injection frameworks, universal containers, global buses or managers for hypothetical features. A direct domain operation is the default. Add a layer only when a demonstrated responsibility or lifetime mismatch warrants it, with the concrete caller and simplification recorded.

Rules that apply to every change

  • Nested ternary expressions are prohibited.
  • Ordinary function implementations belong in .cpp files, including short queries.
  • Use strongly typed enums for cohesive finite choices; avoid magic integer/string states and exclusive Boolean combinations.
  • Use composition for reusable capabilities; inheritance requires a genuine is-a relationship.
  • Keep mutable state private and Blueprint exposure intentional.
  • Tick, abstractions, managers and optimizations need a concrete purpose.
  • Avoid circular dependencies and unrelated refactors; preserve public and serialized contracts unless the requested change requires migration.

Technical exceptions to defaults must name the constraint, affected scope, alternative considered and validation. A short function is not a header exception. Nested ternaries have no project-code exception: express the branch explicitly. Engine signatures and generated code may impose patterns the project cannot change; isolate adapters rather than changing engine code to enforce style.

Engineering principle

Write simple, explicit, cohesive Unreal C++ with clear ownership, narrow responsibilities, controlled dependencies, strong domain types, deliberate Blueprint APIs, reusable composition and minimal hidden behavior. Make invalid states difficult to represent. Use engineering techniques where they improve this game’s actual architecture.
