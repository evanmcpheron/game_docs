Keep rules outside presentation

Blueprint commands request a validated operation; Blueprint queries observe current truth; notifications report completed state. A disabled button, hidden sprite or finished flipbook cannot be the authority for purchase permission, invulnerability, attack damage or death rewards. Test the operation with UI and cosmetics absent.

Do not hard-code presentation paths into C++ constructors. Select assets through existing definition/catalog references and configured Blueprint defaults. Required geometry and algorithmic constants can live in C++ when they are implementation constraints; tunable gameplay values need named authorable fields with units and validation.

Protect invariants around extension points

Use a non-overridable C++ command to validate and commit before invoking optional presentation. A Blueprint override can omit its parent call, reenter code or destroy an object. Establish guards first and revalidate retained references after any callback. Never call Blueprint events from constructors.

During incremental migration

Reparent a feature’s Blueprint only after its native contract is available. Keep composition and tuning in the asset; remove or redirect its old rule graphs in the same feature migration. Do not run both native and Blueprint damage, jump or purchase paths. Existing native APIs and serialized types must be discovered before naming a replacement; the proposed names in these examples are not evidence of implemented classes.
