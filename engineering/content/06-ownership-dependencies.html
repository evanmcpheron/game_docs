Allowed responsibility direction

Definitions and domain value types
        ↓
Profile / WorldState       Live components
        ↑                       ↑
GameInstance coordinator   Body composition / adapters
        ↑                       ↑
World target requests      Controller input requests
        ↓                       ↓
Completed facts → UI and cosmetic observers

These arrows describe responsibility flow, not a mandate that every object hold references to every other. Profile and WorldState do not call one another. GameInstance coordinates operations touching both. Health may query initialized Stats; Stats never queries or mutates Health. Combat requests ActionState and target interfaces; it does not buy skills or save inventory.

Rule: inject known dependencies at an explicit initialization boundary and document which are required. Why: this avoids lookup chains and circular ownership. Applies: bodies, Health/Stats, controller views, session models. Exception: a cast once at a known framework boundary or a scoped initialization lookup is reasonable. Never use repeated global scans as dependency injection.

Body composition is orchestration

The player body can assemble Profile build inputs, initialize its components and wire accepted-hit reactions. That does not make it the inventory store, damage calculator, skill validator or save writer. Keep adapter methods short and domain operations in their owners. See the project ownership matrix.

Coherent cross-owner operations

For pickup claim + inventory grant, unique completion + reward, and consumable use + runtime benefit, the coordinator validates and stages all affected values before mutation. Commit synchronously without latent work, asset loading or external callbacks between mutations. Increment the persistent revision once, then publish completed notifications. All subscribers must be optional for correctness.

Guard the complete operation against reentrant mutation, including event publication. A narrow internal native commit API can be private with a specifically named coordinator friend or another deliberately limited access mechanism. Do not mark internal staging functions BlueprintCallable simply to make wiring convenient. No mutable arrays should escape. This is an application transaction, not an Unreal database guarantee or permission for broad friend access.

Prepared changes must have a commit path that cannot normally reject halfway. If that cannot be ensured, redesign staging or implement an explicit rollback under the same guard before publishing. Do not consume an item, invoke Blueprint presentation and only then find out healing failed. Request saving after commit; disk failure leaves live committed state dirty rather than rolling gameplay back.

Resolve circular dependencies at the responsibility boundary

Inventory and equipment are currently one Profile-owned inventory plus a slot map; do not create InventoryComponent ↔ EquipmentComponent just to mirror folders. Profile provides build inputs to the body; the body supplies Stats with values. Profile must not inspect the current pawn’s Stats or Abilities to determine ownership.

When a new cycle appears, draw the callers and authorities, pass a value/query result where possible, or place orchestration at the existing composition boundary. A weak pointer changes retention, not architectural direction. A delegate can decouple observation, but does not remove a hidden requirement that listeners complete rules.

Lifetime is the test for a subsystem

Use a subsystem only when a real responsibility matches its engine scope and benefits from independent lifecycle. World-scoped registries cannot hold old-world Actors in a session object indefinitely. Local-player presentation may fit local-player scope if later requirements warrant it. The current plan already has GameInstance, AreaRoot, GameMode and models; do not replace them or add duplicate subsystem authorities during routine feature work.

GameInstance remains a narrow session coordinator for model creation, coherent operations, travel handoff and save queue. A growing file can be split by coherent implementation concern without creating a new global owner. Extracting a subsystem requires a concrete lifetime/ownership problem, a migration plan and no duplicated state.
