A coherent class and a small API

Rule: start fields and helpers private. Expose only real commands and queries. Why: the owner can validate every mutation and readers can see its contract. Applies: components, models, Actors and plain C++ values. Exception: simple value structs may expose fields; inheritance hooks may be protected. Protected mutable containers are not a substitute for encapsulation.

Profile may own progression, purchases and inventory/equipment because they form the existing persistent character model. That is not permission to move combat, movement, UI or world simulation into Profile. If it becomes hard to navigate, first group methods/files around those domains while retaining one store; extracting a new model needs a demonstrated ownership benefit.

HealthComponent->CurrentHealth -= Damage;

The above bypasses acceptance and clamping. Prefer the owner’s operation:

const FDamageResult DamageResult = HealthComponent->TryReceiveDamage(DamageSpec);

DamageSpec and DamageResult illustrate native counterparts of the established structures. Inspect actual signatures before implementing them. The caller reacts to acceptance; it does not apply mitigation or health mutation a second time.

Components versus inheritance

Player and enemy bodies remain separate PaperZDCharacter families. Enemy children and small interactable/ability families are valid specialization boundaries. Do not add CharacterWithInventory → CharacterWithEquipment → CharacterWithSkills to share capabilities. Equipment variations in values or appearance belong in definitions and the Profile slot map.

// PlayerCharacter.h
#pragma once

#include "CoreMinimal.h"
#include "PaperZDCharacter.h"
#include "PlayerCharacter.generated.h"

class UHealthComponent;

UCLASS()
class RPG_API APlayerCharacter : public APaperZDCharacter
{
    GENERATED_BODY()

public:
    APlayerCharacter();

private:
    UPROPERTY(VisibleAnywhere, Category = "Capabilities")
    TObjectPtr<UHealthComponent> HealthComponent;
};
// PlayerCharacter.cpp
#include "Player/PlayerCharacter.h"
#include "Combat/HealthComponent.h"

APlayerCharacter::APlayerCharacter()
{
    HealthComponent = CreateDefaultSubobject<UHealthComponent>(TEXT("HealthComponent"));
}

The character base requires the PaperZD module dependency; see module guidance. This focused composition example assumes the native component and RPG module exist; it is not the complete player. Health initialization belongs after Stats and build inputs are ready. Give the component one creation path: if a native default subobject replaces a Blueprint-added Health, remove the old one during the scoped migration. ActorComponent is non-spatial; use SceneComponent only for a capability that needs a transform.

Choose communication by relationship

  • Direct reference: known owner/component or explicitly injected dependency. It is the simplest contract for Health → Stats.
  • Component: shared capability and state, not a way to make every object implement every interface.
  • Inheritance: a real family with substitutable behavior, such as EnemyBase children. Do not inherit hostile AI for NPC dialogue.
  • Unreal interface: unrelated receiver Actors, including Blueprint implementers. It defines behavior, not shared state or multicast events.
  • Delegate: observe a completed fact without requiring the producer to know all listeners. Never require a subscriber to finish an authoritative transaction.

Unreal interfaces

Preserve the four planned contracts: Damageable, Interactable, PersistentActor and AbilityTarget. State the receiver, input validity, result, mutation and readiness conditions. Having a Health component does not automatically implement Damageable on its owning Actor; add an explicit adapter.

For a reflected native interface that Blueprint may implement, validate the UObject, check ImplementsInterface, then call the generated Execute_ function. A native interface-pointer cast alone can miss Blueprint-only implementations. The example assumes a migrated native contract already exists; do not create a duplicate alongside the old BPI merely for the sample.

if (!IsValid(Target))
{
    return;
}

if (!Target->GetClass()->ImplementsInterface(UInteractable::StaticClass()))
{
    return;
}

IInteractable::Execute_Interact(Target, Interactor);

Check the command’s real success output before treating the interaction as accepted. Native-only non-UObject abstractions can use ordinary C++ interfaces when genuinely required; they are not automatically Blueprint contracts. See Epic interfaces.
