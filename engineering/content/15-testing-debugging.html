Separate calculations from presentation

Rule: important math and validation should use explicit value inputs where practical. Why: identical inputs can be reasoned about and tested without HUD/animation. Applies: stat formulas, damage mitigation, progression thresholds, inventory staging, skill availability and snapshot validation. Exception: collision, world lifetime and possession need actual engine integration; do not emulate the world through a new testing framework.

The planned BFL_GameRules represents stateless narrow shared calculations, not a universal utility library. A native function library wrapper may expose a calculation to Blueprint while a focused C++ function implements it. Keep one rule. Do not add mock interfaces solely to test an owned component or test copies of the implementation.

Use Unreal’s normal Automation Tests for value/API checks and map/functional tests for integrated gameplay where useful. Tests must isolate state and not depend on ordering or preexisting disk saves. Engine framework: Epic Automation Test Framework.

Select proof based on changed risk

Stats / HealthSame inputs rebuild identically; capacity increases do not heal; decreases clamp; rejected/invulnerable hits do not mutate; lethal once despite callbacks.
MovementTap/hold, buffered released press, coyote walk-off versus committed jump, ceiling, launch observation, landing confirmation, interruption; approximately 30/60/120 FPS.
Combat / ActionStateStale token cannot release a replacement action; hitch crosses active interval; one target attempt per swing including rejection; walls/spatial sweeps; absent animation changes no damage.
Inventory / EquipmentStack split/remainder, duplicate definition with distinct EntryIds, invalid quantities, slot mismatch, equipped-entry removal rejection, complete transaction with no widgets.
Progression / SkillsLarge XP award grants all crossed thresholds once; import grants none again; prerequisite/exclusion/points checks agree with UI query; duplicate purchase rejected.
Abilities / EffectsFailed executor spawn spends no charge; accepted interrupted use retains baseline cost; stale callback rejected; refresh does not stack; travel restore does not replay healing.
World / NPCsApply records before interaction/AI; duplicate identity rejected; unique rewards once; NPC cancellation sets no completion flags; body teardown does not clear persistent facts.
Save / LoadFresh process round trip preserves IDs; corrupt newer generation falls back; unsupported version reports failure; in-flight older revision leaves new changes dirty; death does not load an older save.

For native/reflection changes, run the applicable Editor build/UHT, compile affected Blueprints and validate their defaults/components. For serialized/soft-reference changes, test retained fixtures and a packaged executable. Tests need to verify both accepted behavior and rejection/no partial mutation; compile success alone is insufficient for gameplay invariants.

Do not add elaborate tests for a prose/style-only change or every getter. Run relevant checks once, then broaden when new failures, code changes or unresolved risks justify it. Report what ran and what remains unverified; never infer a runtime pass from static documentation checks.

Use existing test arrangements

The documentation registers L_MovementLab, L_SystemTests and SliceA/B. After explicit area bootstrap arrives, the original lab has no independent area-definition registration. Use the preserved early-phase lab snapshot or the obstacle course inside registered SliceA; run full player/travel scenarios in SliceA/B. L_SystemTests can host harness-only value/content tests under the documented setup. Do not invent new area assets merely to fill an engineering chapter.

Do not exclude development fixtures required by the slice’s catalog/animation references from the cook. Replace those dependencies with approved production content before excluding them. Validate the package actually contains required soft-referenced definitions, maps and presentation.

Logging that explains the failure

Use scoped project log categories when a domain has enough diagnostics to justify one; declare categories in a narrow header and define them once in .cpp. Include owner/asset, stable ID, old/new state, execution token, entry reason, revision and first failed prerequisite when relevant. Do not spam expected rejections every frame or invent one log category per method.

State-transition debugging records the attempted transition, policy result and token. Movement debugging records native mode/velocity, request age, support permission, jump budget and launch observation. Stats debugging lists each source and final evaluation. Save debugging distinguishes requested, captured, completed and still-dirty revisions.

Editor asset validation is suitable for duplicate IDs, invalid grants, schema values, skill cycles and missing references; keep editor tooling out of packaged runtime dependencies. Runtime validation still guards imported/user/content boundaries. See Epic Data Validation.
