Blueprint RPG Architecture and Development Roadmap

Target: Unreal Engine 5.8.3, single-player, Blueprint-first, Paper2D baseline.
Prepared: October 2, 2026.
Scope: The supplied exploration/action-platforming RPG brief, including its mandatory asset-type and parent-class requirements.

The recommendation in one paragraph

Build a responsive player controller first. Then prove a small combat loop, two connected area maps, persistent world changes, checkpoint recovery, and real disk loading. Only after those foundations work should you expand inventory, equipment, skill trees, active abilities, and dialogue. Keep permanent character records in a BP_PlayerProfile Blueprint Class derived from Object, held by BP_GameInstance derived from GameInstance. Keep permanent world records in a separate BP_WorldState Blueprint Class derived from Object. The player Actor is a replaceable BP_PlayerCharacter derived from PaperCharacter → Character; it is not the permanent RPG character record.

Reading this guide

Folder-placement revision: this edition includes an explicit Content/Game/... destination for every planned asset and a one-line folder creation command in Part H.

Parts A–Z define the architecture. Part AA is the executable development sequence, with exact asset-creation tables and tests. Parts AB–AI provide the vertical slice, dependency graph, ownership matrix, detailed call flows, implementation reference, and review gates. Names such as TryClaimWorldReward, RefreshBuildFromProfile, and InitializeArea are functions you implement, not claims that Unreal ships nodes with those names. PART A — Overall architecture

The layers and their ownership

Definitions are authored, immutable content: item properties, skill costs, attack timings, animation sets, and area destinations. They do not contain the player's inventory quantities, purchased skills, or current health.

Session models contain the current truth about persistent progression. BP_PlayerProfile (Object) owns character progression. BP_WorldState (Object) owns meaningful world changes. BP_GameInstance (GameInstance) constructs them, holds strong references, coordinates cross-model transactions, and writes snapshots. It does not execute attacks or AI.

World framework reconstructs the current map. BP_GameMode (GameModeBase) coordinates area initialization and player spawning. BP_AreaRoot (Actor) describes the current area. Both are replaceable when maps change. Unreal's GameInstance survives ordinary level travel; GameMode does not. [E1]

Bodies and gameplay components implement movement, health, attacks, temporary effects, and active execution. The player and enemies own these Actor Components. Their runtime state can be discarded on death while the session models remain intact.

Presentation reads state and submits requests. BP_PlayerController (PlayerController) owns local UI and input routing. Widget Blueprints derive from UserWidget; they never own inventory, skill rules, or save truth.

PART B — Blueprint base-class plan

How to select the class

For a regular class, use Content Browser → Add → Blueprint Class. Select the listed native class, using All Classes when necessary. With Paper2D enabled, search PaperCharacter for the player and enemy base. PaperCharacter is the selected native parent; Character is its native ancestor, not a second asset you create. It supplies a flipbook representation rather than the usual skeletal mesh. [E2]

For a child of your own Blueprint, right-click the existing parent asset and select Create Child Blueprint Class. The register shows the complete relevant chain. For a component, select Actor Component, whose class name is ActorComponent. For a Widget Blueprint, select UserWidget as its parent. Interfaces and Function Libraries use their own Blueprints asset menu entries rather than the ordinary Actor-parent picker.

For BP_PlayerProfile and BP_WorldState, choose Object under All Classes. In BP_GameInstance (GameInstance), use Construct Object from Class, select each compiled class, set Outer to the GameInstance, and assign the return value to a strongly held typed object-reference variable. An Outer alone is not a substitute for keeping the reference. Call your own Initialize function. These objects are not spawned Actors and do not receive Actor BeginPlay. Keep their operations synchronous and free of world timers. [E3]

The tables distinguish an object's runtime lifetime from whether its value data is exported into a save. No table entry means Unreal automatically serializes an entire object graph.

Deliberately omitted classes

No custom GameState or PlayerState initially. Native framework instances can exist; this recommendation is not an instruction to remove them. Their multiplayer/match-oriented responsibilities do not justify additional custom state owners for this single-player, non-seamless-travel architecture. Do not place a second copy of inventory or purchased skills there. Revisit this decision only if the project's assumptions change. [E1]

No custom GameInstanceSubsystem, inventory manager Actor, equipment manager Actor, or manager per feature. The two explicitly constructed Object models solve the actual persistence problem without adding a plugin or native subsystem class. Profile uses function categories for inventory, equipment, leveling, and skills. Extract another object only after a concrete lifecycle or complexity problem appears.

No custom movement-component subclass initially. The inherited CharacterMovementComponent handles collision and movement integration. The player's Blueprint owns input policy and the limited launch/buffer logic described in Part J.

No custom HUD Actor required. BP_PlayerController (PlayerController) creates and binds the UserWidget screens. A HUD subclass would be an additional layer with no necessary responsibility here.

Data Asset instances, enums, structures, Input Actions, mapping contexts, imported art, flipbooks, maps, and the progression table are specified in the phase creation tables and asset register. Those assets are not omitted from the plan merely because they do not appear in this class table.

Why inventory, equipment, progression, and skills are not components here

These systems represent one persistent player record, not independently reusable behavior on many live Actors. Keep their state and synchronous validation in BP_PlayerProfile (Object), organized into function categories: Progression, Inventory, Equipment, and Skills.

A health component attached to the player disappears with that player Actor. Putting the only inventory copy in an equivalent component would require unnecessary snapshot synchronization at every body replacement. Keeping inventory in the profile avoids that problem. Do not try to attach Actor Components to GameInstance; it is not an Actor.

Movement stays in BP_PlayerCharacter (PaperCharacter → Character) because its jump-buffer and coyote logic depend directly on that Character's native movement component. Do not add a custom Blueprint movement-component subclass merely to distribute graph nodes.

Damage acceptance remains in Health; there is no separate damage-manager component. The owning Actor handles movement-specific reactions after an accepted hit.

PART F — Event Dispatchers and communication rules

Commands request changes; events report completed changes. The owner validates a command, changes its state, and then emits events. A widget or animation listener must never be required for a transaction to finish correctly.

Use a typed direct reference for owned components and injected model references. Cast once at a framework boundary, such as obtaining your configured GameInstance. Use interfaces for unrelated target Actors. Use dispatchers for health, inventory, equipment, level, skills, and world-state notifications. Use Gameplay Tags for extensible semantic labels; use enums for a small closed state machine. Definitions are read-only inputs. [E12]

On respawn or screen reconstruction: unbind from the old source, bind to the new source, then request an initial snapshot. Do not depend on receiving an event that occurred before the widget existed. On EndPlay/widget teardown, explicitly unbind long-lived model events and clear Actor references.

For IA_Jump, use Started for a new press and Completed/Canceled for release. Avoid adding a Hold trigger that delays the initial jump. For a single attack per press, use Started, not an unguarded per-frame Triggered event. These event states are part of Enhanced Input. [E5]

When a modal menu, conversation, death, or transition blocks gameplay, clear pending movement/jump/attack intent. Do not rely solely on hiding the widget or removing a context. Test that the control used to close a paused menu can still execute while paused; either handle it through focused UMG input or configure the relevant Input Action to trigger while paused.

Do not add dash, roll, wall-jump, crouch, double-jump, fast-travel, or map-screen actions before their mechanics are approved.

PART J — Player movement architecture

J1. Owner and coordinate convention

BP_PlayerCharacter is a Blueprint Class derived from PaperCharacter → Character. It owns the movement requests, jump buffer, coyote eligibility, facing sign, and movement interruption hooks. Its inherited CharacterMovementComponent remains responsible for movement integration, floor handling, gravity, and collision.

Use world X for horizontal, Z for vertical, and Y for depth. Constrain movement to an XZ plane using normal (0, 1, 0). Use ordinary 3D collision with sensible depth thickness. Keep gameplay collision independent of sprite silhouettes. Position the camera side-on along Y and test its horizontal orientation before authoring rooms.

Do not move the Character each frame with Set Actor Location. Do not let PaperFlipbook frame changes resize the gameplay capsule.

J2. Implement horizontal movement first

Begin with Add Movement Input along world X. Tune MaxWalkSpeed, MaxAcceleration, BrakingDecelerationWalking, friction, and airborne control on the inherited movement component. Disable unwanted orient-to-movement/controller rotation. The player should have an explicit FacingSign of -1 or +1; flip the visual layers, not the camera.

Test starting, stopping, and turning separately. Acceleration and deceleration are not one interchangeable setting. If a turn feels sluggish, adjust the turn/braking policy rather than adding animation delays. Only add a custom braking rule after native settings have been tested.

J3. Use one jump execution path

For this Blueprint-only implementation, use a project function ExecuteJump that calls Unreal's Launch Character node with (0, 0, JumpSpeed), XY Override false, Z Override true. Use that same path for a grounded jump and a legal coyote jump. The node schedules a launch through Character Movement and puts movement into falling. [E7]

This is a deliberate choice: it gives grounded and coyote jumps the same eligibility and variable-height rules without changing native jump-count logic or replacing Character Movement. Do not also bind input to the native Jump function. This implementation owns its one-jump budget explicitly. Native Jump with JumpMaxHoldTime and StopJumping is a valid different approach, but it is not the parallel implementation used here. [E17]

Important variables, grouped on the Character:

MoveAxis: Float
FacingSign: Float
LastJumpPressedTime: Float
bJumpRequestPending: Boolean
bJumpHeld: Boolean
LastGroundedTime: Float
bCoyoteEligible: Boolean
bJumpConsumedUntilLanding: Boolean
bLaunchPending: Boolean
bPendingJumpCut: Boolean
CoyoteWindow, JumpBufferWindow, JumpSpeed, JumpCutMultiplier: Float
RisingGravityScale, FallingGravityScale: Float

Use game time consistently. Starting values around 0.1 seconds for buffer/coyote windows are test parameters, not final balance commitments.

J4. Press, buffer, validate, consume

OnJumpPressed:
    bJumpHeld = true
    LastJumpPressedTime = CurrentGameTime
    bJumpRequestPending = true
    TryConsumeBufferedJump()

TryConsumeBufferedJump:
    require pending request and age <= JumpBufferWindow
    require action state allows jumping
    require not dead / transitioning / in dialogue
    require genuine ground support OR currently valid coyote permission
    require !bJumpConsumedUntilLanding and !bLaunchPending
    consume request BEFORE scheduling the launch
    consume the jump budget; close coyote permission
    set bLaunchPending
    ExecuteJump()
    broadcast your own OnJumpCommitted presentation event

Expiry removes the request. Holding the button does not continuously create requests. A press just before landing can remain buffered; an old press must not cause a jump seconds later.

J5. Coyote time is permission after a walk-off, not an extra jump

While genuinely grounded, maintain LastGroundedTime. When movement changes from Walking to Falling because the player walked off a ledge, open coyote permission only if no jump was committed and no forced launch/interruption caused that departure.

A legal coyote request requires Now - LastGroundedTime <= CoyoteWindow. Consume it when jumping. Close it when it expires, when hit/knockback starts, on death, on teleport/transition, and on any other forced departure.

Do not keep updating grounded time during the frame after a launch was requested while the native movement update still reports the old floor state. The bLaunchPending guard prevents that edge case.

Reset the jump budget only on a genuine landing transition. Do not reset it every frame that a stale Is Moving on Ground query happens to return true. A character spawned in the air must start with no invented recent-ground timestamp.

J6. Variable jump height and the same-frame release edge case

On release, set bJumpHeld = false. If the committed jump is still rising, request a one-time cut to its positive vertical velocity, for example Velocity.Z * JumpCutMultiplier. Apply that with Launch Character, preserving XY and overriding Z. Never apply the cut to negative falling velocity.

Because a launch is applied on a later movement update, a press and release can happen before positive vertical velocity is visible. In that case, retain bPendingJumpCut and apply it after the launch is observed. The same rule handles a buffered press released before landing: the buffered jump should be a short jump, not a maximum-height jump.

Mark the cut consumed so it does not repeat every frame. Do not call both jump-hold force and jump-cut logic.

J7. Rising, apex, falling, and landing

Use native movement/floor state and vertical velocity as the source of truth. Rising and falling can have different configured gravity scales. Treat the apex as a small presentation band around zero vertical velocity, not a third physics mode or a mandatory movement lock.

Use OnLanded for impact information and a landing presentation request. Unreal still reports Falling during OnLanded. Re-arm and consume buffered jumps when the movement-mode change confirms Walking, or at the next controlled movement update after that confirmation. Do not reject a valid buffered jump simply because Is Falling was checked too early inside OnLanded. [E8]

A landing animation must not delay newly valid movement or jumping. A buffered jump can interrupt the landing presentation immediately.

J8. Interruption and animation output

BPC_ActionState (ActorComponent) controls whether jumping/movement/attacking is currently allowed. The Character responds to its changes by clearing buffers or applying movement restrictions. Prefer an explicit capability query such as CanMove, CanJump, CanAttack rather than a collection of unrelated booleans set by several systems.

Send S_AnimationSnapshot, a Blueprint Structure with no parent class, to BPC_FlipbookAnimator (ActorComponent). The snapshot contains movement facts and current action timing. Animation does not decide whether the jump happens.

J9. Movement completion tests

Run the same obstacle course at approximately 30, 60, and 120 frames per second, with both short taps and long holds. Include starting/stopping, reversal, small ledges, ceiling hits, ground-to-air transitions, short falls, and room-boundary camera movement.

Specifically verify: a coyote jump once within the window; rejection outside it; no second airborne jump; no coyote jump after knockback; buffering just before landing; buffer expiry; a press-and-release in one frame; release before a buffered landing; no jump from an old request after dialogue; and immediate control after landing.

Completion criterion: the controller is enjoyable with temporary art and no rewards. Do not use leveling, combat spectacle, or camera shake to conceal poor movement.

PART K — Animation architecture

Use Paper2D flipbooks for the baseline. BPC_FlipbookAnimator is a Blueprint Actor Component derived from ActorComponent, not an Animation Blueprint derived from AnimInstance. BPDA_AnimationSet is a Blueprint Class derived from PrimaryDataAsset. Its content instances map E_AnimState values to Paper2D Flipbook assets (PaperFlipbook). Sprites are Paper2D Sprite assets (PaperSprite) created from imported Texture2D content; none of those content assets requires choosing a Blueprint parent.

The animator receives S_AnimationSnapshot values and action events. Presentation priority is Death, Hit, active Attack/Ability presentation, then locomotion. A normal locomotion update must not overwrite a death or hit clip. Conversely, a landing clip must be interruptible by a newly accepted jump or attack.

Keep gameplay time authoritative. Combat selects its definition, starts windup, applies hits during the active interval, and ends recovery whether or not a visual clip exists. The animator plays a compatible clip using the same action timing. A flipbook-completion event may report cosmetic completion; it must not grant damage, complete a purchase, or decide whether the character is alive. PaperFlipbookComponent exposes playback-position controls and non-looping completion events in Blueprints. [E9]

Layered visible equipment

The player already has the inherited Paper2D Sprite. Add native PaperFlipbookComponent instances named HeadLayer and BodyLayer, with a native SceneComponent named EquipmentRoot for visual placement. These are component instances inside BP_PlayerCharacter (PaperCharacter → Character), not additional custom Blueprint classes.

An equipped item's BPDA_ItemDefinition (PrimaryDataAsset) references an appearance instance of BPDA_AnimationSet (PrimaryDataAsset). The animator receives the resolved set. It never checks ItemId == SomeHelmet in a graph.

Use one animation clock and one selected state for body and clothing. The animator can stop autonomous playback on the layered components and explicitly set each layer's playback frame/position from that shared clock. Do not expect independently playing flipbooks to remain synchronized after mid-animation equipment changes. [E9]

Author compatible layers with the same pivots, scale, frame timing, facing convention, and frame count for a shared state. Use small Y-depth offsets or an intentional material/sort policy; verify the order when facing both directions. All visual layers have collision disabled. A missing equipment clip should hide/fallback deliberately, not reuse a mismatched run cycle during a death animation.

Test equipping during movement, jumping, attacking, hitstun, and death; test loading with equipment already owned; test low frame rates. Make layer-layout validation part of content checks.

PaperZD decision

PaperZD offers an animation-graph workflow for 2D animated characters. That can reduce authoring friction as an animation catalog grows. It is not necessary for this baseline: the built-in alternative is the explicit flipbook coordinator above. The plugin's own listing also calls out packaging/toolchain considerations. This guide does not assume a verified 5.8.3-compatible PaperZD installation and introduces no PaperZD-dependent class. Re-evaluate it only after the built-in animation slice reveals a concrete authoring problem. [E16]

PART L — World, room, and area architecture

Primary approach: area maps containing several rooms

Use one ordinary Level/Map asset (World) per area, with several connected rooms inside it. Group areas into biomes by BiomeId in BPDA_AreaDefinition (PrimaryDataAsset). A biome does not require a new manager class or a seamless persistent world.

Within an area, rooms are geometry plus BP_RoomVolume (Actor) instances. Crossing a room boundary updates room/camera context and discovery; it does not automatically reload a map. Between areas, BP_AreaTransition (Actor) requests Unreal's Open Level (by Object Reference) using the area's soft World reference. [E13]

This is simpler than starting with World Partition or dynamic streaming for a game that does not require one seamless world. Traditional sublevel streaming is Blueprint-compatible and remains a future option when a specific area's size/loading time justifies it; it would add load/unload readiness and Actor-lifecycle work now. [E14]

Map setup and bootstrap

Each gameplay area map has exactly one BP_AreaRoot, a Blueprint Class derived from Actor, and one or more BP_SpawnPoint instances, from a Blueprint Class derived from PlayerStart. A spawn is addressed by {AreaId, SpawnId}, not by an Actor reference stored in a save.

BP_GameMode (GameModeBase) owns a runtime Map<Name, BP_SpawnPoint reference> for the current area. Configure one spawning route: the final gameplay GameMode uses Default Pawn Class = None and spawns/possesses BP_PlayerCharacter (PaperCharacter → Character) explicitly after readiness. Do not combine manual spawning with an automatic default-pawn spawn. Early phase-0 automatic spawning is replaced, not supplemented, in phase 3.

Bootstrap waits for explicit prerequisites: valid session models, loaded required definitions, registered AreaRoot and PlayerController, and a validated destination. Persistent Actors default to non-interactive/unready. The bootstrap calls their persistence initialization, applies records, resolves the spawn, then creates and initializes the player body. Actors that subscribe late must query the current readiness flag as well as bind to its event.

Do not rely on arbitrary Delay(0.2) nodes or a presumed BeginPlay order. BeginPlay may register participants, but it must not overwrite a persistent state already applied by explicit initialization.

Destination and return locations

Each transition has TargetAreaId and TargetSpawnId. The reverse connection has its own authored destination. Do not guess the return position from the player's last transform. Each area's default SpawnId is a validated fallback; the project also has a validated starting-area destination.

A gate asks for its required progression/capability condition. A persistent shortcut's open record overrides its original closed presentation. Checkpoints record safe spawn identities, not a current animation or an arbitrary airborne transform.

Deliberate reset policies

Situation Persistent models Player health/effects/recharge Ordinary enemies
Move between rooms in same area Retained Retained Remain as currently simulated
Travel to another area Retained Handed off as runtime values Newly loaded area's ordinary enemies start fresh
Death recovery Retained, never rolled back Full recovery health; clear temporary effects and recharge state under this initial recovery policy Reload checkpoint area and reset ordinary enemies

The recovery policy is a proposed baseline that can be changed centrally; it is not an added loss-of-progression mechanic. Normal area travel must not accidentally behave like death recovery. Capture current health, remaining effect durations, and remaining recharge/charges in S_RuntimeTravelState before teardown. Restore effects/build/max health before restoring and clamping current health. Freeze these remaining durations during the loading handoff. Clear the handoff after the new body becomes authoritative.

PART M — Interaction system

The participating assets are BPC_Interaction (Blueprint Actor Component → ActorComponent), BPI_Interactable (Blueprint Interface asset; no parent), BP_InteractableBase (Blueprint Class → Actor), and BP_NPCBase (Blueprint Class → Actor, implementing the same interface without enemy inheritance).

A small overlap region or query obtains candidate Actors. Normalize component overlaps to their owning Actor, filter for the interface, reject invalid/out-of-range targets, and select a deterministic nearest/facing-preferred candidate. Refresh when candidates change and, while candidates exist, at a modest controlled rate if needed; do not scan every Actor in the world on Tick.

BPC_Interaction selects candidate
-> BPI_Interactable.GetInteractionInfo(player)
-> HUD receives the prompt through OnTargetChanged
-> player presses Interact
-> BPC_Interaction revalidates range, readiness, and target
-> BPI_Interactable.Interact(player)
-> target requests its own operation
-> model transaction commits when persistence is involved
-> target/model events update presentation

Revalidate on the actual press: a prompt is not a reservation. If an item disappears or a door changes state, clear the stale target. A non-interactable or failed request must return failure without consuming items or changing flags.

The interaction component does not know whether the target is a checkpoint, NPC, or pickup. Each target owns its behavior. Persistent one-time effects go through the GameInstance transaction facade; temporary-only interactions do not need a save operation.

PART N — Combat architecture

Start with one grounded attack, one airborne-compatible attack definition, a dummy, and one hazard. Use the exact classes in the phase-2 table: BPC_Combat, BPC_Health, BPC_Stats, and BPC_ActionState are ActorComponent-derived Blueprint Actor Components; BP_TrainingDummy and BP_Hazard are Actor-derived Blueprint Classes; BPI_Damageable is a Blueprint Interface asset.

Execution order

The Controller sends attack intent to the body. Combat verifies health, action permission, grounded/airborne eligibility, and definition validity. It acquires an action token from ActionState, snapshots any stats that should remain constant for that attack, and starts Windup → Active → Recovery. BPDA_AttackDefinition, a Blueprint Class derived from PrimaryDataAsset, provides those timings and the hit-shape/scaling data. Its phase-2 DA_ instances are listed in Part AA.

Use one authoritative elapsed-time calculation in Combat. Enable its update only while an attack is running. Determine whether the interval between the previous and current update intersects the active interval; this prevents a low-frame-rate update from skipping an entire short active window. Query at active-window entry, not only on a later overlap event.

Hit detection and hurtboxes

Keep a consistent gameplay hurtbox independent of the displayed sprite; the Character capsule can serve initially. Define a box/swept box in front of the attacker in XZ, with explicit Y thickness. Follow its previous/current transform during the active window. Query only suitable target object types, filter with BPI_Damageable, and check world obstruction so attacks do not hit through blocking walls unintentionally.

Normalize multiple hit components to one damageable Actor. Track a Set of processed Actor references per attack instance. Decide once whether an invulnerability rejection counts as processed; the recommended simple policy is one damage attempt per target per swing. A new swing gets a fresh set and token.

Damage application

S_DamageSpec and S_DamageResult are Blueprint Structure assets; no parent. The source sends raw damage, source/instigator references, combat side, attack token, and optional knockback. Runtime Actor references are acceptable here because this packet is never serialized into a save.

The target Actor's interface implementation delegates to Health. Health rejects dead/unready/invulnerable targets, obtains the final defensive value from Stats, applies the chosen mitigation calculation once, clamps health, and emits an accepted-hit event. The owning Character performs movement-specific knockback and requests hitstun. Health emits death once when crossing to zero.

Use this one damage pipeline. Do not also call native Apply Damage for the same hit unless you deliberately replace the interface pipeline with a native-damage adapter. Mixing two entry paths is a common double-damage bug.

Interruption, projectiles, and hazards

On interruption, release only the matching action token, stop hit queries, invalidate callbacks from the canceled execution, and notify presentation. Never let a delayed recovery event from attack A unlock the input lock belonging to attack B or death.

BP_ProjectileBase is a Blueprint Class derived from Actor. Add a native SphereComponent collision root and ProjectileMovementComponent; do not create a custom movement-class asset. Set owner/instigator, exclude the shooter, configure swept collision, and guard consumption so a projectile cannot apply the same impact twice. Test fast projectiles against thin geometry.

BP_Hazard (Actor) uses the same damage interface. For a sustained damaging region, maintain a per-target repeat deadline and remove invalid targets; do not apply damage every overlap callback/frame without an explicit repeat policy.

Enemy rewards are emitted by the enemy's once-only death/reward handling, not by the animation and not by the attacker's HUD.

PART O — Enemy architecture

Use BP_EnemyBase, a Blueprint Class derived from PaperCharacter → Character, with Stats, Health, ActionState, Combat, and the animator. Create BP_Enemy_MeleeBasic and BP_Enemy_RangedBasic as child Blueprint Classes of BP_EnemyBase → PaperCharacter → Character. Use BP_EnemyAIController, a Blueprint Class derived from AIController, and assign it as the enemy's AI Controller Class with auto-possession appropriate for placed and spawned enemies.

The base owns component wiring, receiving damage, death handling, interruption, facing, and the reward guard. A child overrides only attack selection or movement-intent policy that actually differs. Tuning comes from BPDA_EnemyDefinition (PrimaryDataAsset) instances. A new health value or projectile speed is not a reason for another inheritance layer.

Default AI: a small Blueprint state machine

Use E_EnemyBrainState, a Blueprint Enumeration asset with no parent, for Idle, Patrol, Approach, WaitingForAttack, and Dead. The AIController owns target selection and decisions. Combat owns windup/active/recovery timing, so the AI waits for its result rather than running a second competing telegraph timer.

A think timer can update detection and decisions around every 0.1 seconds. The body must still apply its current movement intent every simulation frame; calling Add Movement Input only once every 0.1 seconds can produce pulsed movement. Check a floor probe ahead and a wall probe before walking. Use simple range/line-of-sight tests and reachable attack geometry; do not assume a 3D NavMesh will solve 2D platform traversal.

Behavior Trees or State Trees become useful when multiple enemy behaviors require richer reusable task orchestration. They are not the primary recommendation for this initial two-family slice. No custom BT Task or StateTree task assets are required now.

Ordinary enemies get fresh runtime state after an area reload. A unique enemy additionally has BPC_PersistentState (ActorComponent) with an authored stable ID. If its completion record is present, suppress the encounter before AI/reward execution starts. Completing it updates its record and reward in one GameInstance transaction, so reloading cannot grant the same unique reward again.

PART P — Stats architecture

BPC_Stats is a Blueprint Actor Component derived from ActorComponent. It owns the final calculated cache for the current body. Base player values come from a BPDA_CharacterDefinition (PrimaryDataAsset) instance; enemy values come from BPDA_EnemyDefinition (PrimaryDataAsset) instances. S_StatBlock and S_StatModifier are Blueprint Structures, no parent. E_StatId is a Blueprint Enumeration, no parent.

For each stat, use this deliberately simple evaluation policy:

FlatValue = Base
          + CumulativeLevelGrowth
          + sum(EquipmentFlat)
          + sum(PassiveSkillFlat)
          + sum(TemporaryEffectFlat)

FinalValue = ClampForStat(
    FlatValue * (1 + sum(AllAdditivePercentageModifiers))
)

With no percentage modifiers, this is exactly the additive model in the brief. Define percentage ordering once; do not let each item decide its own formula. Initially MaxHealth, AttackPower, and Defense are enough to prove the architecture. They are implementation examples, not a final stat catalog. Do not automatically scale platforming movement parameters with RPG level.

The player body supplies a complete build snapshot assembled from Profile + definitions and temporary effects. Recalculate on spawn, level change, equipment change, skill purchase, and effect application/expiration. Do not recalculate on every Tick. Every source has an ID such as Equipment:<EntryId> or Effect:<Handle> for debugging; replacing a source cannot add its bonuses twice.

Maximum health belongs to Stats. Current health belongs to Health. Health queries the authoritative current maximum through its initialized Stats reference. On max-health changes, use CurrentHealth = Min(CurrentHealth, NewMaxHealth) as the initial policy. Increasing max health does not silently heal the player, and equipping/unequipping cannot become a free-heal loop.

Profile never reads Stats to decide what it owns. Stats never modifies the inventory or buys skills. The composition root on the player assembles inputs, which avoids a circular dependency between equipment, skills, buffs, and stat calculation.

PART Q — Leveling and progression

BP_PlayerProfile is a Blueprint Class derived from Object. Its Progression category owns TotalXP and UnspentSkillPoints. DT_LevelProgression is a Data Table using the Blueprint Structure S_LevelProgressionRow; neither asset involves selecting a Blueprint parent.

Each row contains Level, TotalXPRequired, CumulativeStatGrowth, and SkillPointsAwardedOnEnteringThisLevel. TotalXP thresholds must be increasing. Level is a derived value/cache: the greatest unlocked row. The save may carry CachedLevel for inspection/migration, but TotalXP plus the versioned progression definition remains the normal calculation source. This is not two competing authoritative values.

GrantXP(Amount) rejects negative awards, captures the previous level, increments TotalXP once, then processes every crossed level and grants the corresponding points exactly once. Bound the traversal by the table's row count. At maximum level, choose and document whether TotalXP continues accumulating; the simple default is to retain it while level remains capped.

Broadcast progression/UI changes after the complete operation, and emit one build-refresh event. On loading, recompute the level without replaying level-up rewards. A balance update that changes thresholds needs an explicit content-version migration, not accidental point grants during import.

Enemies supply an S_Reward value through GameInstance. Profile does not cast to melee enemies, bosses, or pickups. The same reward function can handle any valid progression source.

PART R — Inventory

Use BP_PlayerProfile, a Blueprint Class derived from Object, for authoritative inventory operations. BPDA_ItemDefinition is a Blueprint Class derived from PrimaryDataAsset. S_InventoryEntry is a Blueprint Structure, and E_ItemKind is a Blueprint Enumeration; those two have no parent class.

An item definition says what an item is. An entry says what this player owns: {EntryId: Guid, ItemId: Name, Quantity: Integer}. Stackables merge only with compatible entries up to the authored stack limit. Equipment initially uses quantity 1 per entry, so duplicate helmets have different EntryIds and equipment slots can identify the exact owned copy. No durability, random affixes, or rarity framework is required.

Expose TryAddItem, CanRemoveItem, TryRemoveItem, FindEntry, and CanUseItem. Validate IDs and quantities before mutation. Do not remove an equipped entry without also resolving its equipment slot in the same operation; the simplest initial rule is to reject direct removal until it is unequipped.

For consuming an item, validate both ownership and the live effect target. The Controller/body asks the GameInstance transaction facade to coordinate Profile removal and runtime application. The non-latent commit must be designed so that after successful validation it cannot partially fail. Never remove the item, wait for an animation, and only then discover that the effect is invalid.

Persist entries, not pickup Actor references or copied item definitions. WBP_Inventory is a Widget Blueprint derived from UserWidget; it reads entries, resolves display definitions, and requests operations. Profile emits OnInventoryChanged only after a committed change.

PART S — Equipment

Keep equipment as a distinct category of BP_PlayerProfile (Object) rather than a second inventory. The authoritative representation is a Map<E_EquipmentSlot, Guid>, where each Guid must resolve to an owned S_InventoryEntry. E_EquipmentSlot is a Blueprint Enumeration asset, and S_InventoryEntry is a Blueprint Structure asset; no parent classes apply.

TryEquip(EntryId, Slot) verifies ownership, item kind, slot compatibility, and current operation permission. It replaces that slot's EntryId without consuming the owned item. TryUnequip(Slot) clears the reference, leaving the item owned. Do not duplicate the item into an equipment-only inventory.

WBP_Equipment (UserWidget) requests equip
-> BP_PlayerProfile (Object) validates and commits slot mapping
-> OnEquipmentChanged for UI
-> OnBuildChanged for the live player adapter
-> BPC_Stats (ActorComponent) recomputes equipment contribution
-> BPC_FlipbookAnimator (ActorComponent) switches resolved visual sets
-> GameInstance marks/saves the committed persistent revision

The player's adapter can refresh stats and visual layers in the same synchronous update. Avoid two independent systems each adding the same equipment modifier. On load, prune or quarantine invalid slot references with diagnostics before rebuilding stats; never dereference a missing inventory entry.

PART T — Skill tree

BPDA_SkillDefinition is a Blueprint Class derived from PrimaryDataAsset. BP_PlayerProfile is a Blueprint Class derived from Object. E_SkillAvailability is a Blueprint Enumeration asset, no parent. WBP_SkillTree and WBP_SkillNode are Widget Blueprints derived from UserWidget.

A skill definition contains SkillId, Cost, PrerequisiteSkillIds, optional ExclusiveGroupId, optional explicit incompatible skill IDs, passive modifiers, granted ability IDs/capability tags, and a UI position. Definitions describe the graph; Profile stores only purchased IDs and unspent points. Derive child edges from prerequisites rather than maintaining two independently editable graph directions.

GetSkillAvailability(SkillId) returns Purchased first, otherwise Locked with a reason when prerequisites/exclusivity/points fail, otherwise Available. TryPurchaseSkill calls the same validation again at commit time, deducts points, and inserts the ID in one synchronous operation. A disabled button is not authoritative validation.

Rebuild passive modifiers from the purchased set. Derive ability unlocks from the purchased definitions; do not persist a second purchased-ability list for the same grants. The test root and mutually exclusive branch definitions in phase 8 prove graph logic, not final specialization design.

Validate missing prerequisite IDs, cycles, negative costs, nonexistent ability grants, and contradictory exclusivity groups. A mandatory route must not depend on an irrevocably excluded specialization. Use common/nonexclusive access, sufficient guaranteed reachable points, or an authored alternative route; test every allowed specialization against required gates. This is a content constraint to validate, not a reason to invent a respec or traversal mechanic.

PART U — Active ability framework

Primary choice: a small Blueprint runtime, not GAS

GAS provides attributes, gameplay effects, ability tasks, and a comprehensive ability execution framework. Epic's documented custom AttributeSet workflow uses native declarations and setup; it should not be presented here as a frictionless, purely Blueprint foundation. For this single-player project, the extra integration does not solve a demonstrated requirement that justifies making it foundational. [E15]

Use BPC_Abilities, a Blueprint Actor Component derived from ActorComponent, and BP_AbilityBase, a Blueprint Class derived from Actor. A per-use executor Actor is a pragmatic Blueprint choice because world traces, timers, and cancellation are straightforward there. It is hidden/non-colliding unless a particular ability needs representation; projectile Actors remain separate.

BPDA_AbilityDefinition is a Blueprint Class derived from PrimaryDataAsset. A definition references the executor subclass, recharge/cooldown settings, scaling/targeting data, and provided capability tags. S_AbilityContext is a Blueprint Structure, no parent, with runtime source/target/context values.

Activation transaction

TryActivate(AbilityId):
  validate unlocked definition, live body, target, charges, and action permission
  acquire an action token
  resolve/load executor class before committing gameplay activation
  spawn executor with no automatic effect in BeginPlay
  if spawning fails: release that token and return failure
  commit charge/cooldown consumption
  call the executor's explicit StartAbility(Context)
  broadcast runtime ability-state change

The executor calls FinishAbility exactly once. Interruption calls CancelAbility, clears timers/hit queries, and ends only its matching token. The component maintains active executor references and destroys canceled executors during death or normal map teardown. Use an activation-generation token so stale callbacks cannot complete a later ability.

The initial policy consumes cooldown once activation is accepted; missing a target or being interrupted afterward does not silently refund it. Treat that as a central configurable rule rather than scattered special cases.

Recharge and ownership

Start with one charge by default. The definition may specify additional charges only where actual recharge behavior needs them; the runtime ledger holds available charges and a next-recharge deadline. Process elapsed intervals correctly, including more than one recharge completion during a delayed update. No mana/energy resource is added by this plan.

Use game-time clocks. Pause freezes progression of these timers. Normal area travel exports remaining recharge and charge counts; it does not reset them. Death/disk recovery uses the explicit clean-recovery policy. None of the exact execution, targeting, or timer state is persisted to disk.

For enemy targets, the executor calls BPI_Damageable, a Blueprint Interface asset. For world targets, it calls BPI_AbilityTarget, also a Blueprint Interface asset. BP_Ability_TestPulse is a child Blueprint of BP_AbilityBase → Actor, and BP_AbilityTestReceiver is a Blueprint Class derived from Actor. They prove both routes and remain test-only.

World gates query the current derived capability/unlock set, not an arbitrary animation state or the name of a development ability. UI observes OnAbilityStateChanged; a cooldown progress display can animate from a notified deadline without making widgets authoritative timer owners.

PART V — Buffs and temporary effects

BPC_StatusEffects is a Blueprint Actor Component derived from ActorComponent. BPDA_EffectDefinition is a Blueprint Class derived from PrimaryDataAsset. S_ActiveEffect is a Blueprint Structure asset with no parent class.

A definition contains an ID, a duration, stat modifiers, and an immediate health effect when needed for a consumable. A runtime effect contains its definition ID, unique handle, and remaining duration/deadline. Keep definitions immutable. An initial same-effect rule is refresh duration, do not stack magnitude; do not build a general stacking-rule language until a real effect requires it.

Applying/removing/expiring a timed modifier requests one Stats recalculation. The modifier source is the effect handle, so expiration removes the correct source. Never add a temporary bonus directly into permanent base stats and try to subtract it later.

Process expiry with a controlled component timer/update while effects exist. Clear it when empty. Use game time so menus and deliberate pause behave consistently. Export remaining durations on normal area travel; restore them before final health clamping. Clear effects on the chosen death/disk-recovery path.

Immediate healing goes to BPC_Health (ActorComponent), not to MaxHealth. A timed max-health buff goes through Stats. Validate both paths before consuming an inventory item. Gameplay does not wait for a consumable animation to finish before determining whether the use transaction succeeded.

PART W — Checkpoint, death, and respawn

Exact participants

BP_Checkpoint is a child Blueprint of BP_InteractableBase → Actor. BPC_Health and BPC_ActionState are ActorComponent-derived Blueprint Actor Components. BP_PlayerCharacter derives from PaperCharacter → Character. BP_PlayerController derives from PlayerController. BP_GameMode derives from GameModeBase. BP_GameInstance derives from GameInstance. BP_PlayerProfile and BP_WorldState derive from Object.

Complete lethal-damage sequence

  1. Health accepts a valid hit, subtracts damage, and clamps to zero. Its lethal guard emits OnDied once.
  2. The body makes Dead the highest-priority action. Stop movement intent, clear jump/attack buffers, stop active hit checks, cancel abilities, prevent interaction, and clear transient target references.
  3. Controller/UI stop accepting gameplay requests. Presentation begins death animation/fade. Gameplay death has already happened; a missing visual completion must not prevent recovery.
  4. GameMode starts one guarded recovery request. Use a bounded presentation delay or explicit presentation-complete callback with a fallback, not an unguarded chain of delays.
  5. GameInstance keeps the current Profile and WorldState objects. It does not call Load Game from Slot. Any newly earned XP/items remain in those models.
  6. Resolve WorldState's active checkpoint {CheckpointId, AreaId, SpawnId}. Without one, use the validated starting-area spawn. An invalid destination follows the documented safe fallback chain and reports an error.
  7. Finish/flush any pending persistent save before the travel handoff. Prepare an E_EntryReason.DeathRecovery transition, with no normal-travel health/effect snapshot.
  8. Reload the checkpoint area, even when it is the same map, so ordinary enemies and temporary world Actors reset predictably. Persistent records are reapplied before gameplay resumes.
  9. GameMode spawns and initializes a new player body. Bind Profile, rebuild equipment/passive/level stats, derive ability unlocks, clear temporary effects and execution state, and set health to the current final maximum under the baseline policy.
  10. Possess the body, bind HUD/components, show the correct equipment, clear the pending transition, fade in, and reopen gameplay.

Checkpoint activation records a stable ID and a safe area/spawn destination, marks it visited, changes the active checkpoint, and requests a save. It does not have to refill health on activation; that additional design choice is not assumed here.

Progression survives because its owner was never destroyed or reloaded from an older disk snapshot. This remains true even when the dead player Actor, Controller, and GameMode are all replaced by ordinary level travel.

PART X — Persistent world state

Stable-ID policy

Use an instance-editable authored Name on BPC_PersistentState, a Blueprint Actor Component derived from ActorComponent. Example values are Area.Forest01.Room02.Shortcut01 and Area.Forest01.Room02.Pickup01. These are illustrative names, not a commitment to a forest biome.

The ID is a durable content key. Do not derive it from an Actor label, runtime object name, array position, memory address, or spawn order. Do not generate a new Guid in BeginPlay or Construction Script every time the actor is loaded. Do not assume an editor Actor GUID is a suitable Blueprint-accessible packaged-game save ID.

Duplicating a placed persistent Actor also duplicates its variable values. Assign a new ID and validate duplicates. Never automatically repair duplicate IDs during load; that could attach old player progress to the wrong object. An ID rename after release requires a migration/alias, not just a Content Browser rename.

World records

BP_WorldState, a Blueprint Class derived from Object, owns Map<Name, S_WorldObjectRecord>. S_WorldObjectRecord is a Blueprint Structure with no parent, containing a primary StateTag and a small set of named flags when one object needs several remembered facts. Discovered rooms/areas and global narrative flags have their own sets. The active checkpoint has its own typed record.

A missing object record means the authored default. An existing record means the actor must reconstruct that state. Ordinary enemies have no persistent record unless explicitly marked as unique. A runtime Actor's visual state is a projection of the record, not another independent persistent owner.

Initialization sequence

Actor exists but is not gameplay-ready
-> BPC_PersistentState validates stable ID
-> receives BP_WorldState reference from explicit area initialization
-> queries ObjectId
-> calls owner BPI_PersistentActor.ApplyPersistentRecord(record, found)
-> actor updates collision/visibility/availability without granting rewards
-> component binds to changes for its ID
-> area readiness allows gameplay

ApplyPersistentRecord must be idempotent. Applying Collected hides/disables the pickup without adding the item again. Applying Opened updates a door's blocker without re-running a switch interaction. Applying Completed suppresses a unique encounter before its AI/reward path starts.

A switch transaction can update an unloaded door by ID. If the door is loaded, its component observes the model event and applies the new record. If it is not loaded, it will query the record later. No cross-map Actor reference is needed.

Validation must cover all authored maps, not only the current one: duplicate/missing IDs, broken target IDs, missing spawns, invalid checkpoint destinations, and renamed content. In the baseline Blueprint test workflow, load each map in a controlled validation pass and combine its reported ID manifest. Do not claim one Get All Actors query proves uniqueness across unloaded maps.

Ability unlocks are reconstructed from purchased skills; they are not saved twice. Base stats come from versioned definitions; derived stats are not stored as permanent truth. Recovery is a snapshot derived from the active checkpoint or start fallback, not an independently mutable second checkpoint system.

Do not save current attack frames, animation state, jump buffers, current AI execution, dialogue cursor, Actor references, component references, temporary projectiles, or a precise airborne transform. The player's current health/effects/cooldowns are runtime state under the selected recovery policy, not a promise to restore the exact instant.

The live model is not the save object

GameInstance constructs Profile and WorldState through Construct Object from Class, sets their Outer to GameInstance, and also stores explicit object-reference variables to keep them referenced. Initialize them through your own synchronous methods; plain Objects do not get an Actor's automatic BeginPlay lifecycle. [E3]

To save, GameInstance uses Create Save Game Object, copies model values into a fresh snapshot, and calls Async Save Game to Slot. The engine supplies the serialization/I/O mechanism; your graphs supply the state selection and reconstruction. The async completion has a success result that must be checked. [E10, E11]

Transaction rule

For a one-time pickup or unique encounter:

validate source record is not already committed
validate all item/XP grants and destination state changes
enter a non-reentrant, non-latent transaction
commit Profile values + WorldState values
increment one session PersistentRevision
broadcast notifications from the complete new state; reject reentrant mutations
exit transaction
request save

No dispatcher, latent node, asset load, animation wait, or disk write belongs between those commits. Prepare required definitions before entering. A failed validation changes neither inventory nor world state. Guard against nested mutation requested by an event listener while another transaction is committing.

Default save strategy

Use one logical player slot backed by two alternating physical generations, for example Profile0_A and Profile0_B. Each successful generation has an increasing SaveSequence. Write the next snapshot into the older/unused generation; leave the other generation untouched. This is a straightforward fallback against an interrupted or invalid latest write, not a guarantee against every storage failure.

Request saving after meaningful persistent transactions: item/reward acquisition, consumption, equipment/skill changes, checkpoints, shortcut completion, unique encounters, and discovery changes. Coalesce requests while an earlier write is active. Do not save on Tick or on every health change.

Maintain PersistentRevision, LastSavedRevision, bSaveInFlight, InFlightSnapshot, and a pending-save flag. Capture a fresh immutable snapshot for a revision and keep it referenced until completion. If newer changes happened while it was writing, immediately schedule another snapshot afterward. Never clear all dirty state merely because an older revision finished.

Allow only one save/load operation at a time for this logical slot. Settle writes before loading, switching profiles/new-game state, area teardown, or final quit; the Blueprint async node warns that simultaneous loading and saving is not supported on every platform. [E11]

On failure, retain dirty state, keep the last valid generation, and expose Retry/continue-with-unsaved-progress feedback. Do not show a saved confirmation merely because a request was queued. A crash before a new snapshot completes can still lose changes since the last successful snapshot; ordinary in-game death does not.

Loading order

Load candidate generations sequentially, validate class/version/content, and select the highest valid SaveSequence. A missing slot means New Game only when it is genuinely absent. A corrupt or unsupported newer save should be reported and must not silently overwrite the old files.

Import values into the session models while gameplay is blocked. Run version migrations, validate item/skill IDs, quantities, slot references, checkpoint/map destinations, and stat/progression consistency. Preserve diagnostic information about removed content rather than silently turning it into a different item.

Resolve recovery, open the target map, apply persistent world records, reconstruct the player build/unlocks/appearance, restore clean recovery health, bind UI, and then enable gameplay. There is no requirement to reproduce exact enemy positions or conversations.

Changing Blueprint Structure definitions can affect saved compatibility. Stabilize the schema early, use explicit versions and fixture saves, and test migration in a packaged executable before distributing updates. Save flags on variables are not a substitute for this explicit snapshot and restore flow.

PART Z — UI architecture

All UI assets in this plan are Widget Blueprints derived from UserWidget: WBP_HUD, WBP_SaveStatus, WBP_Inventory, WBP_Equipment, WBP_SkillTree, WBP_SkillNode, WBP_Abilities, WBP_Dialogue, WBP_PauseMenu, and WBP_MainMenu.

BP_PlayerController (PlayerController) creates/removes them and supplies typed references. The HUD observes the current body's Health/Stats and the persistent Profile. Inventory/equipment/skills observe Profile. Save status observes GameInstance. Dialogue displays the Controller's transient conversation session.

Use bind then pull an initial snapshot. On pawn replacement, disconnect from the old body and connect to the new one. Model-backed screens should bind only once per instance and unbind on teardown. Do not use persistent model delegates as accidental strong-reference storage for old world Actors/widgets.

Use change events for discrete state. A cooldown bar may run a local visual interpolation/timer after a notified recharge start; that is different from polling the entire game state every frame. Health/inventory/skills need no Tick-based binding loops.

The widget asks GetSkillAvailability or TryEquip; it does not duplicate their rules. Invalid requests return a reason that can be shown to the player. A hidden or unloaded widget must not stop progression, rewards, saving, or death recovery.

Pause/menu and dialogue entry must set input mode and focus explicitly, and closing must restore them and clear stale gameplay intent. Under this initial single-player dialogue policy, a modal conversation pauses world simulation; it does not create a separate combat mode or quest system. Clear the transient conversation on travel/recovery without granting a completion flag unless the authored completion event actually occurred.

-> BP_PlayerProfile (Object) + BP_WorldState (Object): ImportSnapshot
-> GameInstance: resolve recovery, open map
-> BP_GameMode (GameModeBase): apply world records, spawn/init/possess
-> BP_PlayerController (PlayerController): bind HUD, enable input

7. Saving

BP_GameInstance (GameInstance): RequestSave
-> if write active: mark pending and return
-> Create Save Game Object [engine node]: BP_SaveGame (SaveGame)
-> BP_PlayerProfile (Object): ExportSnapshot
-> BP_WorldState (Object): ExportSnapshot
-> snapshot Header/Recovery populated from the same committed revision
-> Async Save Game to Slot [engine node]
-> Completed: inspect Success
-> successful captured revision becomes saved
-> schedule a fresh snapshot if a newer revision exists

PART AF — Blueprint implementation reference

This is an architectural API reference, not a promise that the following custom functions already exist as engine nodes. Start with only the variables and functions needed by the current phase.

AF1. Session coordinator

Asset: BP_GameInstance — Blueprint Class → GameInstance. No custom Blueprint parent.

Important variables: PlayerProfile (BP_PlayerProfile object reference), WorldState (BP_WorldState object reference), GameCatalog (BPDA_GameCatalog reference), bSessionReady, PersistentRevision, LastSavedRevision, bSaveInFlight, InFlightRevision, InFlightSnapshot (BP_SaveGame reference), bSavePending, PendingTransition (S_TransitionRequest), TravelHandoff (S_RuntimeTravelState), and bTransactionInProgress.

Function categories:

Category Principal functions Boundary
Session InitializeSession, StartNewGame, TryLoadProfile, ValidateSession Construct/import models; do not grant rewards during import
Persistent transactions TryClaimWorldReward, CommitSwitchAndTargets, ActivateCheckpoint, CommitUniqueEncounter Validate everything before mutating; finish both models before broadcasting
Save RequestSave, BuildSnapshot, HandleSaveCompleted, RetrySave One active writer; immutable snapshots; dirty state follows revisions
Travel RequestAreaTravel, PrepareTravelHandoff, RequestCheckpointRecovery, ResolveRecoveryDestination Normal travel and recovery use distinct policies
Definitions ResolveAreaDefinition, ResolveItemDefinition, ValidateCatalog Stable ID lookup; actionable failure instead of silent substitution

Events/dispatchers: OnSessionReady, OnPersistentCommit, OnSaveStatusChanged, OnTransitionRequested. Do not retain the old PlayerCharacter, door, or Controller as a persistent reference after travel. Temporary transition participants must be explicitly released.

Commit protocol: standalone Profile operations, such as equipping an owned item, validate and commit synchronously, then emit one OnProfileCommitted event containing the change category. GameInstance binds that event once, increments PersistentRevision, and requests a save. Profile also emits its presentation/build change events after the complete mutation. A failed request emits a result, not a commit.

For a transaction touching both Profile and WorldState, GameInstance calls their internal commit functions with notifications deferred, commits both value changes, increments the revision once, then publishes the accumulated domain events and one persistent-commit notification. Do not emit a standalone Profile commit and also independently count the same cross-model transaction. bTransactionInProgress rejects reentrant mutation requests raised synchronously by event listeners. Queries remain safe after the values have been committed.

All validation that could fail belongs before mutation. Do not put a Delay, asynchronous asset load, save call, or UI interaction between the first and last mutation. This is an application-level transaction convention, not a database transaction supplied by Unreal.

AF2. Permanent character model

Asset: BP_PlayerProfile — Blueprint Class → Object. Construct it, do not Spawn Actor.

Variables: TotalXP, CachedLevel, UnspentSkillPoints, PurchasedSkillIds (Set of Name), InventoryEntries (Array of S_InventoryEntry), EquippedEntries (Map from E_EquipmentSlot to Guid), and catalog reference. Future genuinely permanent stat grants belong here only when that mechanic is committed. Do not serialize the current final-stat cache.

Principal functions: InitializeNewProfile, ImportSnapshot, ExportSnapshot, GetInventoryView, TryAddItems, TryRemoveItem, CanUseItem, TryEquip, TryUnequip, AwardXP, GetSkillAvailability, TryPurchaseSkill, GetUnlockedAbilityIds, GetBuildInputs. Separate public validation/query functions from internal mutation helpers.

Dispatchers: OnProfileCommitted, OnInventoryChanged, OnEquipmentChanged, OnProgressionChanged, OnSkillStateChanged, OnBuildChanged. OnBuildChanged fires once after a complete equipment/skill/progression mutation, not once per field changed. Consumers then request the complete current build.

ImportSnapshot validates definition IDs, quantities, unique entry GUIDs, skill references, and equipped-entry ownership. Recalculate cached/derived values without awarding XP, refunding points, or firing pickup effects. Version migrations are deliberate functions, not silent guessed repairs.

A Profile query may use the read-only catalog. It must not find the player Actor, open a level, create a widget, or start a world timer. Applying a consumable to the live body is coordinated with the owning Controller/body and only consumes the quantity after target validation. The item definition can supply ImmediateHealAmount for the initial consumable; phase 9 adds an optional timed-effect definition ID. This scalar does not modify base stats or create an additional state owner.

AF3. Permanent world model

Asset: BP_WorldState — Blueprint Class → Object.

AF8. Snapshot and definitions

Asset: BP_SaveGame — Blueprint Class → SaveGame. Store S_SaveHeader, S_CharacterSave, S_WorldSave, and S_RecoveryData. These are Blueprint Structure assets, with no Blueprint parent. Treat the snapshot as immutable from the moment writing starts. Live gameplay never uses it as the Profile object.

Definition schemas: the BPDA_ classes in Part B are Blueprint Classes derived from PrimaryDataAsset. Their DA_ content objects are Data Asset instances, created by selecting the compiled schema in the Data Asset picker. Keep a stable explicit definition ID even if the content asset's filename changes. Do not rely on an asset rename as a save migration strategy. [E6]

AF9. Blueprint hygiene that affects correctness

When a Map returns a structure, explicitly work on a local copy and add/set the modified value back to the Map. Do not assume a nested field edit mutated the stored value. Validate indexes and IsValid Actor references after any delayed/asynchronous boundary.

Override a parent initialization/cleanup hook intentionally and call the parent implementation where the lifecycle contract requires it. An enemy child should select data or implement one attack hook, not copy the base's entire death graph. Clear timers, unregister candidate targets, and unbind dispatchers in the relevant teardown path. Keep debug output contextual: stable ID, area, function, expected state, and actual state.

Use comments and function categories for ownership boundaries. A visually neat graph that mutates another model's internal fields is still an architectural error.

PART AH — Refactor checkpoints

Gate 1: after movement, before combat

Inspect BP_PlayerCharacter (PaperCharacter → Character), BPC_ActionState (ActorComponent), and BPC_FlipbookAnimator (ActorComponent). Confirm that native floor/velocity state is not duplicated by contradictory visual booleans, jump execution has one path, and landing presentation cannot block a buffered jump. Stop feature work until the same tests pass at the selected frame-rate targets.

No new Blueprint is required. Move misplaced animation selection into the existing animator and action permission rules into the existing action component. Keep the movement policy in the Character rather than extracting an unnecessary movement manager.

Gate 2: after the persistence slice, before inventory breadth

Inspect BP_GameInstance (GameInstance), BP_PlayerProfile (Object), BP_WorldState (Object), and BP_SaveGame (SaveGame). Kill the player after progress made beyond checkpoint activation; travel away and return; exit and load. Search for direct writes to SaveGame and runtime Actor references in snapshot structs.

A transaction must not publish partially updated models. A failed save must not clear dirty state. Repeated calls to a persistent pickup must grant once. Resolve these errors before authoring dozens of persistent objects.

Gate 3: after equipment and passive skills

Inspect BPC_Stats (ActorComponent), the Profile model, and BPC_FlipbookAnimator (ActorComponent). Equip/unequip and buy/load repeatedly; final values must not creep upward, old equipment visuals must not remain attached, and skill points must not be awarded again by loading.

Check that inventory is the only owner of entry instances and equipment stores references to those entries. Check that the skill widget's availability matches the Profile query without recreating the rules in widget graphs.

Gate 4: after active abilities and effects

Inspect BPC_Abilities (ActorComponent), BPC_StatusEffects (ActorComponent), BP_AbilityBase (Actor), and action-token handling. Interrupt an ability in every phase, destroy its target, die, pause, and change areas. Watch for lingering executors, duplicated timers, charges incorrectly restored, and callbacks clearing a newer action lock.

Do not add another layer of managers to cover cancellation bugs. Make Start, Cancel, Finish, and teardown idempotent and keep cooldown authority in the abilities component.

Gate 5: before scaling world content

Audit all placed persistent IDs, area/spawn targets, definition IDs, cook references, and source-control naming. Exercise missing/corrupt/older save generations with BP_ArchitectureTestHarness (Actor) in L_SystemTests, a Level asset (World) with no Blueprint parent.

Measure whether area load times or memory actually justify streaming. The default remains area-map travel. Introduce a different loading strategy only with measured need and a plan to preserve initialization, recovery, and state-application contracts. Do not begin a speculative streaming or native-code rewrite as a substitute for finishing the representative slice.
